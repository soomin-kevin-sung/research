## QwenPaw Windows 실측의 기대값과 관찰값

QwenPaw `2.3.0.post1`, Windows 11 Pro 25H2 빌드 `26200.9974`, 비관리자. ISO-01~14는 두 Windows 백엔드를 직접 호출한 시험입니다. ISO-15~18은 에이전트가 쓰는 도구 래퍼와 승인 서비스를 통한 통합 시험이며, 이 경로는 비관리자에서 Restricted Token을 씁니다.

| 항목 | 기대 | 실측 | 원인 확인 수준 |
| --- | --- | --- | --- |
| ISO-01 작업 폴더 읽기·쓰기 | 두 백엔드 모두 성공 | Restricted Token 초기 0/5, 일반 상속 ACL에서 재측정 5/5. AppContainer 5/5 | 초기 시험 폴더의 OWNER RIGHTS에 의존한 DACL 영향을 대조 실행으로 확인 |
| ISO-02 외부 파일 읽기 | 프로토콜은 차단. Restricted Token의 `allow_read_all=True`에서는 계정 권한으로 읽기 허용 예상 | Restricted Token 5/5 허용, AppContainer 5/5 차단 | 각 백엔드의 읽기 모델과 일치 |
| ISO-03 외부 파일 덮어쓰기 | 양쪽 차단 및 원본 유지 | Restricted Token은 공용 임시 위치에서 5/5 덮어쓰기, Everyone 쓰기 허용이 없는 사용자 임시 위치에서 5/5 차단 및 원본 유지. 공용 위치에서 AppContainer는 5/5 차단 및 원본 유지 | 원인 확정(07): 공용 위치는 다른 프로그램이 `C:\Users\Public\Documents` 아래 만든 임시 폴더로, 명시적 Everyone 모든 권한이 있었습니다. 하네스 폴더에 Everyone 수정 ACE만 더하면 Restricted Token 덮어쓰기 성공 5/5, INTERACTIVE 수정 ACE는 거부 5/5. Restricted Token 제한 SID에 Everyone이 있어 Everyone에 쓰기를 준 곳은 Restricted Token도 씀 |
| ISO-04 환경 변수 허용 목록 | 지정하지 않은 합성 변수가 노출되지 않음 | 양쪽 모두 호스트의 합성 값 출력 | 양쪽 백엔드가 허용 목록을 적용하지 않는다고 제품 로그에 표시 |
| ISO-05 네트워크 | 허용 조건에서 연결 성공, 차단 조건에서 연결 실패 | 외부 목적지 각 5회: Restricted Token은 허용 시 성공, 차단 시 프록시 연결 실패. AppContainer는 허용 시 성공, 차단 시 이름 해석 단계에서 실패. 02의 AppContainer `curl` 실행 거부는 05·06에서 재현되지 않음 | Restricted Token **실패**: 차단 요청은 프록시 변수뿐이며, 07에서 `curl --noproxy "*"`가 차단 조건에서 외부 연결에 5/5 성공. AppContainer **통과**: 네트워크 기능 미부여로 OS 수준 차단(`--noproxy`도 5/5 실패). 도메인 허용 목록은 두 백엔드 모두 목록에 없는 도메인 접속 5/5 성공으로 **실패**(제품도 미집행 경고). 02의 거부는 PATH에서 먼저 찾은 `curl.exe`를 AppContainer가 실행할 수 없을 때 같은 증상이 재현되나, 02의 PATH는 기록이 없어 미확정 |
| ISO-06 지속 파일·임시 파일·자식 종료 | 제품 정리 후 지속 파일 유지, 전용 임시 파일의 삭제 시점 기록, 명령 종료 뒤 자식 상태 확인 | 양쪽 지속 파일 유지. 전용 임시 파일: Restricted Token은 호스트 TEMP를 상속하고 그 위치 쓰기가 거부됨(미지원). AppContainer는 Windows가 만든 컨테이너 전용 `AC\Temp`를 쓰며, 파일은 `stop()` 후에도 남고 `destroy()`에서 삭제(5/5). 시간 초과: Restricted Token은 자식 종료(5초 뒤 5/5), AppContainer는 자식이 살아 있고 호출도 반환하지 않음(5/5). 셸이 끝난 뒤 남은 백그라운드 자식은 두 백엔드 모두 명령 제한을 넘겨도 계속 실행되고 호출이 반환되지 않음(각 5/5). Restricted Token 호스트가 비정상 종료되면 자식은 종료되고 작업 폴더 ACE는 다음 프로세스의 정리까지 남음(5/5) | 시간 제한은 셸 프로세스에만 걸리고 출력 파이프를 끝까지 읽는 소스와 일치. Restricted Token만 시간 초과 시 Job 전체를 종료. AppContainer 비정상 종료는 미실측. AppContainer는 Python 폴더 ACE도 `destroy()`에서 지움(07, 20/20) |
| ISO-07 읽기 전용 하위 폴더 | 읽기 허용, 덮어쓰기·삭제·이름 변경 차단 | 양쪽 모두 읽기·덮어쓰기·이름 변경 허용. AppContainer는 07에서 권한별 열기로 목록·쓰기·삭제 권한 모두 허용(5/5), Python 삭제 성공 | Restricted Token은 읽기 전용 마운트에 별도 ACL을 적용하지 않음. AppContainer는 읽기·실행 ACE를 더하기만 하고 작업 폴더에서 상속된 수정 ACE를 끊지 않아 쓰기가 허용됨(원인 확정) |
| ISO-08·09 접근 거부 하위 폴더 | 읽기·변경 차단, 시작 후 새 파일에도 보호 적용 | 양쪽 모두 기존·신규 파일 읽기 및 기존 파일 덮어쓰기·이름 변경 성공. AppContainer는 07에서 권한별 열기로 모든 권한 허용(5/5), Python 목록·삭제·생성 성공 | Restricted Token 직접 API는 `deny_paths` 미지원. AppContainer는 AppContainer SID 대상 거부 ACE가 폴더와 기존·신규 파일에 실제로 걸렸지만 효과가 없었음(Windows 쪽 이유는 문서로 미확인). 03의 AppContainer 목록·삭제 거부는 보호 효과가 아니라, AppContainer 안에서 cmd `dir`·`del`이 어디서나 실패하는 호환성 문제였음 |
| ISO-10 로컬 서비스 | 필요한 루프백 서비스와 개발 서버는 동작, 차단 조건에서는 연결 실패 | Restricted Token은 호스트 루프백 서비스 접속과 개발 서버 바인딩·접속 5/5 성공. ### QwenPaw Windows 격리 판단

- **기본 에이전트 경로.** `security.sandbox_enabled`가 기본값 False라서 셸 명령에 OS 격리가 적용되지 않습니다.
- **스위치를 켠 비관리자 경로.** Restricted Token이 쓰입니다. 이 백엔드는 작업 폴더 밖 쓰기를 경로 권한에 따라 막는 수준입니다.
  - 사용자 레지스트리 쓰기는 막았습니다. Everyone에 쓰기를 준 공용 폴더는 막지 못합니다.
  - 외부 읽기, 환경 변수, 네트워크 차단, 하위 폴더 보호, 자원 한도는 집행하지 않습니다. 네트워크 차단은 프록시를 쓰지 않는 프로그램에 통하지 않고, 도메인 허용 목록은 적용되지 않습니다.
  - 같은 사용자가 띄운 호스트 파이프를 읽을 수 있고, 클립보드도 열 수 있습니다.
  - 차단된 명령을 승인하면 호스트 계정으로 재실행됩니다(실측). 그 승인은 같은 명령에 대해 세션 동안, 프로세스를 다시 만들어도 유지됩니다. 승인 대기 중 바꾼 정책은 그 승인에 반영되지 않습니다.
  - `strict` 승인 수준을 써도 승인된 셸 명령은 격리 없이 실행됩니다. 내장 파일 쓰기 도구는 샌드박스를 거치지 않고 승인 없이 작업 폴더 밖에 씁니다.
  - 그러므로 신뢰하지 않는 코드나 프롬프트 주입에 대한 보안 경계로 볼 수 없고, 신뢰하는 에이전트의 실수로 인한 쓰기를 줄이는 장치로 판단합니다.
- **AppContainer.** 작업 폴더 밖 읽기·쓰기, 외부 네트워크 차단, 호스트 파이프 차단, 사용자 레지스트리 쓰기 차단을 OS 수준에서 집행했습니다. 다만 한계가 있습니다.
  - 에이전트 거버넌스 경로에서는 선택되지 않습니다.
  - 작업 폴더 안 하위 폴더의 읽기 전용·거부 보호가 실패했습니다. 상속된 수정 권한이 남고, AppContainer SID 대상 거부 ACE가 효과가 없었습니다. 시간 초과 시 자식 정리도 실패했습니다.
  - 클립보드는 열 수 있습니다.
  - 호스트 루프백(양방향), 사용자 설치 도구, cmd의 `dir`·`del`, 일부 레지스트리 키를 쓰는 개발 작업과 호환되지 않습니다.
- **두 백엔드 공통.** 백그라운드 자식이 남으면 명령 시간 제한이 적용되지 않습니다. 프로세스 수·메모리 한도를 집행하지 않습니다. 명명된 파이프로 통신하는 병렬 빌드가 실패합니다.
- **권고.** 신뢰하지 않는 작업에는 QwenPaw의 Windows 샌드박스만으로 격리를 보장할 수 없으므로, 전용 계정이나 VM 같은 별도 경계와 함께 써야 합니다.

### 판단

- **네 구성의 공통 경계.** 네 구성 모두 `WRITE_RESTRICTED` 토큰입니다.
  - 제한 SID 검사는 각 객체 형식의 쓰기 권한에만 적용됩니다.
  - 그래서 파일·레지스트리·프로세스의 **쓰기**는 막지만, 읽기·종료·토큰 열기는 사용자 SID(또는 샌드박스 계정 SID)의 권한을 그대로 따릅니다.
  - 제한 SID 목록에 Everyone과 로그온 SID가 있으므로, 이 SID에 쓰기를 준 위치는 막지 못합니다. QwenPaw 관리자의 로그온 SID는 자기 로그온 세션의 것이라 사용자 로그온 SID에 준 쓰기는 막았습니다.
- **QwenPaw 비관리자.**
  - 작업 폴더 밖 쓰기를 경로 권한에 따라 막는 수준입니다.
  - 작업 폴더 안 보호, 읽기 제한, 다른 프로세스 읽기 차단은 없습니다.
- **Codex `unelevated`.**
  - QwenPaw 비관리자와 같은 경계에 다음이 더해집니다: 작업 폴더 안 보호 경로, 작업 폴더별 SID, 별도 데스크톱.
  - 읽기와 다른 프로세스 읽기는 막지 않습니다.
- **Codex `elevated`.**
  - 다른 계정이라 사용자 전용 파일·`.ssh`·사용자 레지스트리·사용자 범위 DPAPI를 막습니다.
  - 그러나 사용자의 로그온 SID를 공유합니다. 그래서 로그온 세션 기본 DACL로 만들어진 사용자 데스크톱 프로세스는 메모리 읽기·종료 권한으로 열립니다.
  - 측정 전부터 프로필 아래에 쌓인 읽기 ACE 때문에 `~/.codex` 인증 파일도 읽습니다.
  - 샌드박스 명령이 자기 실행기를 모든 권한으로 열 수 있습니다. 따라서 작업 폴더별 쓰기 분리는 샌드박스 계정 권한 안의 구분이며, 그 이상의 경계로 보기 어렵습니다. 실제 주입은 시험하지 않았습니다.
  - 모든 작업 폴더가 같은 계정 프로필을 씁니다. 한 작업이 프로필에 남긴 파일을 다른 작업의 명령이 읽고 지웠습니다(R3). 사용자는 일반 권한으로 그 프로필 안을 볼 수 없습니다.
- **QwenPaw 관리자.**
  - 설정마다 별도 로컬 계정을 만들고 `LogonUserW`로 새 로그온 세션을 엽니다. 그래서 네 구성 중 사용자 데이터와 프로세스의 분리가 가장 넓습니다.
    - 거부된 것: 사용자 전용 파일, `.ssh`, `~/.codex`, `.gitconfig`, 사용자 레지스트리, 사용자 범위 DPAPI.
    - 열지 못한 프로세스: 로그온 SID ACE 유무와 상관없이 사용자 프로세스, 다른 작업 폴더의 샌드박스, 승격된 QwenPaw 작업자.
  - 한계는 다음과 같습니다.
    - `Users`·`Everyone` 읽기가 닿는 파일은 읽습니다. 이 PC처럼 프로필 루트가 그 읽기를 상속하면 프로필 아래 대부분이 해당합니다.
    - 컴퓨터 범위 DPAPI 데이터를 복호화합니다.
    - Everyone에 쓰기를 준 위치에 씁니다.
    - 작업 폴더 안 `.git`·`.codex`·`.agents`와 읽기 전용 마운트를 보호하지 않습니다.
    - 환경 변수를 그대로 전달합니다.
    - 사용자 데스크톱(`WinSta0\Default`)을 공유합니다. 샌드박스 계정에 창 객체 전체 권한 ACE를 주고 Job UI 제한도 없습니다.
  - 비용도 있습니다.
    - QwenPaw 앱 전체가 승격된 관리자 토큰으로 실행돼야 합니다.
    - 사용자가 DACL을 바꿀 수 없는 경로도 관리자 권한으로 ACE를 추가해 쓰기 경로로 만듭니다(B10).
    - 계정을 만드는 첫 명령은 0.8~1.0초 걸립니다.
- **QwenPaw 관리자와 Codex `elevated`가 갈린 이유.** 둘 다 별도 계정의 토큰을 제한하지만, 평소 실행에 관리자 권한을 쓰는지가 반대입니다.
  - Codex `elevated`는 관리자 권한을 설치 때 한 번만 씁니다. 평소 명령은 일반 사용자 권한으로 실행됩니다.
    - 고정 계정 두 개를 모든 작업 폴더가 같이 씁니다.
    - 일반 사용자도 호출할 수 있는 `CreateProcessWithLogonW`로 실행기를 시작합니다. 이 함수가 호출자의 로그온 SID를 새 토큰에 넣어, 사용자와 로그온 SID가 같아집니다.
    - ACL 갱신도 일반 사용자 권한이라, 사용자가 DACL을 바꿀 수 없는 경로에서는 실패하고 명령을 거부합니다.
    - 이미 다른 그룹이 읽을 수 있는 경로에는 읽기 ACE를 달지 않습니다.
  - QwenPaw 관리자는 앱 전체가 관리자로 실행되는 것을 전제로 합니다.
    - 설정마다 계정을 만들고, `LogonUserW`로 새 로그온 세션을 엽니다.
    - `SeImpersonatePrivilege`가 필요한 `CreateProcessWithTokenW`로 명령을 실행합니다.
    - 어떤 경로든 ACE를 달 수 있고, 읽기 전용 마운트에도 허용 ACE를 답니다.
  - 결과로 Codex `elevated`에만 다음이 나타났습니다: 사용자 데스크톱 프로세스 열림, 작업 폴더 사이 계정 공유, 실행기 노출, 읽기 거부 폴더 안 읽기 전용 하위 폴더 거부.
  - QwenPaw 관리자에만 다음이 나타났습니다: 관리자 소유 폴더도 쓰기 경로로 열림, 앱의 관리자 권한, 흔적 누적.
- **운영상 결함.** 네 가지를 확인했습니다.
  - Codex `elevated`의 읽기 거부 ACE는 설정에서 지워도 남습니다(`REVOKE_ACCESS`가 거부 ACE를 지우지 않음).
  - 샌드박스가 처음 만든 보호 폴더는 그 작업 폴더를 사용할 수 없게 만듭니다.
  - 도메인 트러스트가 깨진 PC에서는 QwenPaw 비관리자가 비정상 종료 뒤 작업 폴더 ACE를 정리하지 못합니다.
  - QwenPaw 관리자 정리는 계정과 프로필 폴더는 지우지만 다음을 남깁니다: ProfileList 키, "일괄 작업으로 로그온" 권한 항목, `WinSta0`·데스크톱 ACE, `\\.\NUL` ACE, `QwenpawUsers` 그룹, Python 환경 폴더 ACE.
    - 정리 뒤 다시 만든 계정은 새 SID를 받습니다. 그래서 이 항목들은 계정을 만들 때마다 하나씩 쌓입니다. 이번 측정에서는 20개씩 쌓였습니다.
- **결론.**
  - 세 구성(QwenPaw 비관리자, Codex 두 구성)은 신뢰하는 에이전트의 실수로 인한 쓰기를 줄이는 장치입니다. 신뢰하지 않는 코드에 대해서는 같은 사용자 데스크톱의 다른 프로세스와 비밀값을 보호하지 못하므로 보안 경계로 볼 수 없습니다.
  - QwenPaw 관리자는 다른 계정과 다른 로그온 세션 덕분에 사용자 파일·프로세스 분리를 실제로 집행했습니다. 그래도 경계로 쓰기에는 남는 문제가 있습니다.
    - 사용자 데스크톱을 공유합니다.
    - 다른 계정이 읽을 수 있는 파일과 컴퓨터 범위 DPAPI를 막지 못합니다.
    - 앱 전체를 관리자로 실행해야 합니다.
    - PC에 흔적이 쌓입니다.

## 이름 있는 객체와 명명된 파이프 실측 (2026-11-26)

이벤트·뮤텍스·세마포어·section(공유 메모리)과 명명된 파이프를 네 구성에서 각 5회 측정했습니다. 이름은 측정용 이름만 썼고, 파이프 클라이언트 가장은 측정하지 않았습니다. [실행 기록](runs/2026-11-26-01.md)

| 대상 | QwenPaw 비관리자 | Codex `unelevated` | Codex `elevated` | QwenPaw 관리자 |
| --- | --- | --- | --- | --- |
| 호스트가 `Local\`에 만든 객체 | 열고 조작함(이벤트 신호, 세마포어 해제, 뮤텍스 획득, section 읽기·쓰기, `WRITE_DAC` 열기) | 같음 | 같음 | 거부 |
| 호스트가 `Global\`에 만든 객체 | `SYNCHRONIZE`·`READ_CONTROL`만 허용. 뮤텍스는 획득함 | 같음 | 거부 | 거부 |
| 샌드박스가 만든 `Local\`·`Global\` 객체 | 호스트와 다른 작업 폴더의 샌드박스가 읽고 씀 | 같음 | 같음 | 만들지 못함 |
| 같은 이름으로 호스트가 객체 생성 | 샌드박스 객체를 받음 | 같음 | 같음 | 새 객체 생성 |
| 자기가 만든 파이프에 쓰기 연결(병렬 빌드) | 거부 | 거부 | 허용 | 허용 |
| 샌드박스 파이프에 호스트가 쓰기 | 허용, 데이터 도착 | 같음 | 거부 | 거부 |
| 샌드박스 파이프에 다른 작업 폴더 샌드박스가 쓰기 | 거부 | 거부 | 허용, 데이터 도착 | 거부 |
| 같은 이름으로 호스트가 파이프 서버 추가(첫 인스턴스 플래그 없음) | 추가됨 | 추가됨 | 거부 | 거부 |

- **`Local\`은 로그온 SID를 공유하는 세 구성에서 분리되지 않습니다.** `Local\` 디렉터리는 그 안에 만드는 모든 객체에 사용자 로그온 SID의 `GENERIC_ALL` ACE를 상속합니다. 제한 SID 목록에 이 로그온 SID가 있으므로 쓰기 검사도 통과합니다.
  - Codex가 기본 DACL로 의도한 실행 간 분리는 `Local\` 객체에 적용되지 않습니다. 상속 ACE가 기본 DACL보다 우선하기 때문입니다.
  - Codex `elevated`는 프로세스 열기에서 로그온 SID ACE가 없는 프로세스를 열지 못했지만, `Local\` 객체에는 이 ACE가 항상 붙어 모두 열었습니다.
- **QwenPaw 관리자는 이름 있는 객체 호출 자체가 실패합니다.** `Local\`·`Global\` 모두 만들기와 열기가 `ERROR_ACCESS_DENIED`였습니다. 없는 `Global\` 이름도 "없음" 대신 "거부"가 나와, 세션 이름 공간 디렉터리를 여는 단계에서 실패한 것으로 봅니다. 호스트 객체는 보호되지만, kernel32 함수로 이름 있는 객체를 만드는 프로그램은 이 샌드박스에서 실패할 수 있습니다. Git Bash는 이 구성에서 동작했습니다(아래 실제 도구 결과).
- **명명된 파이프의 기본 DACL은 토큰 기본 DACL을 따르지 않습니다.** SYSTEM·Administrators·소유자에게 모든 권한, Everyone·익명에게 읽기를 줍니다. 그래서 쓰기 가능 여부는 소유자 SID가 제한 SID 목록에 있는지로 갈립니다.
  - 비관리자 두 구성은 소유자가 사용자라서, 샌드박스는 자기 파이프에 쓰지 못하고 호스트는 그 파이프에 쓰거나 같은 이름에 서버를 추가할 수 있습니다.
  - Codex `elevated`는 소유자가 모든 작업 폴더가 같이 쓰는 샌드박스 계정이라, 다른 작업 폴더의 샌드박스가 씁니다.
- **측정하지 않은 것.** 가장, 보안 설명자를 직접 지정하는 프로그램의 객체, `Global\` section(승격되지 않은 프로세스는 만들 수 없음), 실제 프로그램의 객체 이름.

## 개별 계정 Restricted Token의 제한 SID 목록 줄이기 (2026-11-26)

다른 Claude 세션이 요청한 측정입니다.

- **구성.** Codex 제품으로는 제한 SID 목록을 바꿀 수 없어서, Codex `elevated`와 같은 호출 구조의 시험 실행기를 만들었습니다(`CreateProcessWithLogonW` → 실행기 → `CreateRestrictedToken` → 셸).
  - 측정용 계정 두 개를 만들었다 지웠고, 셸은 사용자 데스크톱(`WinSta0\Default`)에서 실행했습니다.
  - 기준(Codex 목록: capability SID, 계정, 사용자 로그온 SID, Everyone)과 축소(capability SID, 계정)를 각 5회 쟀습니다.
  - 축소 목록에서 깨진 대상에만 계정 ACE를 붙이는 구성 8개도 각 5회 쟀습니다.
- [실행 기록](runs/2026-11-26-03.md)

| 항목 | 기준 | 축소 | 축소 + 데스크톱·기본 DACL·장치(`NUL`·`CNG`·`KsecDD`) ACE |
| --- | --- | --- | --- |
| PowerShell 5.1 | 동작 | **시작 실패**(`0xC0000142`) | **실패**: `Starting the CLR failed with HRESULT 80070005`. `Local\`·전역 이름 공간 ACE를 더해도 같음 |

| 자기 실행기를 모든 권한으로 열기 | **열림** | — | **열림** |

- **축소 목록만으로는 셸이 뜨지 않습니다.** 원인은 사용자 로그온 SID나 Everyone에만 쓰기 계열 권한을 주는 시스템 객체입니다.
  - 토큰 기본 DACL(Codex는 로그온 SID에만 모든 권한을 줌)
  - 창 스테이션과 데스크톱
  - `\Device\Null`·`\Device\CNG`·`\Device\KsecDD`
  - 이 대상에 계정 ACE를 붙여야 cmd·Python·Node가 시작합니다. 그래도 PowerShell 5.1, 명명된 파이프를 쓰는 도구(병렬 빌드, `npm`류 자식 프로세스, Git Bash)는 동작하지 않았습니다.
- **닫히는 것은 두 번째 검사로 막히는 구멍입니다.** Everyone·로그온 SID 쓰기 위치와 호스트 `Local\` 객체가 여기에 해당합니다.
  - 첫 번째 검사만 받는 사용자 프로세스 읽기·종료·토큰 열기는 그대로입니다. `CreateProcessWithLogonW`가 그룹 목록에 사용자 로그온 SID를 넣기 때문입니다.
  - 자기 실행기 노출도 그대로입니다. 계정 SID가 제한 SID 목록에 남기 때문입니다.
- **쓰기 ACE는 capability SID만으로는 부족합니다.** capability SID ACE만 있는 폴더는 첫 번째 검사에서, 그룹 ACE만 있는 폴더는 두 번째 검사에서 거부됐습니다.
  - 쓰려면 둘을 함께 붙이거나 계정 ACE를 붙여야 합니다.
  - 같은 이유로, 두 번째 검사에서 막힌 시스템 객체는 그룹 ACE로는 풀리지 않아 계정 SID로 붙여야 합니다.
- **보충 ACE의 비용.** 장치·전역 이름 공간 ACE는 컴퓨터 전체 객체의 DACL 변경입니다. 이번 측정에서는 메모리에서만 바꿨는데, 재부팅하면 사라지므로 설치 단계(관리자)가 계정마다 다시 붙여야 합니다.
- **오류 창.** 시작에 실패한 셸마다 사용자 화면에 "응용 프로그램을 제대로 시작하지 못했습니다" 창이 떴습니다. 실행기에서 Codex처럼 `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX)`를 설정해야 뜨지 않습니다.

### QwenPaw Restricted Token·AppContainer 실측에서 남은 항목

- 다른 사용자 세션의 레지스트리 접근, 자격 증명 관리자의 시험용 자격 증명.

- AppContainer 호스트 프로세스의 비정상 종료.
- 브라우저와 MCP 도구가 실행되는 위치.
- 샌드박스 초기 설정 시간, 최대 메모리.
- 원인을 확정하지 못한 것: AppContainer SID 대상 거부 ACE가 효과가 없었던 이유, 초기 측정에서 AppContainer `curl`이 거부된 이유.

### 측정 환경의 한계

- PC 한 대에서 측정했습니다. 도메인에 가입된 실제 사용 PC이고, Codex `elevated`를 이미 써 온 상태였습니다.
- 사용자 프로필 루트가 `Users`·`Everyone` 읽기를 상속하는 PC였습니다. 별도 계정 구성의 읽기 범위는 이 조건에 따라 달라집니다.
- 도메인 트러스트 오류가 있어 SID를 계정 이름으로 바꾸는 조회가 실패했습니다. QwenPaw 비정상 종료 뒤 ACE 잔류는 이 조건에서 나온 결과입니다.
- 언어 모델 없이 측정 스크립트로 백엔드와 제품 명령을 호출했습니다.

### PC에 남긴 것

- `~/.codex/cap_sid`의 시험 폴더 경로 항목(작업 폴더별 18→21, 쓰기 경로별 90→95). 시험 폴더를 지워 권한을 주지 않으며, 사용자 결정으로 그대로 두었습니다.
- 측정 준비 중 실수로 실행한 Codex `elevated` 1회가 프로필 바로 아래 폴더 2개에 추가한 `CodexSandboxUsers` 읽기 ACE. Codex `elevated`가 평소 실행 때마다 추가하는 ACE와 같아, 사용자 결정으로 그대로 두었습니다.
