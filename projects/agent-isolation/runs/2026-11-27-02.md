## A1. 프록시 경유 외부 접속 (칸마다 5회)

**방법.** 인증 없는 프록시를 띄우고, Codex offline 칸과 호스트 칸을 번갈아 5회씩 실행했습니다. 셸 안 작업은 다음과 같습니다.

- TCP 리스너 표(`GetExtendedTcpTable`, 소유 PID 포함)에서 프록시 포트와 PID 찾기
- `example.com`에 직접 HTTP·HTTPS(Python, 프록시 설정 없음)
- 프록시를 거친 평문 HTTP: 절대 주소 요청(Python 소켓), curl `-x`
- 프록시를 거친 HTTPS: `CONNECT example.com:443` 뒤 Python `ssl` 기본 설정(인증서와 이름 확인)으로 TLS를 맺고 `GET /`
- 프록시에 PC 안 대상 요청: `http://127.0.0.1:9/`, `CONNECT 127.0.0.1:445`

- Codex 방화벽 규칙은 루프백을 Codex 프록시 포트만 남기고 막는다고 소스에 적혀 있습니다([2026-11-26-04](2026-11-26-04.md)). 그런데 이번에도 [2026-11-27-01](2026-11-27-01.md)처럼 사용자 리스너에 닿았습니다. 원인은 확인하지 않았습니다.
- 결론: 네트워크 차단이 켜진 셸도 사용자 계정의 인증 없는 프록시가 있으면 공개 사이트에 평문 HTTP와 HTTPS로 닿습니다. 프록시의 공개 주소 판정은 PC 안 대상만 막습니다.

## A2. 포트 가로채기 (설정 점검, ○)

사용자 결정으로 셸 계정에서 bind를 시도하지 않고 소스와 문서만 읽었습니다.

- **Node가 리슨 소켓에 거는 옵션.**
  - libuv v1.51.0 [`src/win/tcp.c` 277–347행](https://github.com/libuv/libuv/blob/v1.51.0/src/win/tcp.c#L277-L347)
    - 주석에 따르면 `SO_REUSEADDR`는 다른 프로그램이 쓰는 포트를 「훔칠」 수 있어서 걸지 않습니다. `SO_EXCLUSIVEADDRUSE`는 TIME_WAIT 소켓까지 검사해서 걸지 않습니다.
    - `uv__tcp_try_bind`가 `bind` 전에 거는 소켓 옵션은 IPv6 소켓의 `IPV6_V6ONLY`뿐입니다.
    - `UV_TCP_REUSEPORT`를 주면 `ERROR_NOT_SUPPORTED`를 돌려줍니다(298행).
  - Node.js v24.15.0 [`lib/net.js` 172–181행](https://github.com/nodejs/node/blob/v24.15.0/lib/net.js#L172-L181): bind 플래그는 `ipv6Only`와 `reusePort`에서만 나옵니다. 측정용 프록시는 둘 다 쓰지 않습니다.
  - 따라서 프록시의 리슨 소켓은 옵션 없음(Microsoft 문서 표의 「Default」)입니다.
- **Windows의 bind 결과.** Microsoft 문서 [Using SO_REUSEADDR and SO_EXCLUSIVEADDRUSE](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse)의 「다른 사용자 계정」 표(Windows Server 2003 이후)입니다.
  - 첫 소켓은 옵션 없음이고 특정 주소(`127.0.0.1`)에 묶였습니다. 이때 다른 계정의 두 번째 bind 결과는 다음과 같습니다.

    | 두 번째 bind | 와일드카드(`0.0.0.0`) | 특정 주소(`127.0.0.1`) |
    | --- | --- | --- |
    | 옵션 없음 | 성공 | `WSAEADDRINUSE` |
    | `SO_REUSEADDR` | 성공 | `WSAEACCES` |
    | `SO_EXCLUSIVEADDRUSE` | `WSAEADDRINUSE` | `WSAEADDRINUSE` |

  - 첫 소켓이 `SO_EXCLUSIVEADDRUSE`를 걸고 특정 주소에 묶인 경우도 표의 결과가 위와 같습니다. 그래서 프록시가 이 옵션을 걸어도 다른 계정의 bind 결과는 바뀌지 않습니다.
  - 문서는 특정 주소의 첫 소켓 뒤에 와일드카드로 bind한 두 번째 소켓이 「첫 소켓의 특정 주소를 뺀 모든 인터페이스」에 묶인다고 설명합니다. 다만 이 설명은 첫 소켓이 `SO_EXCLUSIVEADDRUSE`를 건 경우의 예로 나옵니다. 옵션 없는 첫 소켓에 대해 같은 설명은 문서에 없습니다.
- **정리.**
  - ○ 셸 계정은 프록시가 듣는 동안 `127.0.0.1`의 같은 포트를 가져갈 수 없습니다. 클라이언트가 `127.0.0.1:<port>`로 붙으면 `0.0.0.0` bind로 그 연결을 받지는 못하는 것으로 봅니다.
  - ○ 프록시는 포트 0으로 시작하므로, 셸이 미리 특정 포트를 잡아 두어도 프록시는 다른 빈 포트를 받습니다.
  - ? 프록시가 닫힌 뒤에도 클라이언트가 옛 포트를 계속 쓰는 경우는 확인하지 않았습니다. 그때는 그 포트가 비어 있어 다른 계정도 bind할 수 있습니다.

## A3. 인증 시제품 (칸마다 5회)

**시제품의 동작.** 프록시 스크립트에 인증 파일(`proxy:<32바이트 무작위 값, base64url>`)을 주면 다음처럼 동작합니다.

- 모든 평문 HTTP 요청과 `CONNECT`에서, URL 해석과 이름 조회보다 먼저 `Proxy-Authorization`을 확인합니다.
- `Basic` 스킴(대소문자 무시)의 base64 값을 풀어 SHA-256으로 해시하고, 기대값의 해시와 `crypto.timingSafeEqual`로 비교합니다.
- 값이 없거나 형식이 다르거나 틀리면 `407 Proxy Authentication Required`와 `Proxy-Authenticate: Basic realm="local-proxy"`를 돌려주고 연결을 닫습니다.
- 통과하면 원래 프록시와 같고, 위로 보내는 헤더에서 `Proxy-Authorization`을 뺍니다.

## B3. OneDrive (측정 불가)

- OneDrive는 컴퓨터 단위로 설치되어 있고 계정 설정도 있었지만, 측정 때 프로세스가 실행 중이 아니었습니다. 이 상태와 실행 중 여부만 읽었습니다.
- 사용자 결정으로 OneDrive를 켜지 않았습니다. 켜면 시험 폴더가 클라우드로 올라가기 때문입니다. 로그인과 설정도 바꾸지 않았습니다.
- 그래서 ACE 변경이 다시 동기화를 일으키는지, 셸 계정이 온라인 전용 파일을 읽을 때 내려받기가 일어나는지는 재지 못했습니다.

| 관리자 토큰(UAC 단계) | 읽음(1회) | 읽음(1회) | — |

- `KEY_READ`와 `KEY_QUERY_VALUE`의 결과는 모든 칸에서 같았습니다.
- 현재 사용자는 관리자이지만 UAC 필터 토큰에서는 Administrators가 거부 전용입니다. 그래서 Administrators 허용 ACE가 적용되지 않고, 설치자가 아닌 키는 거부됐습니다.
- ○ 셸 계정(B)과 Codex offline은 거부 ACE에 걸리는 그룹에 속합니다. 그런데 이 DACL에는 그들에게 맞는 허용 ACE도 없습니다. 거부 ACE를 뺀 DACL은 재지 않았지만, 원리상 결과는 같습니다. 거부 ACE는 나중에 Users 등에 허용 ACE가 더해질 때를 대비하는 역할입니다.
- 부모 키는 `HKLM\SOFTWARE`에서 Users 읽기를 상속하므로 누구나 열고 하위 키 이름을 봅니다. 값은 하위 키에만 두었습니다.
