## 3. 네트워크: 외부와 루프백 (조건마다 각 5회)

- AppContainer는 네트워크를 허용할 때 `internetClient`·`internetClientServer`·`privateNetworkClientServer` 기능을 부여합니다(`sandbox/windows_appcontainer_sandbox.py:315-335`). QwenPaw 소스에는 루프백 예외를 설정하는 코드가 없습니다.

- AppContainer 안에서 `ping`은 `Unable to contact IP driver. General failure.`로 바로 끝났습니다. ICMP를 쓰는 진단 도구도 사용할 수 없습니다.

## 4. 자식 프로세스 수명 (조건마다 각 5회)

`ping`은 AppContainer 안에서 실행되지 않으므로, 두 백엔드에 같은 자식을 쓰기 위해 고유 표식이 붙은 `cmd /d /c` 무한 루프를 사용했습니다. 측정 전 호스트에서 이 루프가 계속 실행되는 것을 확인했습니다. 같은 프로세스인지는 PID와 생성 시각으로 판정했습니다. 호출이 상한 시간 안에 반환되지 않으면, 상한 시점의 생존을 기록한 뒤 이 시험이 만든 자식만 종료했습니다.

| 조건 | Restricted Token | AppContainer |
| --- | --- | --- |
| 시간 초과: 셸이 자식을 기다림, 제한 3초 | 3.0–4.3초에 `timed_out=True`로 반환 5/5. 자식은 반환 직후 종료 4/5, 5초 뒤 종료 5/5 | 9초까지 반환하지 않음 5/5. 9초에 자식 생존 5/5. 하네스가 자식을 종료한 뒤 `timed_out=True`로 반환 |
| 백그라운드: `start /b`로 자식을 띄우고 셸은 정상 종료, 제한 20초 | 10초까지 반환하지 않음 5/5. 10초에 자식 생존 5/5 | 같음 5/5 |
| 백그라운드, 제한 4초 | 12초까지 반환하지 않음, 시간 초과 처리 없음 5/5. 12초에 자식 생존 5/5. 자식 종료 후 반환 코드 −1(4/5) | 12초까지 반환하지 않음, 시간 초과 처리 없음 5/5. 12초에 자식 생존 5/5 |

앞선 `ping` 자식 측정에서도 Restricted Token의 시간 초과(자식 종료 5/5)와 백그라운드(반환하지 않음 5/5) 결과가 같았습니다. AppContainer의 `ping` 회차는 자식이 시작되지 않아 무효로 처리했습니다.

소스상 원인은 다음과 같습니다.

- 두 백엔드 모두 시간 제한은 **셸 프로세스**에만 적용됩니다(`WaitForSingleObject`). 출력 파이프는 끝(EOF)까지 읽습니다. 셸이 정상 종료하면 시간 초과가 발생하지 않고, 파이프를 물려받은 자식이 살아 있는 동안 출력 수집이 끝나지 않습니다.
- Restricted Token은 시간 초과일 때만 Job 전체를 종료하고, Job 핸들은 출력 수집이 끝난 뒤에 닫습니다(`sandbox/windows_unelevated_sandbox.py:1747-1767`). 출력 수집 결과를 10초 이상 기다리면 `TimeoutError`가 나고, `execute()`가 이를 `OSError`로 받아 종료 코드 −1을 반환합니다(`:2422-2426`).
- AppContainer는 시간 초과 시 셸만 종료하고, 출력 수집은 시간 제한 없이 기다립니다(`sandbox/windows_appcontainer_sandbox.py:770-783`).

**판정**

- Restricted Token의 시간 초과는 셸이 실행 중인 자식을 정리합니다(통과).
- AppContainer의 시간 초과는 자식을 정리하지 못하고 호출도 반환하지 않습니다(실패).
- 셸이 끝난 뒤 남은 백그라운드 자식에는 두 백엔드 모두 명령 시간 제한이 적용되지 않고, 호출이 자식이 끝날 때까지 반환되지 않습니다. 개발 서버나 워처를 백그라운드로 띄우는 작업은 도구 호출 하나를 계속 붙잡습니다.

## 5. 출처를 확인하지 못한 ACE

05에서 "3개"라고 적은 `%LOCALAPPDATA%\Temp`의 임의 SID 쓰기 허용 ACE는, 잘린 출력을 보고 센 숫자였습니다. 전체를 다시 조회하니 이름이 풀리지 않는 `S-1-5-21-…` SID가 5개 있었습니다. scratchpad 상위 경로에도 같은 형식의 SID 2개가 더 있습니다.

- 이 7개를 Codex 샌드박스의 SID 파일(`~/.codex/cap_sid`, `~/.codex/.sandbox`)과 일치 여부만 대조했습니다. 인증·비밀 파일과 세션 기록은 열지 않았습니다.
- 4개는 `~/.codex/cap_sid`에 있었습니다. `%LOCALAPPDATA%\Temp`의 2개와 scratchpad 상위 경로의 2개입니다.
- 나머지 3개는 출처를 찾지 못했습니다. 그중 2개의 마스크는 QwenPaw Restricted Token이 쓰는 `0x1301bf`가 아닌 `0x1301ff`입니다. QwenPaw는 작업 폴더 자체에만 ACE를 붙이므로 QwenPaw 잔여물일 가능성은 낮지만, 확정하지 않았습니다.
- 어떤 ACE도 변경하지 않았습니다.

## 6. 측정 중 오류와 처리

1. 네트워크 재측정 1회차(14:08)는 호스트 대조 명령의 비 UTF-8 출력 때문에 샌드박스 시작 전에 멈췄습니다. 디코딩을 고쳐 다시 실행했습니다.
2. 재실행 결과를 거른 `grep`이 비 UTF-8 줄 하나(루프백 예외 목록 출력)를 생략했습니다. 그 값은 PowerShell로 직접 다시 조회했습니다.
3. 자식 수명의 `ping` 회차에서 AppContainer 자식은 시작되지 않아 무효입니다. 이어진 회차는 `rem`이 같은 줄의 `&` 뒤까지 주석 처리해 루프가 실행되지 않았으므로 역시 무효입니다. 표식을 `set`으로 바꾸고 호스트 사전 확인을 거쳐 다시 측정했습니다.
4. 남은 프로세스를 처음 확인할 때 표식 문자열이 확인 명령 자신의 명령줄에 들어가, 확인 명령 자신이 검색되는 오탐이 있었습니다. 표식을 명령줄에 쓰지 않는 스크립트로 다시 확인했고, 남은 시험 자식은 0개였습니다.

## 7. 아직 미실측인 항목

- AppContainer 호스트의 비정상 종료: 실제 `Packages` 폴더와 HKCU 매핑을 일부러 남기게 됩니다.
- ISO-13, ISO-12의 쓰기·세션 간 접근, ISO-16~18의 승인 흐름 통합 시험: 실제 사용자 상태를 바꾸거나 호스트 권한 실행을 유발합니다.
- 위 항목은 전용 시험 계정이나 VM에서 측정해야 합니다.

> 정정: 위 분류는 과했습니다. 두 번째 계정이 꼭 필요한 것은 세션 간 접근뿐입니다. AppContainer 비정상 종료는 기존 AppContainer 시험과 같은 종류의 변경이라 시험 후 정리를 전제로 이 PC에서 측정할 수 있습니다. ISO-12 쓰기 권한, ISO-13 클립보드 열기, ISO-15~18 통합 시험은 실제 상태를 바꾸지 않는 방법으로 [2026-11-24-07](2026-11-24-07.md)에서 측정했습니다.
