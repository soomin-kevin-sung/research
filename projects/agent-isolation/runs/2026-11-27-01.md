## 1. 휴지통 (칸마다 5회)

**방법.**

- 회차마다 호스트가 휴지통 시험 폴더에 파일 3개를 만들고, 셸이 각각 다른 방법으로 지웠습니다.
  - 휴지통으로 보내는 `SHFileOperationW`: `FO_DELETE`, `FOF_ALLOWUNDO | FOF_SILENT | FOF_NOCONFIRMATION | FOF_NOCONFIRMMKDIR | FOF_NOERRORUI`
  - VisualBasic `DeleteFile(..., OnlyErrorDialogs, SendToRecycleBin)`
  - `Remove-Item`
- 이어서 호스트가 확인했습니다.
  - 자기 탐색기 휴지통(`Shell.Application` 네임스페이스 10)의 시험 항목
  - 계정 휴지통 폴더를 목록으로 읽을 수 있는지
- 셸은 `SHEmptyRecycleBinW("C:\\", 0x7)`로 자기 휴지통을 비웠습니다.
  - 셸이 사용자 휴지통 폴더 목록을 읽을 수 있으면 비우지 않도록 막아 두었습니다. 35회 모두 읽지 못해(오류 5) 비우기를 실행했습니다.
- 칸 순서가 결과에 영향을 줍니다. 계정 휴지통 폴더는 처음으로 휴지통에 들어간 삭제가 만듭니다. 그래서 A → B → D → C → D2 → A2 → B2 순서로 칸마다 5회씩 쟀습니다.

- **● Codex와 같은 로그온 플래그 0에서는 휴지통으로 보낸 삭제가 영구 삭제였습니다(A·B·A2·B2).**
  - `SHFileOperationW`는 0을 반환했고 `fAnyOperationsAborted`는 거짓이었습니다. 호출한 쪽에서는 휴지통에 들어갔는지 알 수 없습니다.
  - VisualBasic `DeleteFile`도 같았습니다. 오류 창 없이 끝났습니다.
  - 계정 휴지통 폴더가 이미 있어도(A2·B2) 들어가지 않았습니다. 플래그 0의 셸은 HKCU가 `.DEFAULT`이고 `USERPROFILE`이 `C:\Users\Default`입니다([2026-11-26-05](2026-11-26-05.md) 2장). 이것과 관련이 있어 보이지만 원인은 확인하지 않았습니다.
- **● 프로필을 로드하면 `C:\$Recycle.Bin\<계정 SID>`로 갔습니다.** 제한 없는 셸(C)은 첫 회차에 이 폴더를 만들었습니다.
- **Codex 제한 토큰 셸(D)은 폴더를 스스로 만들지 못했습니다.** 그래서 휴지통 대신 영구 삭제됐습니다.
  - 폴더가 생긴 뒤(D2)에는 5/5 들어갔습니다.
  - ○ `C:\$Recycle.Bin`의 DACL(읽기만 함)은 Administrators·SYSTEM 모든 권한, Users 읽기·실행·하위 폴더 만들기(`AD`)·특성 쓰기, capability SID 1개 읽기입니다. `WRITE_RESTRICTED` 토큰의 쓰기는 제한 SID 목록(capability SID·계정·로그온 SID·Everyone)으로도 허용돼야 합니다. 이 목록의 어느 SID에도 `AD`가 없으므로 폴더를 만들 수 없습니다. 폴더가 생긴 뒤에는 계정 SID가 제한 SID 목록에 있어 그 안에 쓸 수 있습니다. 계정 휴지통 폴더의 DACL은 기록하지 않았습니다.
  - D2의 「삭제 직후」 확인은 3/5였습니다. 5회 모두 `$I`·`$R` 파일은 바로 있었습니다. 다만 1·2회차는 그 순간 `$I` 파일에서 원래 이름을 읽지 못했습니다. 같은 회차의 다음 확인에서는 이름이 맞았습니다. 위 표는 다음 확인 기준입니다.
- **● `Remove-Item`은 모든 칸에서 영구 삭제였습니다.** 휴지통을 쓰지 않습니다.
- **● 사용자 쪽에서는 보이지도 않고 되살릴 수도 없었습니다.**
  - 휴지통에 들어간 항목(C·D2 20개)은 사용자 탐색기 휴지통에 하나도 보이지 않았습니다.
  - 사용자는 계정 휴지통 폴더 목록을 읽지 못했습니다(오류 5).
  - ○ 관리자 권한이면 그 폴더에서 꺼낼 수 있지만 재지 않았습니다.
- **● 비우기는 셸 자신의 휴지통만 비웠습니다.** 프로필을 로드한 칸(C·D2)만 성공했고, 플래그 0 칸은 `0x80070005`로 실패했습니다.
  - 사용자 휴지통은 측정 동안 비어 있었습니다(0개). 그래서 「사용자 휴지통을 비우지 않는다」는 항목 수로 확인한 것이 아닙니다. 근거는 두 가지입니다.
    - 셸이 사용자 휴지통 폴더를 읽지 못했습니다(35/35, 오류 5).
    - ○ `SHEmptyRecycleBinW`는 호출한 사용자의 휴지통을 비웁니다.

## 2. 클립보드 (칸마다 5회)

**방법.**

- 호스트가 임의의 표식 텍스트를 클립보드에 넣었습니다.
- 셸이 그것을 읽었습니다. Python은 `OpenClipboard`·`GetClipboardData`, PowerShell은 `Get-Clipboard`를 썼습니다.
- 셸이 표식 3개를 차례로 썼습니다. `Set-Clipboard`, `clip.exe`, Python(`EmptyClipboard`·`SetClipboardData`)입니다.
- 쓸 때마다 호스트가 클립보드를 읽어 확인했습니다.

| 창 스테이션·바탕 화면 | `WinSta0\Default` | `WinSta0\Default` | `WinSta0\Default` | `WinSta0\CodexSandboxDesktop-…` |

| Python 읽기 일치 | 5/5 | 5/5 | 0/5(`GetClipboardData` 오류 5) | 5/5 |

- **● 제한 토큰 셸도 사용자 클립보드를 읽고 씁니다.**
  - ○ 클립보드는 창 스테이션 단위입니다.
  - Codex offline 셸은 개인 바탕 화면에 있지만 창 스테이션은 사용자와 같은 `WinSta0`입니다. 그래서 결과가 같았습니다.
- **● Codex offline 셸이 속한 Job에는 UI 제한이 없었습니다(0).** 셸 안에서 자기 Job을 조회한 값입니다.
- **● Job UI 제한(J)은 읽기와 쓰기를 막았습니다.**
  - `OpenClipboard`는 성공했고, `CountClipboardFormats`도 형식 수(4)를 돌려줬습니다. 데이터를 꺼내는 `GetClipboardData`와 넣는 `SetClipboardData`만 거부됐습니다.

- 측정이 끝난 뒤 사용자 클립보드의 텍스트를 되돌렸습니다.

## 3. PC 안 통신 (칸마다 5회)

**방법.**

- 호스트가 HTTP 서버를 `127.0.0.1`, `::1`, PC의 LAN 주소에 띄웠습니다. 포트는 41000–49000 사이의 임의 값입니다.
  - 서버는 이 PC 주소에서 온 요청에만 응답하게 했습니다. 다른 주소의 요청은 0건이었습니다.

  - 같은 셸에서 외부 HTTPS(`10013`)와 445 포트 연결(루프백 포함, `10013`)은 막혔습니다. 445 포트는 SMB용 WFP 필터에 걸린 것으로 보입니다.

## 4. 공유 폴더(SMB)와 WebDAV (칸마다 5회)

**방법.**

- 셸이 다음 경로를 열었습니다.
  - `\\localhost\iso-ux-share\hello.txt` 읽기(Python)와 `dir`(cmd)
  - `\\<LAN 주소>\iso-ux-share\hello.txt` 읽기
  - `\\localhost\C$` 목록
  - `\\192.0.2.1\iso` 목록
  - `net use \\example.com@SSL\DavWWWRoot`와 그 경로의 목록
- 셸 자신의 TCP 연결로 `192.0.2.1:445`에도 접속했습니다(5초 제한).
- 호스트는 0.1초 간격으로 TCP 연결 표(`GetExtendedTcpTable`)를 읽어, 해당 연결의 소유 프로세스를 기록했습니다.
- 호스트 칸은 `192.0.2.1`과 WebDAV를 재지 않았습니다.

| 항목 | Codex offline | A: 플래그 0, 제한 | B: 플래그 0, 제한 없음 | 호스트 |
| --- | --- | --- | --- | --- |
| `\\localhost` 공유 파일 읽기, `dir` | 0/5(오류 13, `Access is denied.`) | 0/5(같음) | 5/5, 5/5 | 5/5, 5/5 |
| `\\<LAN 주소>` 공유 파일 읽기 | 0/5(오류 13) | 0/5(오류 13) | 5/5 | 5/5 |
| `\\localhost\C$` 목록 | 0/5(오류 5) | 0/5(오류 5) | 5/5(항목 수만 셈) | 5/5 |
| 로컬 공유 SMB 연결(연결 표) | 없음 | 없음 | System 소유, `::1:445`·LAN 주소`:445` 5/5 | 같음 |
| `\\192.0.2.1\iso` 목록 | 0/5(오류 5, 즉시) | 0/5(오류 5, 즉시) | 0/5(오류 64·53, 21초 뒤) | — |
| `192.0.2.1:445` SMB 연결(연결 표) | 없음 | 없음 | **System 소유 `SYN_SENT` 5/5** | — |
| 셸 자신의 TCP `192.0.2.1:445` | 0/5(`10013`, 즉시) | 0/5(5초 초과, `python.exe` 소유 `SYN_SENT` 5/5) | 0/5(같음) | — |
| `net use \\example.com@SSL\DavWWWRoot` | 0/5(System error 67) | 0/5(같음) | 0/5(같음) | — |
| `\\example.com@SSL\DavWWWRoot` 목록 | 0/5(오류 5) | 0/5(오류 5) | 0/5(오류 53) | — |
| `net.exe` 자신의 `example.com:443` 연결 | 없음 | `SYN_SENT` 1/5 | `ESTABLISHED` 4/5 | — |

- **● 제한 토큰 셸(A, Codex offline)은 SMB 연결이 생기기 전에 거부됐습니다.**
  - 모든 UNC 경로가 바로(0.0초) 실패했고, 연결 표에도 SMB 연결이 생기지 않았습니다.
  - 그래서 「셸의 SMB가 방화벽과 관계없이 나가는가」는 이 구조의 제한 토큰 셸에서는 일어나지 않았습니다.
  - Codex offline에서는 셸 자신의 445 포트 연결도 `10013`으로 막혔습니다.
- **● 제한 없는 별도 계정(B)의 SMB 연결 소유자는 System이었습니다.**
  - 로컬 공유를 읽을 때 연결은 System(PID 4) 소유였습니다.
  - `\\192.0.2.1`로 가는 445 연결도 System 소유 `SYN_SENT`였습니다. 셸 자신의 연결은 `python.exe` 소유로 따로 보였습니다.
  - ○ Codex의 방화벽 규칙과 WFP 필터는 offline 계정 SID를 조건으로 합니다. System 소유 연결에는 이 조건이 맞지 않을 것입니다. 다만 Codex offline 셸은 위처럼 UNC 단계에서 거부되므로 이 경우를 재지는 못했습니다.
- **? 그 패킷이 PC 밖으로 나갔는지는 확인하지 못했습니다.**
  - `pktmon` 캡처(네트워크 어댑터, `192.0.2.1` 필터)에는 시작 헤더 3개만 있고 패킷은 0개였습니다.
  - 연결 표에 `SYN_SENT`로 보인 셸 자신의 연결(A·B 10회)도 캡처되지 않았습니다. 따라서 이 캡처로는 나갔는지를 판정할 수 없습니다.
  - Wi-Fi 어댑터에서의 캡처 조건은 확인하지 않았습니다.
- **? 어떤 자격 증명으로 SMB 인증을 했는지는 확인하지 못했습니다.** `Get-SmbConnection`이 호스트를 포함한 모든 칸에서 액세스 거부였습니다.
- **● B와 호스트는 `\\localhost\C$` 목록을 읽었습니다.**
  - `C$`의 공유 권한(관리자 단계에서 읽기만 함)은 Administrators·Backup Operators·INTERACTIVE 모든 권한입니다.
  - ○ 목록은 `C:\`의 파일 DACL을 따르므로, 로컬에서 읽을 수 있는 것 이상을 주지는 않습니다. 이번에는 최상위 항목 수만 셌습니다.
- **● WebDAV는 WebClient 서비스를 거치는 경로까지 가지 못했습니다.**
  - WebClient는 측정 전후 내내 중지 상태였습니다. `net use`와 폴더 열기로는 시작되지 않았습니다.
  - `net use`는 모든 칸에서 System error 67(네트워크 이름을 찾을 수 없음)이었습니다.
  - 대신 `net.exe` 자신이 `example.com:443`에 TCP 연결을 열었습니다(B `ESTABLISHED` 4/5, A `SYN_SENT` 1/5). Codex offline에서는 이 연결이 보이지 않았습니다. 셸 프로세스 자신의 연결이라 offline 방화벽이 막은 것으로 보입니다. 무엇을 보냈는지는 기록하지 않았습니다.
  - ? WebClient가 실행 중일 때는 재지 않았습니다.
  - ○ WebClient는 서비스로 실행되므로, 그 연결의 소유자는 셸이 아니라 서비스가 될 것입니다.

## 5. BITS (칸마다 5회)

**방법.**

- 셸이 `https://example.com/`을 내려받았습니다.
  - `Start-BitsTransfer -Asynchronous`: 45초까지 상태 확인
  - `bitsadmin /transfer … /download /priority FOREGROUND`
- 셸이 자기 BITS 작업을 확인하고 지웠습니다.

| 항목 | Codex offline | A: 플래그 0, 제한 | B: 플래그 0, 제한 없음 | 호스트 |
| --- | --- | --- | --- | --- |
| `Start-BitsTransfer` | 0/5(`NullReferenceException`) | 0/5(같음) | 0/5(`0x800704DD`) | 5/5(`Transferred`) |
| `bitsadmin /transfer` | 0/5(`Unable to create job - 0x80070005`) | 0/5(같음) | 0/5(`Unable to add file - 0x800704dd`) | 5/5 |
| 내려받은 파일 | 0/5 | 0/5 | 0/5 | 5/5 |
| 자기 작업 조회·삭제 | 조회 거부(`0x80070005`) | 같음 | 조회는 됨, 삭제 실패(`0x800704DD`) | 됨(남은 작업 0) |
| BITS 서비스의 `example.com:443` 연결 | 없음 | 없음 | 없음 | `svchost`(BITS) 소유 |

- **● 제한 토큰 셸(A, Codex offline)은 BITS 작업을 만들지 못했습니다.** `bitsadmin`은 작업 생성 단계에서 `0x80070005`로 실패했습니다. `Start-BitsTransfer`는 `NullReferenceException`으로 끝났고, 자기 작업 조회도 `0x80070005`로 거부됐습니다.
- **● 제한 없는 별도 계정(B)은 작업은 만들었지만 파일을 추가하지 못했습니다.**
  - 오류는 `0x800704DD`(`ERROR_NOT_LOGGED_ON`), 「사용자가 네트워크에 로그온하지 않았다」였습니다. BITS가 `CreateProcessWithLogonW` 로그온을 작업 소유자의 로그온으로 인정하지 않은 것으로 보입니다. 원인은 확인하지 않았습니다.
  - 파일이 없는 작업이 남았고, 셸은 같은 오류로 지우지 못했습니다.
    - 회차마다 2개씩 늘어 마지막 회차 뒤 22개였습니다. 점검 실행과 첫 전체 실행의 작업도 포함된 수입니다.
    - 관리자 정리 단계에서 지웠습니다(6장).
  - 이 칸에서 BITS 서비스의 외부 연결은 생기지 않았습니다.
- **● 호스트의 BITS 전송은 BITS 서비스(`svchost`)가 연결을 맺었습니다.**
  - ○ 따라서 BITS는 [2026-11-26-04](2026-11-26-04.md)의 DNS 클라이언트 서비스(Dnscache)처럼 서비스가 대신 연결하는 경로입니다. 계정 단위 방화벽 규칙은 이 연결에 맞지 않을 것입니다.
  - ● 다만 이 구조에서는 작업 생성(제한 토큰)이나 파일 추가(제한 없는 별도 계정)에서 먼저 막혔습니다.
  - ? 프로필을 로드한 로그온에서 BITS는 재지 않았습니다.
- 연결 표 해석에서 두 가지 기록은 칸의 결과에서 뺐습니다.
  - 호스트 1회차의 BITS 연결이 같은 로컬 포트로 다음 칸들의 연결 표에 계속 보였습니다. 칸 시작 때(0.0초) 이미 있던 연결은 앞 회차의 것으로 보고 뺐습니다. 호스트의 로컬 공유 SMB 연결도 같습니다.
  - `TIME_WAIT` 상태 연결은 PID가 0이라, 소유자 표시가 같은 PID 0인 중지된 WebClient로 잘못 붙었습니다. 그래서 `TIME_WAIT`는 판정에서 뺐습니다.

- **측정 계정의 BITS 작업 정리.**
  - 관리자 정리 단계의 목록 조회 줄에 스크립트 오류가 있었습니다. `OwnerAccount`(NTAccount 형식)에 문자열 함수 `Split`을 바로 불렀습니다.
  - 그래서 정리 직전 작업 수는 기록되지 않았습니다. 대신 작업마다 같은 오류가 stderr에 남았습니다.
  - 삭제 명령(`Get-BitsTransfer -AllUsers | Where-Object DisplayName -like 'iso-ux-*' | Remove-BitsTransfer`)은 오류 없이 끝났습니다.
  - 삭제 뒤 같은 조회에서는 오류가 하나도 나오지 않았습니다. 해당 작업이 남지 않았다는 뜻입니다.
  - 측정 계정도 그 뒤에 지웠습니다. 스크립트는 고쳤습니다.
- `pktmon` 텍스트 변환 결과는 UTF-16이었습니다. 정리 단계는 이를 UTF-8로 읽어 `192.0.2.1` 줄 수를 셌습니다. 다시 UTF-16으로 읽어도 헤더 3줄뿐이어서 결과(0개)는 같습니다. 스크립트는 고쳤습니다.
- **WFP 필터 수가 달라진 것.** 측정 때와 정리 때 PC가 연결된 Wi-Fi 네트워크가 달랐습니다.
  - 방화벽 규칙 수와 Codex 규칙·필터 이름은 같았습니다. Windows 방화벽이 규칙에서 만든 WFP 필터 수만 바뀌었습니다.
  - Codex의 WFP 필터(`codex_wfp_*`) 12개는 같았습니다.
  - 측정은 00:53 상태(규칙마다 2개)에서 했습니다. 이 측정은 규칙을 추가하거나 바꾸지 않았습니다.
  - 네트워크 프로필에 따라 필터 수가 바뀌는 방식은 확인하지 않았습니다.

## 7. 확인하지 못한 것

- **패킷 수준 확인.** `pktmon`이 이 PC의 Wi-Fi 어댑터에서 아무 패킷도 기록하지 않았습니다. 그래서 System 소유 SMB 연결과 `net.exe` 연결이 실제로 PC 밖으로 나갔는지는 판정하지 못했습니다(?). 연결 표의 상태와 소유자만 근거입니다.
- **SMB 인증 주체.** `Get-SmbConnection`이 관리자 권한 없이 거부돼, 어떤 계정의 자격 증명으로 연결했는지 보지 못했습니다.
- **셸 리스너의 LAN 주소.** 방화벽 알림 창 때문에 재지 않았습니다.
- **WebClient를 거치는 WebDAV.** 서비스가 시작되지 않아 재지 못했습니다. 서비스를 직접 시작하는 시험은 하지 않았습니다.
- **프로필 로드 로그온의 BITS.** 플래그 0 칸에서만 쟀습니다.
- **휴지통의 실제 Codex 셸.** Codex offline 칸은 휴지통 묶음에 넣지 않았습니다.
  - 요청 세션이 전한 Codex 0.172.0 `runner_client.rs` 내용에 따르면, Codex는 플래그 0으로 로그온합니다. A가 이 조건과 같습니다.
  - 그 소스는 이 세션에서 읽지 않았습니다.
- **원인.** 다음 세 가지의 원인은 확인하지 않았습니다.
  - 플래그 0에서 휴지통 폴더가 있어도 영구 삭제되는 이유
  - Codex의 루프백 차단 규칙이 루프백 HTTP를 막지 않은 이유
  - BITS의 `0x800704DD`
- **범위.** PC 한 대(도메인 가입)에서만 쟀습니다. 사용자 휴지통은 측정 동안 비어 있었습니다.
