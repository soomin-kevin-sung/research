## 실행 조건

[측정 계획](../plan-token-backends.md)의 R3를 [2026-11-25-01](2026-11-25-01.md)과 [2026-11-25-02](2026-11-25-02.md)에서 빠뜨려, Codex `elevated`만 따로 측정했습니다.

- **측정 대상 구성.** Codex `elevated`(오프라인 계정 `CodexSandboxOffline`), `iso` 프로필, 실제 `~/.codex`.
- **준비.** 최종 정리 뒤라 [R3 준비](probe-token-backends-r3-prep.py)로 시험 폴더를 최소 구성으로 다시 만들었습니다.
  - 만든 것: 독립 Python 런타임, 샌드박스 안 측정 프로그램, `codex-elevated\ws-A`·`ws-B`·`temp`.
  - 경로가 이전 측정과 같아서 Codex는 `cap_sid`의 기존 항목을 다시 썼습니다. 측정 전후 `cap_sid`는 같았습니다.
- **계정 변경 감시.** [Codex `elevated` 보호 실행](probe-token-backends-elevated-guard.py)으로 실행했습니다. 두 샌드박스 계정의 비밀번호 변경 시각과 계정 기록 파일 해시는 바뀌지 않았습니다.
- **측정 방법(5회).** [측정](probe-token-backends-campaign.py)의 `r3` 그룹입니다.
  1. `ws-A` 명령이 샌드박스 계정 프로필 폴더(`C:\Users\CodexSandboxOffline`)에 합성 파일을 만듭니다.
  2. `ws-B` 명령이 그 파일이 있는지 보고, 읽고, 지웁니다.
  3. 다시 `ws-A` 명령이 파일이 없어졌는지 확인합니다.
  4. 각 명령은 HKCU `Software`를 쓰기 권한(`KEY_SET_VALUE | KEY_CREATE_SUB_KEY`)과 읽기 권한으로 열고 바로 닫습니다. 값은 쓰지 않습니다.
- **만들지 않은 것.** PowerShell 프로필이나 시작 스크립트처럼 실제 Codex 사용에 영향을 주는 파일은 만들지 않았습니다.
- **원본 데이터.** `local/2026-11-25/`에 있으며 저장소에 올리지 않습니다.

- **작업 폴더 사이 공유.** Codex `elevated`는 모든 작업 폴더가 같은 고정 계정을 씁니다. 그래서 한 작업 폴더의 명령이 샌드박스 계정 프로필에 남긴 파일을 다른 작업 폴더의 명령이 읽고 지울 수 있었습니다.
  - Codex는 이 프로필을 명령마다 비우지 않습니다. 따라서 한 작업이 남긴 설정 파일이 다른 작업의 명령에 영향을 줄 수 있습니다.
  - 작업 폴더별 capability SID는 작업 폴더 쓰기만 나누며, 계정 프로필은 나누지 않습니다.
- **레지스트리.** HKCU는 `.DEFAULT`이고 쓰기가 거부되므로 HKCU를 통해서는 상태를 남기지 못합니다.
- **사용자가 확인하기 어려움.** 일반 권한의 사용자는 샌드박스 계정 프로필 안을 볼 수 없었습니다. 샌드박스가 그 안에 무엇을 남겼는지 확인하려면 관리자 권한이 필요합니다.
- **QwenPaw 관리자.** R3를 직접 측정하지 않았습니다. 다만 [2026-11-25-02](2026-11-25-02.md)에서 작업 폴더마다 계정·프로필·`TEMP`가 달랐고(B8b), 다른 작업 폴더의 샌드박스 프로세스도 열지 못했습니다(P6). 같은 작업 폴더의 실행끼리는 같은 계정을 다시 쓰므로 그 안에서는 상태가 이어집니다.
