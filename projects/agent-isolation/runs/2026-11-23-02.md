## Restricted Token 후속 진단

새 합성 폴더에서 같은 호스트 셸과 `WindowsUnelevatedSandbox`로 각 명령을 한 번씩 실행했습니다. 두 실행의 `cd`는 동일한 작업 폴더를 출력했고, 두 환경에서 `NoDefaultCurrentDirectoryInExePath`는 설정되지 않았습니다.

| 명령 | 호스트 | Restricted Token |
| --- | --- | --- |
| `dir /b` | `run.cmd`와 `starter.txt` 표시 | 코드 1, `File Not Found` |
| `type run.cmd` | 배치 파일 내용 표시 | 코드 1, `Access is denied.` |
| `type starter.txt` | `fixture-v1` 출력 | 코드 1, `Access is denied.` |
| `echo probe>probe.txt` | 코드 0 | 코드 1, `Access is denied.` |
| `run.cmd` | `WORKLOAD_OK` | 코드 1, 명령 이름을 찾지 못함 |
| `.\run.cmd` | `WORKLOAD_OK` | 코드 1, `Access is denied.` |

배치 본문을 실행하지 않아도 목록 조회, 직접 읽기, 파일 생성에 실패했습니다. 결과는 명령 이름 검색 실패가 작업 폴더 내 파일 접근 실패와 함께 발생했음을 보여 줍니다. 실제 토큰의 유효 권한과 개별 파일 ACL에 대한 접근 검사까지는 수행하지 않아 어떤 권한 검사가 거부를 일으켰는지는 미확정입니다. 이번 진단용 폴더는 자식 Python 프로세스가 종료된 뒤 상위 측정 프로세스가 정리했습니다.

추가 재현에서 Windows `OpenProcessToken`과 `IsTokenRestricted`로 QwenPaw가 실제로 시작한 `cmd.exe`의 토큰을 조회했습니다. 호스트 Python은 `False`, 샌드박스 `cmd.exe`는 `True`였고 사용자 SID는 같았습니다. 이 실행에서도 `type starter.txt`는 코드 1과 `Access is denied.`를 반환했습니다. 이 확인은 제한 토큰 적용의 증거입니다. 토큰의 구체적인 플래그와 읽기 거부를 일으킨 접근 검사는 미확인입니다.

### Windows API 단독 재현

[재현 코드](probe-restricted-token.py)는 QwenPaw를 호출하지 않고 현재 호스트 토큰에서 `CreateRestrictedToken`으로 토큰을 만든 뒤, 현재 스레드에 적용하고 `CreateFile`을 호출합니다. 시스템 임시 경로의 합성 파일에 대해 세 가지 읽기 열기 마스크(`GENERIC_READ`, `FILE_READ_DATA`, `FILE_READ_DATA | SYNCHRONIZE`)와 새 파일 생성을 시험했습니다.

| 구성 | 세 가지 읽기 열기 | 새 파일 생성 |
| --- | --- | --- |
| 호스트 | 모두 성공 | 성공 |
| `DISABLE_MAX_PRIVILEGE`, 제한 SID 없음 | 모두 성공 | 성공 |
| 플래그 없음, 제한 SID 1개 | 모두 WinError 5 | WinError 5 |
| `WRITE_RESTRICTED`, 동일한 제한 SID | 모두 WinError 5 | WinError 5 |
| 두 플래그, 동일한 제한 SID | 모두 WinError 5 | WinError 5 |

이 조건에서 `DISABLE_MAX_PRIVILEGE`만으로는 읽기 거부를 재현하지 못했고, 제한 SID를 지정한 구성에서는 최소 읽기 마스크도 거부됐습니다. 이 재현은 시험 ACL에 권한이 없는 SID 하나와 스레드 가장을 사용합니다. QwenPaw의 SID 구성 및 자식 프로세스 토큰과 차이가 있어 제품 쪽 거부 원인을 특정할 수 없습니다.

후속 실행에서는 pywin32의 토큰 생성 래퍼 대신 `advapi32!CreateRestrictedToken`을 직접 호출했습니다. 기본 임시 경로와 `%LOCALAPPDATA%\Temp`에서 모두 같은 결과였습니다. 자식 토큰과 호스트 토큰의 일반 그룹 SID 및 속성 목록은 모든 구성에서 같았습니다. 별도 합성 파일의 DACL에 제한 SID의 `FILE_GENERIC_READ` 허용 ACE를 명시적으로 추가해도, 제한 SID가 들어간 세 구성의 실제 파일 열기는 모두 WinError 5였습니다. 이 실험에서 읽기 거부와 함께 바뀐 조건은 제한 SID 목록의 유무입니다. 명시 ACE를 추가한 검사에서도 경로 전체를 여는 `CreateFile`을 사용했으므로, 파일 객체와 상위 경로의 접근 검사를 이 비교만으로 구분할 수 없습니다.

### QwenPaw 자식 프로세스에서 플래그 비교

같은 합성 작업 폴더에서 QwenPaw의 비관리자 백엔드를 사용했습니다. 시험 Python 프로세스에서만 `_WC.WRITE_RESTRICTED`를 `0x08`, `0x00`, `0x08`, `0x00` 순으로 바꿨습니다. `DISABLE_MAX_PRIVILEGE`, 제한 SID를 구성하는 코드, 실행 계정과 셸 경로는 같았습니다. 회차별로 샌드박스를 정리해 토큰을 새로 만들었습니다. 호스트 셸의 `type starter.txt`는 코드 0과 `fixture-v1`을 반환했습니다.

| 토큰 플래그 | 파일 읽기 | 새 파일 쓰기 | 작업 폴더와 입력 파일 ACL |
| --- | --- | --- | --- |
| `WRITE_RESTRICTED` 포함 (`0x09`) | 0/2 성공, 코드 1 및 `Access is denied.` | 0/2 성공, 같은 오류 | 두 ACL 모두 제품 capability SID의 ACE 존재 |
| `WRITE_RESTRICTED` 제외 (`0x01`) | 0/2 성공, 코드 1 및 출력 없음 | 0/2 성공, 코드 1 및 출력 없음 | 두 ACL 모두 제품 capability SID의 ACE 존재 |

플래그를 빼도 읽기·쓰기는 성공하지 않았고 오류 출력은 달라졌습니다. 플래그를 뺀 조건에서 빈 출력의 발생 단계는 미확인입니다. ACL 조회는 ACE의 존재만 확인했으므로 실제 토큰과 파일에 대한 유효 권한은 미확인입니다. 제품 로그상 모든 회차에서 폴더 ACE를 제거했고, 시험 프로세스와 임시 폴더 정리를 마쳤습니다.

### 실제 자식 토큰의 읽기 권한 검사

기본 비관리자 Restricted Token 구성에서 새 합성 `starter.txt`의 보안 설명자를 `GetNamedSecurityInfoW`로 조회했습니다. 호스트 Python과 QwenPaw가 실제로 시작한 `cmd.exe`의 토큰을 각각 가장 토큰으로 복제했습니다. 두 사용자 SID는 같았습니다. 같은 보안 설명자로 `AccessCheck`를 실행하고, 각 복제 토큰을 현재 스레드에 적용해 같은 파일을 `CreateFile`로 열었습니다.

| 토큰 | 요청 권한 | AccessCheck | CreateFile |
| --- | --- | --- | --- |
| 호스트 | `FILE_READ_DATA` | 허용 | 성공 |
| 호스트 | `FILE_GENERIC_READ` | 허용 | 성공 |
| QwenPaw 자식 | `FILE_READ_DATA` | 거부 | WinError 5 |
| QwenPaw 자식 | `FILE_GENERIC_READ` | 거부 | WinError 5 |

원래 자식 프로세스의 `type starter.txt`도 종료 코드 1과 `Access is denied.`를 반환했습니다. 따라서 해당 호스트와 시험 경로에서 자식 토큰의 파일 접근 검사만으로 읽기 거부가 재현됩니다. 어느 SID 또는 ACE가 결과를 결정했는지와 다른 Windows 계정에서의 결과는 미확인입니다. 제품 ACL 정리와 시험 임시 폴더 삭제를 완료했습니다.

별도 재현에서 `allow_read_all=True`로 시작된 실제 `cmd.exe`의 토큰을 Windows `GetTokenInformation(TokenIsAppContainer)`로 조회했습니다. 반환값은 `0`이었고, 같은 실행에서 `type starter.txt`는 다시 `Access is denied.`를 반환했습니다.

### Windows API 단독 재현의 파일 권한 검사

[재현 코드](probe-restricted-token.py)에 파일의 보안 설명자를 직접 검사하는 `AccessCheck`를 추가했습니다. 기본 임시 경로와 사용자 임시 경로에서 각각 실행했고 결과가 같았습니다. 상속 ACL 파일과 제한 SID에 `FILE_GENERIC_READ` ACE를 직접 추가한 파일을 모두 검사했습니다. 각 파일의 `FILE_READ_DATA`와 `FILE_GENERIC_READ` 검사 결과도 같았습니다.

| 토큰 구성 | 상속 ACL 파일의 AccessCheck | 명시적 읽기 ACE 파일의 AccessCheck | 명시적 읽기 ACE 파일의 CreateFile |
| --- | --- | --- | --- |
| 호스트 | 허용 | 허용 | 성공 |
| `DISABLE_MAX_PRIVILEGE`만 | 허용 | 허용 | 성공 |
| 제한 SID만 | 거부 | 거부 | WinError 5 |
| 제한 SID와 `WRITE_RESTRICTED` | 거부 | 거부 | WinError 5 |
| 제한 SID와 두 플래그 | 거부 | 거부 | WinError 5 |

파일 자체의 보안 설명자 검사에서 거부가 재현되므로, 상위 폴더를 실제로 통과하는 과정 없이도 실패합니다. 명시적 ACE가 있는 경우에도 거부를 일으키는 구체적인 토큰 상태와 권한 검사 조건은 미확인입니다.

`--inspect-ancestors`로 공용 `CreatorTemp`와 사용자 임시 경로 두 곳에서 루트부터 시험 폴더까지 `FILE_LIST_DIRECTORY`와 `FILE_TRAVERSE`를 별도로 요청했습니다. 호스트와 두 플래그를 켠 제한 토큰 모두 기존 상위 폴더 전체에서 두 요청에 성공했고 `SeChangeNotifyPrivilege`도 활성 상태였습니다. 제한 토큰은 새로 만든 시험 폴더 자체에서만 두 요청이 WinError 5였고, 그 안의 파일은 `AccessCheck`와 `CreateFile`에서 계속 거부됐습니다. 이 비교는 QwenPaw 없이 만든 제한 SID 하나의 토큰을 사용했습니다.

### 독립 검증과 QwenPaw 대조 실행

같은 호스트의 독립 검증에서 Python 3.12.10의 `tempfile` 시험 폴더 DACL은 SYSTEM, Administrators 및 OWNER RIGHTS(`S-1-3-4`)만 허용했고 파일이 이를 상속했습니다. 일반 사용자의 SID를 직접 허용하는 ACE가 없었습니다. 시험 파일에 제한 SID 읽기 ACE만 추가해도 기존 소유자 권한 쪽 조건은 같았습니다. 생성한 토큰과 복제 토큰에서 제한 SID 및 `WRITE_RESTRICTED` 상태를 확인했습니다. 일반 ACL 폴더를 사용한 대조 실행에서 `WRITE_RESTRICTED`를 켜면 읽기는 허용되고 쓰기는 거부됐습니다. C# P/Invoke의 별도 합성 파일 행렬에서도 소유자 권한 ACE만 있는 파일은 읽기·쓰기가 거부됐고, 일반 사용자 읽기·쓰기 ACE가 있는 파일은 `WRITE_RESTRICTED`로 읽기만 성공했습니다.

QwenPaw `2.3.0.post1`의 비관리자 백엔드로 동일한 상위 폴더 아래 두 작업 폴더를 비교했습니다. 상위 폴더도 `mkdir`로 만들어 기본 ACL을 상속하도록 했습니다.

| 시험 폴더 생성 | 입력 파일에 OWNER RIGHTS ACE | `type starter.txt` | 새 `result.txt` 쓰기 |
| --- | --- | --- | --- |
| `tempfile.mkdtemp()` | 있음 | 코드 1 | 코드 1, 파일 없음 |
| `Path.mkdir()` | 없음 | 코드 0, `fixture-v1` | 코드 0, 파일 생성 |

처음에는 공통 상위 폴더도 `tempfile.mkdtemp()`로 만들어 두 하위 폴더 모두 OWNER RIGHTS ACE를 갖고 실패했습니다. 위 표는 그 상속 조건을 바로잡은 대조 실행입니다. 이번 대조는 개별 읽기·쓰기 명령 각 1회이며, 전체 `run.cmd`의 반복 측정은 포함하지 않습니다. 시험 폴더는 정리했습니다.

### 전체 워크로드 재측정

QwenPaw `2.3.0.post1` 비관리자 `WindowsUnelevatedSandbox`, `allow_read_all=True`에서 매 회차 일반 ACL을 상속하는 새 작업 폴더에 원본 워크로드를 복사하고 `run.cmd`를 실행했습니다. 호출 제한은 30초입니다. 5회 모두 종료 코드 0, 표준 출력 `WORKLOAD_OK`, 표준 오류 없음, 결과 파일 첫 줄 `verified-v1`을 확인했습니다. **ISO-01 통과 (5/5)**. 호출 시간은 45.915, 42.029, 40.626, 41.026, 41.611 ms였고 중앙값은 41.611 ms입니다. 백엔드 초기화와 결과 수집을 포함합니다. 시험 폴더는 프로세스 종료 뒤 정리했습니다.
