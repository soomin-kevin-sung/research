# 코덱스 사용 방식 평가와 실험 계획

자주 하는 작업을 같은 조건에서 반복해 어떤 모델·프롬프트·스킬·플러그인 조합이 원하는 결과를 만드는지 확인합니다. 실제 결과의 품질과 함께, 결과를 쓰기까지 내가 추가로 지시하거나 직접 고친 양을 기록합니다.

## 평가표

평가 축은 **코딩, 글쓰기, 디자인, 업무 흐름, 판단** 다섯 가지입니다. **전달 방식은 글쓰기 아래의 평가 기준**입니다. 과제마다 필요한 항목을 실행 전에 고릅니다. 코딩이나 디자인 작업에서도 결과 보고가 있다면 전달 방식을 채점합니다.

| 평가 축 | 평가 항목 | 2점 기준 |
| --- | --- | --- |
| 코딩 | 동작과 유지보수 | 요구한 동작을 만족하고 관련 기존 기능을 보존합니다. 변경 범위와 코드 구조를 이해하고 수정하기 쉽습니다. |
| 글쓰기 | 내용 | 독자와 목적에 맞고, 사실과 근거가 정확하며 필요한 내용을 담습니다. |
| 글쓰기 | 전달 방식 · 말투 | 직접적이고 자연스러우며 상황과 독자에 맞습니다. |
| 글쓰기 | 전달 방식 · 간결함 | 판단에 필요한 근거를 남기면서 반복과 불필요한 설명을 줄입니다. |
| 글쓰기 | 전달 방식 · 정보 순서 | 핵심 결론을 먼저 읽을 수 있고, 결정할 사항이나 남은 일이 있으면 쉽게 찾을 수 있습니다. |
| 글쓰기 | 전달 방식 · 예시 | 설명이 추상적이면 핵심을 이해하는 데 도움이 되는 구체적인 사례를 듭니다. |
| 디자인 | 시각적 완성도와 사용성 | 첫 화면에서 중요한 정보와 행동이 드러나고, 시각 요소가 일관되며, 필요한 화면 크기에서 작업을 마칠 수 있습니다. |
| 업무 흐름 | 진행과 검증 | 필요한 맥락을 찾아 작업을 마치고, 발생한 오류를 처리하며, 필요한 검증을 실제로 수행합니다. |
| 판단 | 범위와 의사결정 | 작업 범위를 적절히 잡고 중요한 가정을 확인합니다. 스스로 결정할 일과 사용자에게 물을 일을 적절히 판단합니다. |

예를 들어 중복 저장 버그를 수정했다면, **한 건만 저장되는지**는 코딩, **연속 클릭을 테스트했는지**는 업무 흐름, **“연속 클릭해도 한 건만 저장된다”는 결론을 바로 찾을 수 있는지**는 글쓰기의 전달 방식에서 평가합니다.

### 채점과 기록

- 각 항목에 **0점 미충족, 1점 부분 충족, 2점 충족**을 매기고, 응답 발췌·테스트 결과·화면 등 근거 한 줄을 남깁니다. 예시가 필요 없는 답변은 예시 항목을 `해당 없음`으로 표시합니다. 확인하지 못한 항목은 `미실측`과 이유를 기록합니다.
- 과제별로 미리 정한 **필수 완료 조건**은 별도로 통과 여부를 기록합니다. 예를 들어 “저장 버튼을 연속으로 눌러도 한 건만 저장되고 테스트로 확인했다”는 코딩 과제의 통과 조건이 될 수 있습니다.
- **사용자 부담**은 첫 요청 이후 추가 지시 횟수와 직접 고친 시간(분)으로 기록합니다. 필요한 설명을 다시 요청한 횟수는 추가 지시에 포함합니다. 첫 요청부터 최종 응답까지의 경과 시간도 기록합니다.
- [실행 양식](../../templates/run.md)의 관찰 결과에 `글쓰기 / 전달 방식 / 정보 순서`처럼 항목명을 적습니다. 비교할 때는 기준 설정과 변경 설정의 항목별 차이, 완료 여부, 사용자 부담을 나란히 봅니다.

## 실험 설계

| 바꾸는 요소 | 비교 방법 |
| --- | --- |
| 프롬프트 | 현재 지시와 비교해 추가하거나 바꾼 문구를 그대로 기록합니다. |
| 스킬 | 스킬 하나의 적용 여부를 바꿉니다. 어떤 과제에서 실제로 사용됐고 결과에 어떤 차이가 있었는지 기록합니다. |
| 플러그인 | 연결하는 플러그인 하나를 바꿉니다. 실제로 사용됐는지와 각 설정으로 어디까지 완료할 수 있었는지 기록합니다. |
| 모델 | 설정 변경의 효과를 확인할 때, 모델마다 현재 구성과 변경 구성을 한 쌍으로 실행합니다. 입력과 평가 기준을 공유해 모델별로 어떤 항목이 달라졌는지 비교합니다. |

1. 실제로 반복하는 작업을 고르고 입력, 시작 상태, 필수 완료 조건, 채점 항목을 고정합니다. 파일 작업은 같은 커밋과 입력 파일에서 시작합니다.
2. 같은 모델에서 현재 구성과 한 요소를 바꾼 구성을 비교합니다. 새 대화에서 각각 실행하고 모델 이름, 확인 가능한 버전, 실행 환경, 설정 차이를 기록합니다.
3. 개선이 보이면 새 과제로 재확인하고 다른 모델에서도 반복합니다. 결과 편차가 크거나 한 번의 실행에서만 개선됐다면 같은 조건을 다시 실행합니다.

필수 완료 조건을 충족하고 관심 항목이 개선되거나 사용자 부담이 줄면 채택 후보로 둡니다. 다른 항목의 하락이나 경과 시간 증가가 있으면 함께 기록합니다. 개선이 여러 과제에서 반복되면 해당 모델의 기본 설정 후보로, 특정 과제에서 반복되면 작업별 설정 후보로 둡니다.

## 첫 실험

**같은 모델에서 실제 과제 두 개를 두 번씩 실행**합니다. 과제마다 현재 설정으로 한 번, 아래 문구를 추가해 한 번 실행합니다.

| 과제 | 실행 전에 정할 완료 조건 | 채점 항목 |
| --- | --- | --- |
| 설명이 필요한 질문 | 핵심 질문에 답하고, 판단에 필요한 사실이나 근거를 포함합니다. | 글쓰기의 내용과 전달 방식 네 항목 |
| 수정·검증 결과를 보고하는 작업 | 요청한 변경을 완료하고, 필요한 검증을 수행해 결과를 보고합니다. | 작업 결과에 해당하는 평가 축, 업무 흐름, 전달 방식 |

> 결론부터 자연스럽고 직접적으로 말해줘. 내가 결정하거나 확인해야 할 일이 있으면 앞에 알려줘. 판단에 필요한 근거는 남기고 반복은 줄여줘. 설명이 추상적이면 구체적인 예시 하나를 들어줘.

네 번의 실행으로 말투, 간결함, 정보 순서, 예시 중 무엇이 달라졌는지와 설명을 다시 요청하거나 직접 고칠 일이 줄었는지 확인합니다. 이후 UI 개선, 여러 도구를 쓰는 업무, 요구사항이 모호한 작업을 추가하고, 반복해서 나타난 문제를 기준으로 스킬과 플러그인 후보를 고릅니다.
