## 1. ISO-15~18 승인 흐름 통합 (시나리오마다 5회)

### 방법

- 시험 프로필의 `config.json`에 `security.sandbox_enabled=true`만 넣었습니다. 정책 수준은 기본값 `smart`이고, ISO-16만 세션 승인 수준 `strict`를 요청 문맥에 넣었습니다.
- 셸 도구는 `execute_shell_command`, 파일 도구는 `write_file`·`read_file`이며, 에이전트가 쓰는 것과 같은 `PolicyGuardedTool`로 감쌌습니다. 비관리자이므로 거버넌스 경로는 Restricted Token을 골랐습니다.
- 승인된 명령이 하는 일은 작업 폴더 밖 하네스 폴더에 표식 파일 하나를 쓰는 것뿐입니다. Restricted Token은 이 폴더 쓰기를 거부하므로, 표식 파일이 생겼다면 그 명령은 샌드박스 없이 실행된 것입니다. 호스트에서 같은 폴더 쓰기 대조는 성공했습니다.
- 작업 폴더 안 양성 대조는 승인 요청에 거부로 답하게 했습니다. 샌드박스 실패가 호스트 재실행으로 가려지지 않게 하려는 것입니다.
- 승인 대상 일반화는 원래 LLM을 부릅니다. 시험 프로필에는 모델이 없어서 그 함수를 즉시 실패하도록 바꿨고, 제품은 이 경우 정확한 대상을 표시·저장합니다. 응답 만료 시험만 승인 대기 시간을 기본 300초에서 3초로 줄였습니다.

### Git Bash가 셸로 잡힌 경우 (각 5회)

QwenPaw는 셸을 고를 때 `SHELL` 환경 변수를 따릅니다. 처음 1회 점검에서는 측정 프로세스를 Git Bash에서 띄워 `C:\Program Files\Git\usr\bin\bash.exe`가 쓰였습니다. 같은 조건을 따로 5회 측정했습니다.

- 작업 폴더 안 `echo ok > pc.txt`도 Restricted Token에서 `fatal error - CreateFileMapping <SID>.1, Win32 error 5`로 바로 끝났습니다 5/5.
- 위반 분류 정규식의 `error 5\b`가 이 문구에 맞아 샌드박스 위반으로 분류됐고, "격리 없이 재실행" 승인 요청이 떴습니다 5/5.
- Git Bash로 QwenPaw를 띄운 사용자는 모든 셸 명령이 샌드박스에서 실패하고 호스트 재실행 승인을 요청받습니다. 습관적으로 승인하면 샌드박스가 사실상 꺼집니다.

본 측정은 `SHELL`을 지워 제품 기본 셸(cmd)로 실행했습니다.

| --- | --- | --- |

## 6. 보강: 원인과 작업 호환성 (조건마다 5회)

### ISO-03 Restricted Token이 작업 폴더 밖 파일을 덮어쓴 원인

[2026-11-24-01](2026-11-24-01.md)에서 쓰기가 허용된 "공용 임시 위치"는 다른 프로그램이 `C:\Users\Public\Documents` 아래 만든 공용 임시 폴더였습니다. 공개 저장소 원칙에 따라 그 프로그램의 폴더 이름은 적지 않습니다. 이전 세션 기록에서 경로를 찾았고, 그 폴더는 읽기 전용으로 ACL만 조회했습니다. 이 폴더에는 명시적 `Everyone:(OI)(CI)(F)`가 있습니다.

원인을 가리기 위해 하네스 폴더 세 곳에 ACE를 하나씩 더하고, Restricted Token으로 그 안의 파일 덮어쓰기를 시도했습니다.

| 하네스 폴더의 추가 ACE | Restricted Token 덮어쓰기 |
| --- | --- |
| 없음(사용자 임시 폴더 상속) | 거부 5/5 |
| `Everyone` 수정 | 성공 5/5 |
| `INTERACTIVE` 수정 | 거부 5/5 |

Restricted Token의 제한 SID에는 Everyone이 들어 있습니다. 그래서 Everyone에 쓰기를 준 위치는 Restricted Token도 쓸 수 있습니다. 공용 폴더나 권한이 넓은 다른 프로그램 폴더는 Restricted Token으로 보호되지 않습니다. 원인 **확정**.

### ISO-07~09 AppContainer의 하위 폴더 보호가 실패한 원인

작업 폴더 아래에 `ro`(읽기 전용 마운트)와 `deny`(`deny_paths`)를 두고 측정했습니다. 샌드박스 안 토큰, 각 객체의 AppContainer 관련 ACE, 권한별 열기, 실제 조작을 확인했습니다. 권한별 열기는 각 권한으로 열기만 하고 닫는 검사입니다.

| 확인 항목 | 결과 (5/5 동일) |
| --- | --- |
| 자식 토큰 | AppContainer, 무결성 Low, capability 없음. AppContainer SID는 ACL의 SID와 같음 |
| `ro` 폴더와 파일 | 제품이 추가한 읽기·실행 ACE `0x1200a9`와, 작업 폴더에서 상속된 수정 ACE `0x1301ff`가 함께 있음 |
| `deny` 폴더와 파일 | 폴더에 AppContainer SID 거부 `FA`와 상속용 거부 ACE, 파일에 상속된 거부 `FA`. 작업 폴더에서 상속된 수정 ACE도 있음 |
| 권한별 열기(AppContainer) | 두 폴더 모두 목록·파일 추가·하위 삭제, 기존·신규 파일의 읽기·데이터 쓰기·삭제 권한이 **모두 허용** |
| cmd 조작(AppContainer) | 읽기·덮어쓰기·이름 변경 성공, `dir`·`del`은 `Access is denied.` |
| Python 조작(AppContainer) | 목록·삭제·새 파일 생성 모두 성공(호스트에서 확인) |
| cmd `dir /b`, 보호 없는 작업 폴더 루트(AppContainer) | 실패 5/5 |

- **읽기 전용 마운트가 실패한 원인은 확정입니다.** 제품은 읽기·실행 ACE를 더하기만 하고, 작업 폴더에서 상속되는 수정 ACE를 끊지 않습니다. 두 ACE가 합쳐져 쓰기가 허용됩니다.
- **거부 경로**에는 AppContainer SID를 대상으로 한 거부 ACE가 실제로 걸려 있었습니다. 그런데도 AppContainer 프로세스는 모든 권한을 받았습니다. 관찰상 AppContainer SID 대상 거부 ACE는 효과가 없었습니다. Windows가 AppContainer 접근 검사에서 이런 거부 ACE를 어떻게 다루는지는 문서로 확인하지 못했습니다.
- **run 03의 "AppContainer는 목록·삭제를 막았다"는 보호 효과가 아니었습니다.** AppContainer 안에서 cmd의 `dir`·`del`은 보호 설정이 없는 작업 폴더 루트에서도 실패했습니다. [AppContainer cmd 진단](probe-ac-cmd-diag.py)에서도 상대·절대 경로, `cd` 후 실행이 모두 같았고, Restricted Token에서는 전부 성공했습니다. 같은 동작을 Python으로 하면 성공합니다. AppContainer에서 에이전트가 흔히 쓰는 cmd 명령이 깨지는 호환성 문제입니다.
- ISO-09(시작 뒤 생긴 파일)도 상속 ACE가 같아 결과가 같았습니다.

합성 빌드로 작은 모듈 16개를 Python `ProcessPoolExecutor`(작업 프로세스 4개)로 컴파일했습니다.

| 조건 | 순차 빌드 | 병렬 빌드 |
| --- | --- | --- |

| Restricted Token | 성공 5/5 | 실패 5/5 |

두 백엔드 모두 작업 프로세스를 만들기 전 `multiprocessing.connection.Pipe`에서 `PermissionError [WinError 5]`가 났습니다. 이 함수는 Windows에서 명명된 파이프를 만듭니다. ISO-14에서 자식 3개를 동시에 띄우는 것은 됐으므로, 막힌 것은 명명된 파이프로 통신하는 병렬 작업입니다. 다른 빌드 도구의 결과는 측정하지 않았습니다.

## 7. 시험용 venv 폴더의 AppContainer ACE

AppContainer는 샌드박스를 만들 때 QwenPaw를 실행한 Python 폴더에도 읽기·실행 ACE를 추가합니다. 대상은 `sys.executable`의 상위 폴더로, 여기서는 시험용 venv인 `%LOCALAPPDATA%\agent-isolation-qwenpaw-2.3.0.post1`입니다(`windows_appcontainer_sandbox.py:275-289`, `windows_unelevated_sandbox.py:377-385`). 사용자 설치 Python 폴더는 대상이 아닙니다.

- 보강 측정의 AppContainer 샌드박스 20개 모두 실행 중에는 이 ACE가 있었고, `destroy()` 뒤에는 삭제됐습니다(20/20).
- 측정 전부터 이 폴더에 존재하지 않는 AppContainer SID의 명시적 읽기·실행 ACE가 4개 있었습니다. 측정 전후로 그대로였습니다.
- 4개의 출처는 확정하지 못했습니다. 정상 `destroy()`는 매번 지웠으므로, 이전 세션에서 비정상 종료된 AppContainer 실행의 잔여물일 가능성이 높습니다. 이 ACE는 변경하지 않았습니다.
- 처음 조회한 시점에는 5개로 보였는데, 하나는 그때 실행 중이던 AppContainer 측정의 것이었습니다.

## 8. 측정 중 오류와 처리

1. 승인 흐름 1회 점검에서 측정 프로세스의 `SHELL`(Git Bash) 때문에 제품이 bash를 셸로 썼습니다. 그 회차는 무효로 하고, 본 측정은 `SHELL`을 지워 제품 기본 셸로 실행했습니다. bash 동작은 별도 시나리오로 5회 측정했습니다.
2. 같은 점검에서 대기 중 정책 변경을 메모리의 규칙 목록에만 넣었습니다. 승인 경로가 규칙을 저장하면서 `policy.yaml`을 다시 읽어 이 변경이 사라졌습니다. 본 측정은 `governor.add_rule()`로 디스크에 저장했고, 직후 새 호출이 거부되는 것으로 변경이 적용됐음을 확인했습니다.
3. 클립보드·레지스트리 1회 점검에서 호스트 대조의 cmd 따옴표 전달이 잘못돼 대조가 무효였습니다. 대조를 Python 직접 실행으로 바꿨습니다. 자원 한도 검사는 현재 프로세스 핸들 형식 오류로 실패해 고쳤습니다. 본 측정은 고친 뒤 실행했습니다.
4. 제품이 표준 출력에 진행 문구를 써서 결과 JSON이 섞였습니다. 결과를 별도 파일로 쓰게 바꿨습니다.
5. 승인 흐름 하네스는 감사 DB(`audit.db`)가 열린 채로 시험 폴더를 지우려 해 폴더가 남았습니다. 측정이 끝난 뒤 지웠습니다.

## 실제 계정 보존 확인

측정 후 실제 `~/.qwenpaw`는 기준선과 같았습니다. `%LOCALAPPDATA%\Packages\qwenpaw_*`, HKCU의 qwenpaw AppContainer 매핑, 남은 시험 프로세스, 하네스 폴더는 모두 0개였습니다. HKCU AppContainer 매핑 전체 수는 측정 시작 전과 끝난 뒤 모두 137개였습니다. 06 기록의 138개와 1개 차이는 이번 측정 시작 전에 이미 있었고, qwenpaw 매핑이 아니어서 원인은 조사하지 않았습니다. 레지스트리 값과 클립보드 내용은 읽거나 쓰지 않았습니다. ACE는 하네스 폴더에만 추가했습니다.
