# agent-desktop QA 운영 가이드

PR에서는 기존 Playwright와 네이티브 E2E로 회귀를 검사한다. Windows 빌드를 직접 확인하는 QA에서는 agent-desktop으로 실제 앱 창의 컨트롤을 읽고 조작한다. 첫 도입 범위는 검증을 마친 **대상 앱 온보딩** 한 흐름이다. 오버레이는 사람이 함께 보는 시연이나 버그 재현에서 켠다.

## 첫 시나리오

| 단계 | 동작 | 기대 상태 |
| --- | --- | --- |
| 1 | 테스트 빌드를 새 임시 프로필로 실행한다. | 온보딩이 열리고 `1 / 3`이 표시된다. |
| 2 | 최신 접근성 스냅샷에서 `다음`을 찾아 누른다. | 새 스냅샷에서 `2 / 3`이 확인된다. |
| 3 | 최신 스냅샷에서 `건너뛰기`를 찾아 누른다. | 안내와 해당 버튼이 사라진다. |

Windows QA 세션에서 앱 빌드와 agent-desktop 버전을 기록한다. 현재 확인한 구성에서는 테스트 프로세스에만 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`로 `--force-renderer-accessibility`를 전달한다. 오버레이를 켤 때는 [검증한 임시 실행 파일 이름과 설정](windows-cursor-overlay.html)을 사용한다.

## 판정과 기록

- **통과**는 클릭 후 기대 상태가 새 스냅샷이나 독립 검증에서 확인된 경우다.
- **실패**는 검증 가능한 실제 앱 상태가 기대와 다른 경우다. 독립 검증에서도 같은 동작이 실패하는지 확인한다.
- **판정 불가**는 필요한 접근성 요소를 찾지 못했거나, 창 포커스 또는 입력 전달 문제로 앱 동작까지 검증하지 못한 경우다.

실행마다 빌드와 도구 버전, 실행 옵션, 실패 단계와 기대·실제 상태를 `runs/`에 기록한다. 상세 CLI 응답, 직전·직후 접근성 JSON, 화면 캡처는 실행 ID별로 `local/`에 보관한다. [첫 WebView2 실행 기록](runs/2026-11-23-02.md)에 증거 위치와 실제 판정 예가 있다.

온보딩을 수동 QA 체크에 먼저 넣고, 같은 빌드에서 독립 실행 세 번이 통과하면 Windows 실행 스크립트로 고정한다. 설정 열기는 클릭 응답 후 화면 전환이 없었고, 저장 충돌은 전경 입력에서 막혔다. 두 흐름은 각각 동작 후 상태를 재현하고 확인한 뒤 체크에 추가한다.
