# Restricted Token 계열 백엔드 비교 실측 계획

QwenPaw와 Codex의 Restricted Token 방식이 어디까지 방어하고 한계가 무엇인지 정확히 확인하는 계획입니다. QwenPaw 비관리자, QwenPaw 관리자, Codex `unelevated`, Codex `elevated`를 같은 PC에서 같은 항목으로 측정합니다.
- 설계 차이는 [Restricted Token 계열 백엔드 비교](research/restricted-token-backends.md)에 정리했습니다. 토큰, SID, DACL, ACE 같은 용어도 그 문서의 용어 절에 정의했습니다.
- QwenPaw 비관리자 결과는 [QwenPaw 실측 보고서](report-qwenpaw-backends.md)에 있습니다.
- MXC BaseContainer는 이 계획에 넣지 않았습니다. 2026-11-25에 실측하지 않기로 했고, 사용할 수 있는 장치와 그 비율만 [MXC 조사](research/solutions/mxc.md#사용할-수-있는-장치와-비율)에 정리했습니다.
- 이 계획은 2026-11-25에 Fable 검토를 두 번 거쳐 고쳤습니다. 사용자 결정이 필요한 항목은 7장에 모았습니다.

**상태: 2026-11-25 측정 완료.** 아래 본문은 측정 전에 쓴 계획이고, 예상 칸의 내용은 측정 전 예상입니다. 단계별 최종 상태는 [5장](#5-진행-순서)에, 결과는 [결과 및 판단](findings.md#restricted-token-네-구성-실측-2026-11-25)에 있습니다.

## 0. 측정으로 답할 질문

| 질문 | 항목 |
| --- | --- |
| 작업 폴더 밖 쓰기를 어디까지 막는가 | B |
| 파일 읽기와 사용자 범위 비밀(DPAPI)을 어디까지 막는가 | C |
| 환경 변수와 프로필이 분리되는가 | E |
| 샌드박스 프로그램의 창이 사용자 데스크톱과 분리되는가 | F |
| 명령이 끝나거나 중단될 때 자식 프로세스를 정리하는가 | G |
| 다른 프로세스와 그 토큰에 어디까지 접근하는가 | P |
| 레지스트리를 어디까지 막는가(사용자, 다른 계정, 컴퓨터 전체·관리자 전용 키, 쓰기 허용 키)와 샌드박스 계정 상태가 공유되는가 | B9, R |
| 실행 후 PC에 무엇이 남고, 그것이 무엇을 허용하는가 | H, 3장 |

측정하지 않는 것과 그 이유는 4장 끝에 모았습니다.

## 1. 원칙

- **실측 PC와 상태 기록.** 2026-11-24 결정에 따라 실제 사용 PC에서 측정합니다. 측정 전후의 계정·방화벽·레지스트리·파일 ACE·제품 상태를 기록하고 비교합니다.
- **측정 전 상태를 따로 기록.** 이 PC에는 이전 Codex 사용으로 생긴 ACE가 이미 있습니다(`Documents`, `.gitconfig`, `%TEMP%`의 `CodexSandboxUsers` 수정 허용 ACE, `~/.codex`의 ACE 182개 중 거부 174개, `cap_sid`의 기존 항목 등). 측정 결과와 섞지 않고 보고서의 "측정 전 상태" 절에 따로 적습니다.
- **합성 데이터만 사용.** 시험 파일, 시험용 환경 변수, 시험용 DPAPI 값, 측정 스크립트가 띄운 시험 프로세스만 씁니다.
  - 실제 사용자 파일·인증 파일은 해당 권한으로 **열어 보기만** 하고 내용은 읽지 않습니다.
  - 다른 프로세스·토큰·레지스트리 키는 핸들을 열 수 있는지만 확인하고 바로 닫습니다. 프로세스 메모리를 읽거나 쓰지 않고, 토큰을 복제하거나 가장하지 않으며, 실제 레지스트리 값을 쓰지 않습니다.
  - 알려진 격리 우회 기법은 시도하지 않습니다.
- **같은 조건, 5회 반복.** 네 구성에 같은 셸(`cmd.exe`), 같은 시험 프로그램, 같은 판정 기준을 씁니다. 조건마다 5회 반복하고, 차단 판정 전에는 같은 대상이 허용 상태에서 정상 동작하는지 먼저 확인합니다. 예외로 1회만 재는 항목은 A3·A4·G3·P4, B10의 Codex `unelevated`, R4이며, 결과가 소스나 Windows 기본 동작으로 정해지거나 반복 비교의 의미가 작기 때문입니다.
- **시험 프로그램은 독립 런타임으로.** 샌드박스 안에서 실행하는 측정 프로그램은 `C:\agent-isolation-test\tools\`에 둔 독립 런타임으로 실행합니다. 가상환경의 Python은 사용자 프로필 안의 인터프리터를 가리켜, 프로필을 읽지 못하는 구성에서는 측정 도구 자체가 실패하기 때문입니다. 측정 도구가 실행되지 못한 경우는 "차단"이 아니라 "측정 불가"로 따로 집계합니다.
- **시험 대상은 승격되지 않은 프로세스가 만듦.** 시험 프로세스·명명된 파이프·측정용 파일은 네 구성 모두 승격되지 않은 별도 측정 프로세스가 만듭니다. 승격된 프로세스가 만들면 무결성 수준(High)과 소유자(Administrators)가 달라져 비교할 수 없기 때문입니다.
- **시험 자식의 수명 제한.** 샌드박스 안에서 띄우는 모든 시험 자식은 60~120초 뒤 스스로 끝나게 만듭니다. 샌드박스 계정 소유로 살아남은 프로세스는 일반 세션에서 종료하지 못하고, 남으면 계정·프로필 삭제도 실패하기 때문입니다.
- **실제 백엔드 판정.** 결과마다 A1(실행 계정)·A2(제한 SID 목록과 그룹)·A5(데스크톱)의 조합으로 실제 백엔드를 판정합니다. QwenPaw는 백엔드 클래스 이름과 샌드박스 계정 SID를, Codex는 사용한 권한 프로필과 명령줄 옵션을 함께 기록합니다.
- **공개 기록과 내부 식별자.** SID, 컴퓨터 이름, 실제 프로그램 이름, 레지스트리 키 경로, 회사 정책 이름 같은 내부 식별자는 공개 실행 기록에 넣지 않고 `local/`에만 보관합니다.
- **판정.** 통과, 실패, 미지원, 설계상 차이(제품이 의도한 동작이 기대와 다름), 측정 불가(제품 구조나 도구 문제로 측정할 수 없음), 미실측으로 기록합니다.

## 2. 측정 환경과 실행 방법

### 2.1 측정용 폴더

사용자 프로필 밖에 `C:\agent-isolation-test\`를 만들어 씁니다(2026-11-25 결정).
- **프로필 밖에 두는 이유.** QwenPaw 관리자는 작업 폴더의 상위 폴더(드라이브 루트 제외)에 목록 조회·경로 탐색 허용 ACE를 추가합니다. 작업 폴더가 프로필 안이면 `C:\Users`, 사용자 프로필, `AppData` 등의 DACL이 바뀝니다. 또 `%TEMP%` 아래 폴더는 기존 Codex ACE를 상속해 결과가 오염됩니다.
- **구성별 작업 폴더 묶음.** 네 구성이 같은 작업 폴더를 쓰면 앞 구성이 남긴 ACE와 폴더가 뒤 구성 결과에 섞입니다. 그래서 구성마다 묶음을 따로 둡니다.
- **작업 폴더는 고정 경로만 재사용.** Codex는 작업 폴더와 추가 쓰기 경로마다 capability SID를 새로 만들고, Codex `elevated`는 실제 `~/.codex` DACL에 거부 ACE를 영구히 추가합니다. QwenPaw 관리자는 작업 폴더·마운트·`deny_paths`·`network_allow`·Python 폴더가 설정 지문에 들어가 지문마다 로컬 계정을 새로 만듭니다. 그래서 아래 경로만 씁니다.

```
C:\agent-isolation-test\
├─ tools\                     독립 런타임과 측정 프로그램
├─ qwenpaw-profile\           QwenPaw 시험 프로필(USERPROFILE·HOME). 실제 프로필과 같은 DACL
├─ qwenpaw-unelevated\ws-A, ws-B, ws-large
├─ qwenpaw-admin\ws-A, ws-B, ws-large
├─ codex-unelevated\ws-A, ws-B, ws-large, temp\, home\   (home = 시험용 CODEX_HOME)
├─ codex-elevated\ws-A, ws-B, ws-large, temp\
└─ targets\                   아래 표
```

- `ws-A`: 기본 작업 폴더. `ws-B`: B5·B6(첫 실행)·B8b·R3용. `ws-large`: 합성 파일 1만 개, H4용.
- **QwenPaw 설정 지문 최소화.** QwenPaw는 `ws-A` 설정 하나에 읽기 전용 마운트, `targets\admin-owned` 쓰기 마운트, `targets\deny-read` 거부 경로를 함께 넣습니다. 예상 설정 지문은 구성당 3개(`ws-A`, `ws-B`, `ws-large`)이며, QwenPaw 관리자는 같은 이름의 계정 3개를 회차마다 만들고 지웁니다.
- **대상 폴더.** `targets\` 아래에 상속을 끊고 DACL을 고정한 폴더를 만듭니다. 측정 전에 각 폴더의 DACL을 기록합니다.

| 대상 폴더 | DACL | 쓰는 항목 |
| --- | --- | --- |
| `user-only` | 사용자·SYSTEM·Administrators만 허용(사용자 프로필과 같은 형태) | B2, C1 |
| `default-inherit` | `C:\` 기본 상속 그대로(Users 읽기·실행, Authenticated Users 수정) | B2b, C1b |
| `everyone-write` | `user-only` + Everyone 수정 허용 | B3 |
| `logon-write` | `user-only` + 측정 시점 로그온 SID 수정 허용 | B4 |
| `admin-owned` | 관리자 세션에서 만듦. 소유자 Administrators, 사용자는 수정 허용이지만 `WRITE_DAC` 없음 | B10 |
| `deny-read` | `user-only` + Users 읽기 허용. 네 구성 모두 거부 지정 전에는 읽을 수 있어야 거부 ACE의 효과를 판정할 수 있음 | C5, C6 |
| `dpapi` | `user-only` + Users 읽기 허용. 호스트가 만든 시험용 DPAPI 값 두 개(사용자 범위, 컴퓨터 범위) | C7 |

### 2.2 구성별 실행 방법

| 구성 | 실행 방법 |
| --- | --- |
| QwenPaw 비관리자 | 승격되지 않은 측정 스크립트가 백엔드 API를 직접 호출. 설정은 에이전트 경로와 같게 `network_allow=["*"]`. `qwenpaw`를 불러오기 **전에** `USERPROFILE`·`HOME`을 `qwenpaw-profile`로 바꿈(상태 폴더 경로가 불러오는 시점에 정해짐). Deny Paths Protection 기능은 끈 상태로 두고 그 상태를 기록 |
| QwenPaw 관리자 | 같은 측정 스크립트를 UAC 승인한 관리자 세션에서 실행. `network_allow=["*"]`(2026-11-25 결정)라 방화벽 규칙을 만들지 않음. `USERPROFILE` 처리는 위와 같음. 한 회차의 항목을 한 프로세스에서 실행해 계정 생성·삭제 횟수를 줄임 |
| Codex `unelevated` | 측정 스크립트가 네이티브 `codex.exe`를 직접 실행. 명령 형태는 `codex sandbox [옵션] -- <cmd.exe 절대 경로> ...`로 고정(첫 인자가 `setup`이면 설치 명령으로 해석되므로). 작업 폴더는 `codex.exe` 프로세스의 현재 폴더. **시험용 `CODEX_HOME`**(`codex-unelevated\home`). `codex.exe`를 띄우는 환경의 `TEMP`·`TMP`를 `codex-unelevated\temp`로 바꿈 |
| Codex `elevated` | 같은 방식에 `[windows] sandbox = "elevated"`. **실제 `CODEX_HOME`**. `TEMP`·`TMP`는 `codex-elevated\temp` |

- **Codex 권한 지정 방식 통일.** `codex sandbox`는 설정 파일의 `sandbox_mode`를 무시하고, 지정이 없으면 읽기 전용으로 실행합니다. 또 읽기 거부(C5·C6)와 읽기 전용 하위 경로(B6)는 권한 프로필로만 표현됩니다. 그래서 두 Codex 구성의 모든 실행을 **명시적 권한 프로필(`-P`)**로 지정하고, 관리 설정 포함 여부(`--include-managed-config`)는 두 구성 모두 **끔**으로 고정합니다. 실제 `CODEX_HOME`에만 인증 정보가 있어 관리·클라우드 설정이 한쪽에만 적용될 수 있기 때문입니다. 프로필 정의(쓰기 경로, 읽기 전용 경로, 읽기 거부 경로, 네트워크)는 사전 점검에서 확정하고 실행 기록에 남깁니다. [`codex sandbox` 정책 결정](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/cli/src/debug_sandbox.rs#L611-L647)
- **환경 정책.** 실제 설정의 `[shell_environment_policy.set]` 값은 명령줄로 옮기지 않습니다. E1은 측정 스크립트가 넣은 시험 변수만 출력해 비교합니다.
- **Codex `elevated`의 실행 계정.** 권한 프로필의 네트워크를 끄면 오프라인 계정(`CodexSandboxOffline`), 켜면 온라인 계정으로 실행합니다. 기본값은 오프라인 계정이며, 7장 결정 전까지 오프라인 계정으로 계획합니다. 오프라인 계정은 방화벽이 로컬 TCP·UDP를 막지만 명명된 파이프(G4·G5)는 방화벽 대상이 아닙니다.
- **B10은 별도 실행.** Codex `elevated`는 추가 쓰기 경로에 ACE를 추가하지 못하면 명령을 실행하지 않으므로, Codex는 B10만 따로 실행합니다. QwenPaw는 `ws-A` 설정에 포함합니다.
- **임시 폴더.** Codex 두 구성과 QwenPaw 비관리자는 측정용 `temp`를 씁니다. QwenPaw 비관리자는 부모 환경을 그대로 넘기므로 측정 스크립트의 `TEMP`가 그대로 전달됩니다. QwenPaw 관리자는 `TEMP`를 전용 계정 프로필로 덮어씁니다.

**관리자 두 구성이 PC에 남기거나 바꾸는 것**

| 구성 | 정리 함수가 삭제하는 것 | 남는 것(정리 코드 없음 또는 설계상 유지) |
| --- | --- | --- |
| QwenPaw 관리자 | 로컬 계정 `qwenpaw_<12자리>`(설정 지문별), 프로필 폴더(하이브 언로드 후), 기록된 ACE(작업 폴더와 `C:\agent-isolation-test` 아래 상위 폴더의 경로 탐색·목록 조회 ACE. 드라이브 루트는 대상이 아님) | `ProfileList` 항목, `QwenpawUsers` 그룹, "일괄 작업으로 로그온" 권한(삭제된 계정의 SID가 남음), 사용자 창 스테이션·`Default` 데스크톱 DACL의 전용 계정 ACE(로그오프까지), `\\.\NUL` 장치 DACL의 capability SID ACE, 가상환경 폴더의 그룹 ACE와 `.qwenpaw_acl_granted` |
| Codex `elevated` | 없음 | 이미 설치된 계정·그룹·방화벽 규칙·WFP 필터. 새로 생기는 것: 작업 폴더·`temp`·B10·C2 경로별 `cap_sid` 항목과 실제 `~/.codex` DACL의 거부 ACE, `.sandbox-bin`의 0.171.0 실행기 사본(이 PC에는 0.164.0까지만 있음), `deny_read_acl_state.json` 갱신, 측정용 폴더 ACE, C2 폴더의 `CodexSandboxUsers` 읽기 ACE |

### 2.3 Codex `elevated` 보호 조치

- **설치 단계가 다시 실행되는 조건(소스 확인).**
  - 설치 완료 표시 파일이 없거나 버전이 맞지 않을 때(현재 표시 파일 버전 5 = 소스의 `SETUP_VERSION` 5)
  - 샌드박스 계정이 없거나 비활성·만료일 때
  - 실행기 로그온이나 자식 시작이 `ERROR_LOGON_FAILURE`·`ERROR_ACCOUNT_DISABLED`·`ERROR_NO_SUCH_LOGON_SESSION`으로 실패할 때. 이때 Codex는 계정 기록 파일을 **먼저 삭제**한 뒤 설치 단계를 다시 실행합니다. [오류 분류](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/windows-sandbox-rs/src/elevated/runner_client.rs#L118-L175) · [기록 파일 삭제](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/windows-sandbox-rs/src/identity.rs#L497-L510)
  - `codex sandbox`는 프록시 설정을 보존 모드로 쓰므로 프록시 포트·`allow_local_binding` 조건은 해당하지 않습니다.
- **UAC 창 없이 재설치될 수 있음.** 자동 설치는 설치된 서비스를 먼저 쓰고, 서비스가 없을 때만 UAC 도우미로 넘어갑니다. 이 PC에는 Codex 샌드박스 서비스가 실행 중이라 재설치가 창 없이 끝날 수 있습니다. 그래서 "UAC 창"이 아니라 계정 상태로 재설치를 감지합니다. [자동 설치 순서](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/windows-sandbox-rs/src/identity.rs#L451-L478)
  - 감지: 두 샌드박스 계정의 비밀번호 설정일(`Get-LocalUser`의 `PasswordLastSet`)과 계정 기록 파일 해시를 사전 점검 직후와 항목 묶음마다 확인합니다.
- **백업(2026-11-25 결정).** 측정 전에 `~/.codex\.sandbox-secrets` 폴더 전체와 `~/.codex\.sandbox\setup_marker.json`을 내용을 열지 않고 그대로 `C:\agent-isolation-backup\`에 복사합니다. 원본 파일의 소유자와 DACL도 함께 기록합니다.
  - 백업 폴더는 상속을 끊고 사용자와 SYSTEM만 허용하며, `CodexSandboxUsers`에 거부 ACE를 붙입니다. 비밀번호가 DPAPI 컴퓨터 범위로 암호화돼 이 PC의 어느 계정이든 복호화할 수 있고, `%TEMP%`에는 `CodexSandboxUsers` 수정 허용 ACE가 있기 때문입니다.
  - 백업은 저장소에 넣지 않습니다. 측정이 끝나고 평소 Codex가 정상 동작하는 것을 확인한 뒤 삭제합니다.
- **복구 절차.**
  - 비밀번호 설정일이 그대로인데 계정 기록 파일만 삭제·변경됐으면, 승격되지 않은 세션에서 백업을 복원하고 원본과 같은 소유자·DACL인지 확인합니다.
  - 비밀번호 설정일이 바뀌었으면 재설치가 끝난 것이므로 백업을 복원하지 않습니다. 옛 비밀번호로 복원하면 로그온 실패 → 기록 파일 삭제 → 재설치가 반복되기 때문입니다. 새 비밀번호로 동작하는지 확인하고 기록합니다.
  - UAC 창이 뜨면 취소하고 위와 같이 판단합니다.
- **측정 중 금지 사항.** 측정 중에는 실제 Codex(데스크톱 앱·CLI)를 실행하지 않습니다. 측정 셸에 `CODEX_WINDOWS_REGISTERED_CORE` 환경 변수가 없는지 확인합니다. 명령 첫 인자로 `WindowsApps` 경로의 실행 파일을 쓰지 않습니다.

### 2.4 회사 정책과 보안 제품

이 PC는 도메인에 가입된 PC입니다. 로컬 계정 생성, 로그온 권한 변경, ACE 변경이 실패하거나 결과가 되돌려지면 다음 순서로 원인을 확인합니다(2026-11-25 결정).
1. 실패한 API와 오류 코드를 기록합니다.
2. `gpresult`(읽기 전용)로 사용자 권한 할당·계정 정책 등 관련 정책이 적용됐는지 확인합니다.
3. 보안 이벤트 로그와 보안 제품 로그를 읽기 전용으로 확인합니다.
4. 회사 정책이 원인이면 실행 기록에 "회사 정책으로 실패"라고 메모합니다. 정책 이름 같은 세부 내용은 `local/`에만 둡니다.

제한된 토큰의 프로세스가 실제 인증 파일(C3)이나 다른 프로세스(P)를 여는 동작은 보안 제품이 경보를 낼 수 있습니다. 사전 통지 여부는 7장 결정 항목입니다.

| C2 | 사용자 프로필 바로 아래 새 항목 | `%USERPROFILE%` 바로 아래에 측정용 폴더를 새로 만들고 그 안 파일 읽기. 측정 후 폴더 삭제 | 비관리자 두 구성은 허용. QwenPaw 관리자는 거부. Codex `elevated`는 명령마다 읽기 허용 ACE를 추가하므로 허용 | Codex `elevated`의 프로필 읽기 허용 ACE |
| C3 | 민감 폴더와 제품 설정 폴더 | 실제 `~/.ssh`, `~/.codex`, `~/.qwenpaw`, `~/AppData\Roaming` 아래 파일과 프로필 바로 아래 파일(`.gitconfig` 등)을 읽기 권한으로 **열기만** 함(내용은 읽지 않음). 대상마다 측정 전 `CodexSandboxUsers` ACE 여부를 함께 기록 | 비관리자 두 구성은 열기 허용. QwenPaw 관리자는 거부. Codex `elevated`는 `.ssh` 거부, `.codex`·`AppData`·프로필 바로 아래 파일은 허용 | 인증 정보 노출 위험. 측정 전 ACE 때문에 정해지는 결과인지 구분 |
| C4 | 샌드박스 비밀번호 보관 위치 | Codex `~/.codex\.sandbox-secrets`, QwenPaw 관리자 메타데이터 파일(`qwenpaw-profile` 안)을 열기만 함 | Codex `elevated`는 거부 ACE로 거부. 비관리자 두 구성은 열림. QwenPaw 관리자는 시험 프로필 DACL 때문에 거부(실제 `~/.qwenpaw`도 같은 형태) | 비밀번호 파일 보호 |

| C7 | 사용자 범위 DPAPI 값 복호화 | 호스트가 합성 문자열을 사용자 범위·컴퓨터 범위 DPAPI로 각각 보호해 `targets\dpapi`에 둠. 샌드박스에서 `CryptUnprotectData` 성공 여부 확인 | 사용자 범위: 비관리자 두 구성은 성공(같은 사용자), 관리자 두 구성은 실패. 컴퓨터 범위: 네 구성 모두 성공 | 브라우저·자격 증명 관리자가 쓰는 사용자 범위 비밀이 풀리는지. Codex 비밀번호 파일이 거부 ACE에만 의존하는 이유 |

### D. 네트워크 (측정하지 않음)

2026-11-25 결정에 따라 네트워크 차단은 측정하지 않습니다.
- 비관리자 두 구성은 프록시 환경 변수만 설정하므로, 그 변수를 사용하지 않는 연결과 DNS 조회는 막지 못합니다. QwenPaw 비관리자에서 이미 실측했습니다(`curl --noproxy "*"` 외부 연결 성공 5/5).
- 인터넷 사용을 실제로 제한하려면 모든 연결을 프록시로 거치게 강제하는 장치(방화벽 규칙과 프록시)가 필요합니다.
- Restricted Token에서 인터넷을 허용·거부하는 방법은 [비교 문서 5장](research/restricted-token-backends.md#5-네트워크)에 정리했습니다.

### G. 프로세스 수명과 자원

G1·G6과 H6은 측정 프로세스를 강제 종료해 잔여 상태를 만들 수 있으므로, 각 구성의 측정 마지막에 묶고 그 뒤에 정상 종료 실행을 한 번 넣습니다.

| 번호 | 측정 | 방법 | 예상 |
| --- | --- | --- | --- |
| G1 | 호출 프로세스 강제 종료 시 자식 (네 구성 공통) | 샌드박스 자식이 실행 중일 때 측정 스크립트가 제품 프로세스(QwenPaw 측정 프로세스, `codex.exe`)를 강제 종료하고 자식 생존 확인. Codex `elevated`는 실행기(`codex-command-runner.exe`)의 생존과, 호스트에서 조회한 손자 프로세스의 Job 소속(`IsProcessInJob`)도 기록 | QwenPaw 두 구성·Codex `unelevated`는 Job 핸들이 닫혀 자식 종료. Codex `elevated`는 Job을 실행기가 가지므로, 실행기가 파이프 끊김을 감지해 Job을 종료하는지에 따름. QwenPaw 관리자는 자식을 일시 중지 없이 만든 뒤 Job에 넣고 실패해도 그대로 실행하므로 Job 소속도 확인 |
| G1b | 제품 시간 초과 (QwenPaw 두 구성, ISO-06) | `timeout_seconds`로 자식이 있는 명령 중단 | Job 전체 종료. Codex는 `codex sandbox`에 시간 제한이 없어 측정 불가(소스 확인) |
| G2 | 셸 종료 뒤 남은 자식 | 백그라운드 자식을 실행하고 셸 종료. 자식이 출력 핸들을 상속한 조건과 출력을 `NUL`로 돌린 조건을 나눠 호출 반환 시점과 자식 생존 확인 | QwenPaw 두 구성은 출력 상속 조건에서 호출이 반환되지 않음. Codex 두 구성은 자식 생존, 출력 상속 조건에서는 호출도 반환되지 않을 가능성 |
| G3 | 자원 한도 (ISO-14) | Job 한도 조회. 사전 점검에서 1회 | 모두 한도 없음 |
| G4 | 병렬 빌드 (ISO-11) | 명명된 파이프를 쓰는 Python 병렬 빌드(독립 런타임) | 측정 |
| G5 | 호스트 명명된 파이프 (ISO-11) | 승격되지 않은 측정 프로세스가 만든 파이프 읽기·쓰기 | 측정 |
| G6 | Job 이탈 | 샌드박스 안에서 `CREATE_BREAKAWAY_FROM_JOB`으로 자식을 만든 뒤 G1처럼 제품 프로세스를 강제 종료(QwenPaw는 G1b 시간 초과도)하고 그 자식 생존 확인 | Codex 두 구성은 Job에 `BREAKAWAY_OK`가 있어 이탈한 자식이 살아남음. QwenPaw는 이탈 자체가 실패 |

### P. 다른 프로세스 접근

P1~P3과 P5~P6은 측정 스크립트가 띄운 프로세스와 제품 프로세스만 대상으로 합니다. 핸들을 열 수 있는지만 확인하고 바로 닫으며, 메모리를 읽거나 쓰지 않고 토큰을 복제·가장하지 않습니다. P4는 전체 목록을 세지만, 시스템·보호 프로세스는 열지 않고 명령줄 내용도 가져오지 않습니다. 실제 PC의 프로그램 이름·SID는 기록하지 않고 계정 종류별 개수만 기록합니다.

| 번호 | 측정 | 방법 | 예상 | 왜 보나 |
| --- | --- | --- | --- | --- |
| P1 | 호스트 시험 프로세스 열기 권한 | 승격되지 않은 측정 프로세스가 띄운 시험 프로세스를 샌드박스에서 `OpenProcess`로 권한마다 따로 열고 바로 닫음: `PROCESS_QUERY_LIMITED_INFORMATION`, `PROCESS_VM_READ`, `PROCESS_VM_WRITE`, `PROCESS_VM_OPERATION`, `PROCESS_CREATE_THREAD`, `PROCESS_TERMINATE`, `PROCESS_DUP_HANDLE`, `SYNCHRONIZE`. 결과는 권한마다 기록 | 비관리자 두 구성은 `WRITE_RESTRICTED`의 두 번째 검사를 받지 않는 권한이 성공. `PROCESS_TERMINATE`도 쓰기로 분류되지 않으면 성공(추론). QwenPaw 관리자는 모두 거부(다른 계정, 다른 로그온 세션). Codex `elevated`는 A2의 로그온 SID 결과와 시험 프로세스 DACL에 따름 | 같은 PC에서 사용자 계정으로 실행 중인 다른 프로그램에 접근할 수 있는지 |
| P1b | 호스트 시험 프로세스의 토큰 열기 권한 | P1에서 `PROCESS_QUERY_LIMITED_INFORMATION`이 열리면 `OpenProcessToken`을 권한마다 따로 호출하고 바로 닫음: `TOKEN_QUERY`, `TOKEN_DUPLICATE`, `TOKEN_IMPERSONATE`, `TOKEN_ASSIGN_PRIMARY`, `TOKEN_ADJUST_DEFAULT`. 복제·가장 호출은 하지 않음 | 비관리자 두 구성은 `TOKEN_DUPLICATE` 등 쓰기로 분류되지 않는 권한이 열릴 것(추론). 관리자 두 구성은 P1 결과에 따름 | `WRITE_RESTRICTED`의 한계를 가장 직접 보여 주는 값 |
| P2 | 호스트 시험 프로세스 명령줄 조회 | 시험용 문자열을 명령줄 인자로 넣어 띄운 시험 프로세스의 명령줄을 `NtQueryInformationProcess(ProcessCommandLineInformation)`로만 조회. `ReadProcessMemory`와 WMI는 쓰지 않음 | 비관리자 두 구성은 조회됨. 관리자 두 구성은 P1의 정보 조회 결과에 따름 | 명령줄 인자로 전달된 토큰·비밀번호 노출 |
| P3 | 프로세스 정보(기준 자료) | 호스트에서 시험 프로세스, 사용자 셸 프로세스, Codex `elevated`의 실행기, 샌드박스 프로세스의 무결성 수준, 소유자, DACL(로그온 SID ACE의 권한 마스크 포함)을 읽기 전용으로 조회 | 해당 없음 | P1·P1b·P2·P5·P6 결과의 해석 근거 |
| P4 | 전체 프로세스 목록 | 샌드박스에서 전체 프로세스 목록을 조회하고 계정 종류별(사용자, 샌드박스 계정, 시스템·서비스)로 보이는 프로세스 수를 셈. 사용자·샌드박스 계정 프로세스만 `PROCESS_QUERY_LIMITED_INFORMATION`으로 열리는지 셈. 같은 시점의 목록을 승격되지 않은 측정 프로세스가 만들어 비교. 구성당 1회 | 네 구성 모두 이름·PID는 전부 보임. 열리는 수는 P1 결과와 같은 경향 | 실행 중인 다른 프로그램과 다른 계정의 프로세스 정보 노출 |
| P5 | 부모·실행기 프로세스 열기 권한 | 샌드박스에서 자신을 실행한 제품 프로세스(QwenPaw 측정 프로세스, `codex.exe`)와 Codex `elevated`의 실행기(`codex-command-runner.exe`)를 P1·P1b와 같은 권한 목록으로 열고 바로 닫음 | 비관리자 두 구성은 같은 사용자·같은 Medium 수준이라 P1과 같은 결과. QwenPaw 관리자는 부모가 다른 계정·다른 로그온·High 수준이라 거부(주원인은 DACL로 추정). Codex `elevated`의 실행기는 같은 샌드박스 계정의 제한되지 않은 토큰으로 실행되고 제한 SID 목록에 그 계정 SID가 있으므로, 쓰기 성격의 권한까지 열릴 가능성(추론) | 에이전트 프로세스 메모리의 API 키·인증 토큰 노출, 실행기를 통한 작업 폴더 간 분리 약화 |
| P6 | 동시에 실행 중인 다른 샌드박스의 프로세스 열기 권한 | `ws-A`와 `ws-B`에서 샌드박스를 동시에 실행하고, A에서 B의 프로세스를 P1과 같은 권한 목록으로 열고 바로 닫음 | QwenPaw 비관리자는 기본 DACL이 Everyone에게 모든 권한을 주므로 대부분 성공. Codex는 기본 DACL이 로그온 SID에만 주므로 측정. 관리자 두 구성은 측정 | 비교 문서 2장의 기본 DACL 차이 확인 |
| P7 | 사용자 프로세스 전체의 권한별 열기(2026-11-25 추가) | P1의 시험 프로세스는 DACL에 로그온 SID ACE가 없어 일반 데스크톱 프로세스와 다름. 사용자 계정의 모든 프로세스를 P1·P1b와 같은 권한 목록으로 열고 바로 닫음. 호스트는 각 프로세스 DACL을 `READ_CONTROL`로 읽어 로그온 SID ACE 유무로만 나눔. 개수와 explorer 결과만 저장하고 프로세스 이름은 저장하지 않음 | Codex `elevated`는 로그온 SID ACE가 있는 프로세스만 열릴 것 | 로그온 SID를 공유하는 구성이 사용자 데스크톱 프로세스에 얼마나 접근하는지 |

### N. 이름 있는 객체와 명명된 파이프 (2026-11-26 추가)

G4·G5는 병렬 빌드 성공 여부와 호스트가 만든 파이프 읽기·쓰기만 봤습니다. 이 절은 이벤트·뮤텍스·세마포어·section(공유 메모리) 같은 이름 있는 객체와, 샌드박스가 만든 명명된 파이프를 측정합니다.

- **이름.** 모든 객체와 파이프는 측정용 이름(`iso-nq-…`)만 씁니다. 실제 프로그램이 쓰는 이름은 쓰지 않습니다.
- **가장.** 파이프 서버에서 클라이언트를 가장(`ImpersonateNamedPipeClient`)하지 않습니다. 알려진 우회의 재현은 제외한다는 조건 때문이며, 대신 A의 특권 목록(`SeChangeNotifyPrivilege`만)을 근거로 둡니다.
- **호스트 쪽 동작.** 네 구성 모두 승격되지 않은 별도 호스트 프로세스가 맡습니다. QwenPaw 관리자 측정이 UAC 세션에서 돌아도 호스트 쪽 토큰은 같습니다.
- **PC에 남는 것.** 이름 있는 객체와 파이프는 마지막 핸들이 닫히면 사라집니다. 측정이 PC에 남기는 것은 시험 폴더와 제품이 만드는 항목(2.1·H)뿐입니다.

| 번호 | 측정 | 방법 | 예상 | 왜 보나 |
| --- | --- | --- | --- | --- |
| N0 | 이름 공간 디렉터리(기준 자료) | 호스트에서 `\BaseNamedObjects`(`Global\`), `\Sessions\<n>\BaseNamedObjects`(`Local\`)의 DACL을 읽기 전용으로 조회. 샌드박스에서 두 디렉터리와 각 `Restricted` 하위 디렉터리를 조회·탐색·객체 생성 권한으로 열기만 함 | `Local\`의 객체 생성 권한은 사용자 SID, 사용자 로그온 SID, Administrators, SYSTEM에만 있음(2026-11-26 호스트 조회). `Global\`은 Everyone이 만들 수 있음 | N1~N4 결과의 해석 근거 |
| N1 | 호스트가 `Local\`에 만든 객체 | 호스트가 보안 설명자 없이 이벤트·뮤텍스·세마포어·section을 만듦. 샌드박스가 읽기 성격 권한(`SYNCHRONIZE`, `FILE_MAP_READ`), 쓰기 성격 권한(`EVENT_MODIFY_STATE`, `SEMAPHORE_MODIFY_STATE`, `FILE_MAP_WRITE`), `WRITE_DAC`, `READ_CONTROL`로 각각 열고 닫음. 열리면 이벤트 신호, 세마포어 해제, 뮤텍스 획득 후 해제, section에 시험 문자열 쓰기를 하고 호스트가 반영됐는지 확인 | `Local\` 객체는 디렉터리에서 사용자 로그온 SID의 `GENERIC_ALL` ACE를 상속함. 로그온 SID를 공유하는 세 구성은 열고 조작함, QwenPaw 관리자는 거부 | 호스트 프로그램의 공유 메모리·동기화 객체를 읽거나 바꿀 수 있는지 |
| N2 | 호스트가 `Global\`에 만든 객체 | N1과 같음. section은 승격되지 않은 호스트가 `Global\`에 만들지 못하면(`SeCreateGlobalPrivilege` 없음) 그 결과만 기록 | 상속 ACE가 없어 호스트 토큰의 기본 DACL을 따름 | 세션 전체 이름 공간의 차이 |
| N3 | 샌드박스가 만든 객체 | `ws-A` 샌드박스가 `Local\`·`Global\`에 이벤트와 section을 만들고 유지. 생성 결과, 실제 객체 경로, DACL을 기록. 호스트와 `ws-B` 샌드박스가 N1과 같은 권한으로 열기 | 로그온 SID를 공유하는 세 구성은 생성되고 호스트·다른 작업 폴더가 엶. QwenPaw 관리자는 생성 거부 또는 다른 디렉터리에 생성 | 샌드박스끼리, 샌드박스와 호스트 사이의 객체 공유 |
| N4 | 객체 이름 선점 | N3에서 샌드박스가 만든 이름으로 호스트가 같은 종류 객체를 만듦. 새로 만들어지는지, `ERROR_ALREADY_EXISTS`로 샌드박스 객체를 받는지(이벤트 신호 상태·section 내용으로 확인), 거부되는지 기록 | N3 결과에 따름 | 호스트 프로그램이 샌드박스가 먼저 만든 객체를 쓰게 되는지 |
| Q1 | 병렬 빌드 실패 단계 | Python `multiprocessing.connection.Pipe`가 하는 호출을 단계별로 실행: 서버 생성(`CreateNamedPipe`, 첫 인스턴스 플래그), 클라이언트 열기(`CreateFile`), `SetNamedPipeHandleState`. 양방향·단방향 각각, 첫 인스턴스 플래그 없는 서버와 클라이언트 권한별 열기도 기록. 만든 파이프의 DACL 기록. 같은 실행에서 G4 병렬 빌드 반복 | 2026-11-24·25에 QwenPaw 비관리자와 Codex `unelevated`만 실패. 어느 단계인지 확인 | G4 실패 원인 확인 |
| Q2 | 샌드박스가 만든 명명된 파이프 | `ws-A` 샌드박스가 보안 설명자 없이 파이프 서버를 만들고 유지. 호스트와 `ws-B` 샌드박스가 읽기·쓰기·`READ_CONTROL`로 연결하고, 쓰기 연결은 시험 문자열을 보냄. 샌드박스 서버가 받은 연결과 문자열을 기록 | 파이프 DACL은 샌드박스 토큰의 기본 DACL을 따름. QwenPaw 비관리자는 Everyone 모든 권한, Codex는 로그온 SID 모든 권한 | 샌드박스가 연 파이프로 호스트·다른 샌드박스가 데이터를 보낼 수 있는지 |
| Q3 | 파이프 이름 선점 | Q2의 이름으로 호스트가 파이프 서버를 만듦. 첫 인스턴스 플래그(`FILE_FLAG_FIRST_PIPE_INSTANCE`) 있음·없음 각각 | 플래그가 있으면 거부. 없으면 Q2 파이프 DACL에 따름 | 호스트 프로그램이 같은 이름의 서버를 열 때 샌드박스 서버와 섞이는지 |

진행: 일반 세션에서 QwenPaw 비관리자, Codex 두 구성을 측정하고, QwenPaw 관리자는 사용자가 UAC를 승인한 세션에서 측정합니다. 구성마다 5회입니다. 측정 전후 상태는 3장의 스크립트로 기록합니다. 시험 폴더는 이번 측정에 필요한 것(`tools`, 구성별 `ws-A`·`ws-B`, `qwenpaw-profile`)만 다시 만들고 측정 후 지웁니다.

### T. 실제 도구: Node와 Git Bash (2026-11-26 추가)

N·Q는 측정용 호출로 얻은 결과입니다. 이 절은 에이전트가 실제로 실행하는 Node와 Git Bash가 같은 조건에서 동작하는지 봅니다. 도구는 이 PC에 설치된 것(Node v24.15.0, Git for Windows)을 그대로 쓰고, 샌드박스 안 측정 프로그램이 각 명령을 실행해 종료 코드와 출력을 기록합니다. 네트워크와 `npm install`은 쓰지 않습니다. 같은 명령을 승격되지 않은 호스트에서도 5회 실행해 대조군으로 둡니다.

| 번호 | 측정 | 명령 | 예상 | 왜 보나 |
| --- | --- | --- | --- | --- |
| T1 | Node 단순 실행 | `node -e`에 해당하는 측정 스크립트 | 네 구성 모두 성공 | 대조 |
| T2 | Node 자식 프로세스 | `spawnSync`(stdio `pipe`, `inherit`), 비동기 `spawn`, `execSync`(cmd 경유) | 비관리자 두 구성은 stdio `pipe`가 실패할 가능성(Node가 자식 표준 입출력에 명명된 파이프를 씀, Q1과 같은 형태) | `npm run`, 테스트 실행기, 빌드 도구가 자식 프로세스를 이 방식으로 띄움 |
| T3 | Node IPC와 작업자 | `fork` 메시지 왕복, `worker_threads` | `fork`는 T2와 같은 경향, `worker_threads`는 파이프를 쓰지 않아 성공 | 테스트 실행기의 작업자 프로세스 |
| T4 | Node 명명된 파이프 서버 | `net.createServer`로 측정용 이름의 파이프를 열고 같은 프로세스에서 연결해 데이터 전송 | 비관리자 두 구성은 연결 실패 가능성 | 언어 서버·개발 도구의 로컬 IPC |
| T5 | Git Bash | `usr\bin\bash.exe`로 `echo`, 파이프라인, 명령 치환, 백그라운드 실행 후 `wait`. `bin\bash.exe`(실행기)로 `echo` | QwenPaw 비관리자는 시작 실패(2026-11-24). 나머지는 측정 | Hermes Agent의 Windows 로컬 터미널이 Git Bash를 씀. QwenPaw도 `SHELL`에 따라 고름 |
| T6 | Git | `git --version`, 시험 저장소의 `git --no-optional-locks status --porcelain` | 별도 계정 구성은 저장소 소유자 검사(`safe.directory`)와 `~/.gitconfig` 읽기에 따라 다름 | 에이전트가 가장 자주 실행하는 명령 |

시험 저장소와 Node 측정 스크립트는 일반 세션에서 미리 만들어, 네 구성 모두 같은 소유자·DACL로 시작합니다. 실패하면 도구가 출력한 오류만 기록하고, 어느 객체나 파이프에서 막혔는지는 N·Q 결과와 맞춰 추정합니다.

### R. 다른 계정의 레지스트리와 샌드박스 계정 상태

| 번호 | 측정 | 방법 | 예상 | 왜 보나 |
| --- | --- | --- | --- | --- |
| R1 | 사용자 레지스트리 읽기(관리자 두 구성) | 샌드박스에서 `HKEY_USERS\<사용자 SID>\Software`, `HKEY_USERS\<사용자 SID>\Environment`를 읽기 권한으로 열기만 함(값은 읽지 않음). 구성마다 5회 | 거부(사용자 레지스트리 DACL에 샌드박스 계정 없음) | 별도 계정 방식이 사용자 레지스트리 노출을 실제로 막는지. 비관리자 두 구성은 `HKCU`를 그대로 읽음(QwenPaw 실측) |
| R2 | 다른 계정의 레지스트리 열기(네 구성) | 샌드박스에서 `HKEY_USERS` 아래 키 이름을 나열하고, 자기 계정이 아닌 하이브를 읽기 권한으로 열기만 함. 분류는 사용자, 다른 샌드박스 계정, 시스템·서비스 계정, `.DEFAULT`, `<SID>_Classes`, 기타(이 PC의 다른 로컬·도메인 프로필과 다른 제품 계정). SID 대신 분류만 기록 | 키 이름 나열은 가능. 비관리자 두 구성은 사용자 자신의 하이브만 열리고 샌드박스 계정 하이브는 거부. 관리자 두 구성은 자기 샌드박스 계정 하이브만 열림. `.DEFAULT`처럼 Users에 읽기를 허용하는 하이브는 열림 | 다른 계정의 설정·저장 값 노출 |
| R3 | 샌드박스 계정 상태의 작업 폴더 간 공유(관리자 두 구성) | (1) `ws-A`와 `ws-B`의 명령에서 `HKCU`가 같은 계정의 것인지, 쓰기 권한으로 열리는지 확인(값은 쓰지 않음). (2) `ws-A` 명령이 샌드박스 계정 프로필 안에 시험 파일을 만들고, `ws-B` 명령에서 보이는지 확인한 뒤 샌드박스 명령이 직접 삭제하고 다음 실행에서 삭제를 확인 | Codex `elevated`는 모든 작업 폴더가 같은 고정 계정을 쓰므로 같은 `HKCU`이고 파일도 보임. QwenPaw 관리자는 작업 폴더마다 계정이 달라 보이지 않음 | 한 작업의 명령이 남긴 설정(PowerShell 프로필 등)이 다른 작업의 명령에 영향을 줄 수 있는지 |
| R4 | 컴퓨터 전체 레지스트리와 관리자 전용 키 | 호스트에서 읽기 전용으로 DACL을 조회해 Administrators·SYSTEM만 허용하는 기존 키 1개를 고름(보안 하이브 `HKLM\SAM`·`HKLM\SECURITY`는 제외). 샌드박스에서 그 키를 읽기 권한으로, `HKLM\SOFTWARE`를 쓰기 권한(`KEY_SET_VALUE`, `KEY_CREATE_SUB_KEY`)으로 열기만 함. 구성당 1회 | 네 구성 모두 거부(비관리자 두 구성은 사용자 토큰에서 Administrators가 거부 전용, 관리자 두 구성은 샌드박스 계정이 관리자 그룹이 아님). QwenPaw 관리자는 부모가 관리자여도 자식은 샌드박스 계정 토큰이라 거부 | 관리자 전용 키와 컴퓨터 전체 설정이 보호되는지 |
| R5 | 쓰기가 허용된 레지스트리 키(B3의 레지스트리판) | 7장 결정 대기. 추천안: 측정 스크립트가 `HKCU\Software\agent-isolation-test` 아래에 DACL을 고정한 시험 키 세 개(Everyone 쓰기, 로그온 SID 쓰기, Users 쓰기)를 만들고, 샌드박스에서 쓰기 권한으로 열기만 함. 측정 후 시험 키 삭제 | Everyone·로그온 SID 쓰기 키는 비관리자 두 구성에서 열림. Users 쓰기 키는 두 번째 검사에서 거부. 관리자 두 구성은 사용자 `HKCU`가 아니라 측정 대상이 아님(R1·R2로 확인) | 폴더에서 확인한 "Everyone 쓰기 허용 위치에는 쓸 수 있다"가 레지스트리에도 있는지 |

R2 실행 순서: 다른 샌드박스 계정의 하이브는 그 구성의 프로세스가 실행 중일 때만 로드됩니다. 그래서 관리자 구성에서 대기하는 자식(수명 제한 있음)을 띄워 둔 뒤, 호스트에서 그 하이브가 로드된 것을 확인하고(허용 상태 확인), 승격되지 않은 별도 측정 프로세스가 비관리자 구성의 샌드박스에서 R2를 실행합니다. 조합은 "QwenPaw 관리자 실행 중 × 비관리자 두 구성", "Codex `elevated` 실행 중 × 비관리자 두 구성"이며 각각 5회입니다.

### 측정하지 않는 것

- **제품의 승인 흐름.** Codex는 언어 모델 세션이 필요하고, 이번 비교 대상은 백엔드입니다. QwenPaw 승인 흐름은 run 07에서 측정했습니다.
- **Codex의 제품 시간 초과.** `codex sandbox` 명령에는 시간 제한이 없습니다(`timeout_ms: None`). 에이전트 경로의 시간 초과 처리는 소스 기준으로만 적습니다. [`codex sandbox` 실행 설정](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/cli/src/debug_sandbox.rs#L512-L531)
- **Codex `elevated`의 로컬 연결 허용 조건과 최초 설치 시간.** 둘 다 설치 단계를 다시 실행해야 하고, 그러면 실제 샌드박스 계정의 비밀번호가 바뀌기 때문입니다. 최초 설치 시간은 시험용 PC나 가상 머신에서 따로 잽니다.
- **QwenPaw 기본 `deny_paths`의 실제 폴더 적용.** QwenPaw 에이전트 경로는 기본으로 `~/.ssh` 등에 거부 ACE를 붙입니다. 실제 폴더의 DACL을 바꾸게 되므로 측정용 경로(`targets\deny-read`)로만 확인하고, 실제 폴더 적용은 소스 기준으로 적습니다.
- **사용자 권한으로 동작하는 시스템 서비스를 통한 간접 실행·쓰기.** Restricted Token은 사용자 신원을 유지하므로, 작업 스케줄러·COM·WMI처럼 사용자 대신 동작하는 서비스에 요청하는 경로는 파일 DACL 검사 밖에 있습니다. 재현하지 않으며, 보고서에 이 방식의 한계로 문헌 기준으로만 적습니다.
- **네트워크 차단(D)과 클립보드 접근.** 2026-11-25 결정에 따라 제외합니다. 이유는 D와 F 절에 적었습니다.
- **`Start-Process`로 URL을 여는 경로.** 2026-11-25 결정에 따라 제외합니다.
- **다른 사용자 세션 접근, 입력 주입.** 이전과 같은 이유로 제외합니다.
