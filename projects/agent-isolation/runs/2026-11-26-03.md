# 실행 2026-11-26-03 — 개별 계정 Restricted Token에서 제한 SID 목록 줄이기

## 실행 조건

다른 Claude 세션이 요청한 측정입니다.

- **비교 대상.** 제한 SID 목록을 「승인용 SID + 샌드박스 계정」으로 줄였을 때, 셸·도구가 동작하는지와 2026-11-25에 확인한 구멍이 닫히는지 비교했습니다. 기준은 Codex `elevated` 목록입니다.
- **측정 조건.**
  - 셸은 별도 데스크톱 없이 사용자 데스크톱(`WinSta0\Default`)에서 실행합니다.
  - 쓰기 허용은 승인용 capability SID ACE로, 읽기 허용은 샌드박스 그룹 읽기 ACE로 줍니다.
- **일시와 환경.** 2026-11-26 03:01–04:17 KST. Windows 11 Pro 25H2 빌드 26200, 도메인에 가입된 실제 사용 PC입니다(2026-11-25와 같음).
- **시험 실행기.** Codex 제품 바이너리로는 제한 SID 목록을 바꿀 수 없어서, 같은 호출 구조의 시험 실행기를 만들었습니다.

- `LUA_TOKEN`은 관리자 그룹이 없는 표준 사용자 계정이라 영향이 없습니다.
- **측정용 계정.** UAC 단계에서 표준 사용자 `iso-rt-sbx1`·`iso-rt-sbx2`와 그룹 `iso-rt-sbx-users`를 만들고, 측정 뒤 지웠습니다. 로그온 플래그가 0이라 프로필은 만들어지지 않고, `HKCU`는 `.DEFAULT`를 가리켰습니다.
- **실행기 토큰.** 그룹 목록에 사용자 로그온 SID가 들어 있었습니다. `CreateProcessWithLogonW`가 호출자의 로그온 SID를 새 토큰에 넣는다는 2026-11-25 관찰과 같습니다.

- **시험 폴더.** `C:\agent-isolation-test`를 새로 만들고 측정 뒤 지웠습니다.
  - `rt` 아래 폴더는 상속을 끊고 사용자·SYSTEM·Administrators만 둔 뒤, 그룹 읽기 ACE를 상속되게 붙였습니다.
  - `ws-A`(작업 폴더, Node 측정 스크립트, 사용자 소유 시험 저장소): capability SID와 그룹의 수정 ACE. Codex `elevated`가 쓰기 경로에 붙이는 조합입니다.
  - `ws-cap`(capability SID만), `ws-grp`(그룹만), `ws-acct`(계정만): 쓰기 ACE 대상 비교용입니다.
  - `targets\everyone-write`·`logon-write`·`user-only`와 `HKCU\Software\agent-isolation-rt`의 같은 이름 키 세 개(2026-11-25 R5와 같은 DACL)를 두었습니다.
  - capability SID는 Codex 형식(`S-1-5-21-a-b-c-d`)의 무작위 값입니다.
  - 이 SID의 ACE는 Win32 API로 붙였습니다. `icacls`는 SID를 먼저 찾으려다 이 PC의 도메인 트러스트 오류로 실패했습니다(2026-11-25 QwenPaw와 같은 원인).
- **환경 변수.** 사용자의 기본 환경 블록(`CreateEnvironmentBlock`)에서 `TEMP`·`TMP`만 시험 폴더(`rt\temp`, capability SID·그룹 수정 ACE)로 바꿨습니다. Codex처럼 `USERPROFILE` 등은 사용자 값 그대로입니다.
- **회차.** 구성마다 5회이고, 회차마다 실행기를 세 번 시작했습니다.
  1. 본 단계: PowerShell 두 번, cmd 두 번, 샌드박스 안 측정 프로그램 한 번
  2. 창 단계: PowerShell에서 메모장 시작, 측정 프로그램의 시험 창
  3. 선점 단계: 샌드박스가 `Local\` 객체를 만들고 대기하는 동안 호스트가 같은 이름으로 생성

## 2. 해석

### 셸이 시작되는가

축소 목록에서는 PowerShell·cmd·Python이 모두 DLL 초기화 단계에서 실패했습니다(`0xC0000142`, 5/5). 대상별로 권한을 하나씩 붙여 보니 원인은 세 가지였습니다. 모두 「사용자 로그온 SID나 Everyone에만 쓰기 계열 권한을 주는 객체」이고, 제한 SID 목록에서 이 둘을 빼면 두 번째 검사를 통과하지 못합니다.

1. **토큰 기본 DACL(콘솔 호스트).** 기본 DACL에 계정 SID를 넣으면 cmd가 시작했습니다.
   - Codex 기본 DACL은 로그온 SID에만 모든 권한을 줍니다. 그래서 셸이 새로 만드는 자기 객체(프로세스·스레드, 숨은 콘솔의 `conhost`)에 계정이 쓰기 계열 권한을 얻지 못합니다.
   - 사전 점검에서는 콘솔 없이(`DETACHED_PROCESS`) 시작하면 기본 DACL을 바꾸지 않아도 cmd가 시작했습니다. 그래서 콘솔 호스트가 이 객체에 접근하는 단계에서 막힌 것으로 추정합니다.
2. **창 스테이션과 데스크톱.** `WinSta0`과 `Default`의 DACL은 사용자 로그온 SID에 모든 권한을 줍니다. user32를 쓰는 프로그램(PowerShell, 사전 점검의 `whoami`·Node)은 여기에 계정 ACE를 붙여야 이 단계를 넘었습니다. 데스크톱 ACE를 붙인 구성에서는 측정 프로그램의 시험 창이 사용자 데스크톱에 보였습니다.
3. **장치 `\Device\CNG`·`\Device\KsecDD`·`\Device\Null`.** 세 장치의 DACL은 쓰기를 Everyone·SYSTEM·Administrators·ALL APPLICATION PACKAGES에만 주고, RESTRICTED에는 읽기만 줍니다.
   - 계정 ACE를 붙이자 Python이 시작했습니다. Python과 사전 점검의 `certutil`은 `bcrypt.dll`을 직접 씁니다.
   - 같은 ACE로 cmd의 `>nul`·`2>nul`과 Python `subprocess.DEVNULL`도 동작했습니다.
   - 세 장치 중 어느 것이 Python 시작에 필요한지는 나누어 재지 않았습니다.

세 가지를 모두 붙여도 PowerShell 5.1은 `Starting the CLR failed with HRESULT 80070005`로 끝났습니다(5/5). `Local\` ACE를 더해도 같았습니다. 전역 `\BaseNamedObjects`와 MSYS2 디렉터리 ACE를 더해도 같았습니다.

### 셋 다 붙여도 남는 실패

- **명명된 파이프 생성.** `CreateNamedPipe`가 거부(5)됐습니다. 그래서 다음이 모두 실패했습니다.
  - Python 다중 프로세스 병렬(G4)과 `multiprocessing.connection.Pipe()`
  - Node의 stdio `pipe` 자식 프로세스(`spawnSync`·`spawn`·`execSync`·`fork`): 25초 제한까지 응답 없음
  - Node `net` 파이프 서버: `EADDRINUSE`로 보고됨
  - 2026-11-26-01의 비관리자 구성은 파이프를 만들고 연결에서 막혔는데, 축소 목록은 생성부터 막힙니다. 파이프 루트(`\\.\pipe\`)의 보안 설명자는 조회 자체가 `ERROR_INVALID_PARAMETER`로 막혀, 원래 상태로 복원할 수 없으니 ACE 시험은 하지 않았습니다. 생성 권한이 Everyone 쪽에만 있다고 추정합니다.
- **Git Bash.** `NtCreateDirectoryObject(\BaseNamedObjects\msys-2.0S5-…)`가 `0xC0000022`로 거부돼 시작하지 못했습니다. MSYS2는 전역 이름 공간에 자기 디렉터리를 만듭니다. 전역 `\BaseNamedObjects`는 객체·하위 디렉터리 만들기를 Everyone에게 줍니다. 
  - 전역 `\BaseNamedObjects`에 계정 ACE를 붙여도(추가 UAC 단계) 같은 오류였습니다(5/5).
  - MSYS2 디렉터리는 이 PC에서 먼저 시작한 Git Bash(이 측정을 돌린 세션의 Git Bash)가 이미 만들어 둔 것이었습니다. 소유자는 사용자이고 DACL은 Everyone에게만 권한을 줍니다(`D:(A;;CCDCLCSWRC;;;WD)`). 같은 설치의 Git Bash는 모두 이 디렉터리를 엽니다.
  - 이 디렉터리에 계정 ACE를 붙이자 그 단계는 넘었지만, 다음 단계인 신호용 명명된 파이프 생성에서 `couldn't create signal pipe, Win32 error 5`로 실패했습니다(5/5).
  - 결국 Git Bash는 명명된 파이프 생성이 막히는 한 동작하지 않습니다.
- **이름 있는 객체.** `Local\`·`Global\` 이벤트·뮤텍스·section 만들기가 모두 거부(5)됐습니다.
  - 세션 `BaseNamedObjects`에 계정 ACE를 붙이면 `Local\` 생성이, 전역 `\BaseNamedObjects`에 붙이면 `Global\` 생성이 됐습니다.
  - 대신 샌드박스가 호스트보다 먼저 같은 이름을 만드는 선점이 다시 가능해졌습니다(5/5).
- **`git status`.** 사용자 소유 저장소는 `safe.directory` 없이는 거부됐습니다(기준 구성도 같음).
  - Codex처럼 `GIT_CONFIG_*` 환경 변수로 `safe.directory`를 넣으면 `fatal: unknown error occurred while reading the configuration files`로 실패했습니다. 측정용 계정이 사용자 `~/.gitconfig`를 읽지 못하기 때문입니다.
  - `HOME`을 계정이 읽을 수 있는 폴더로 바꾸면 성공했습니다.
  - 2026-11-25에 Codex `elevated`가 성공한 것은, 프로필 아래 항목마다 붙은 `CodexSandboxUsers` 읽기 ACE로 `.gitconfig`를 읽을 수 있었기 때문으로 봅니다.

### 구멍이 닫히는가

셸이 시작되는 「축소+셋 다」 구성에서 확인했습니다.

| 구멍 | 기준 | 축소+셋 다 | 이유 |
| --- | --- | --- | --- |
| Everyone·사용자 로그온 SID에 쓰기를 준 폴더와 `HKCU` 키 | 씀 | **거부** | 두 번째 검사에 Everyone·로그온 SID가 없음 |
| 호스트가 `Local\`에 만든 객체를 쓰기 권한으로 열기 | 열고 조작함 | **거부**(읽기 권한 열기도 거부) | 이름 있는 객체 함수가 세션 디렉터리를 여는 단계에서 실패(2026-11-26-01의 QwenPaw 관리자와 같은 모양) |
| 같은 이름 선점 | 호스트가 샌드박스 객체를 받음 | **막힘**(샌드박스가 만들지 못함). `Local\` ACE를 붙이면 다시 가능 | 위와 같음 |
| explorer를 `VM_READ`·`TERMINATE`로 열기 | 열림 | **열림** | 첫 번째 검사만 적용되는 권한이고, 그룹 목록에 사용자 로그온 SID가 남음 |
| explorer의 토큰을 `TOKEN_DUPLICATE`·`TOKEN_IMPERSONATE`로 열기(열기만) | 열림 | **열림** | 같음 |
| 로그온 SID ACE가 없는 사용자 프로세스 | 거부 | 거부 | 계정이 DACL에 없음 |
| 자기 실행기를 `VM_WRITE`·`CREATE_THREAD` 등 모든 권한으로 열기 | 열림 | **열림** | 실행기 프로세스 DACL이 계정에 모든 권한을 주고, 계정이 제한 SID 목록에 남음 |

- 축소 목록이 닫는 것은 두 번째 검사(쓰기 계열 권한)로 막히는 구멍입니다.
- 첫 번째 검사만 받는 읽기·종료·토큰 열기는 그룹 목록에 사용자 로그온 SID가 있는 한 그대로입니다. 이 SID는 `CreateProcessWithLogonW`가 넣습니다.
- 실행기 노출은 계정 SID가 제한 SID 목록에 있는 한 그대로입니다.

### 쓰기 ACE를 어디에 붙여야 하는가

| 폴더의 쓰기 ACE | 기준·축소+셋 다 결과 | 이유 |
| --- | --- | --- |
| capability SID + 그룹 | 씀 | 첫 번째 검사는 그룹, 두 번째 검사는 capability SID로 통과 |
| capability SID만 | 거부 | 첫 번째 검사(일반 그룹 목록)에 capability SID가 없음 |
| 그룹만 | 거부 | 두 번째 검사(제한 SID 목록)에 그룹이 없음 |
| 계정만 | 씀 | 계정 SID가 두 목록에 모두 있음 |

- 요청 조건의 「쓰기 허용은 승인용 SID ACE로」만으로는 쓸 수 없고, 그룹(또는 계정) 쓰기 ACE가 함께 있어야 합니다. Codex `elevated`도 쓰기 경로에 그룹 ACE를 같이 붙입니다.
- 같은 이유로, 장치·데스크톱처럼 두 번째 검사에서 막히는 대상은 그룹 ACE로는 풀리지 않습니다. 이번 측정의 보충 ACE는 모두 계정 SID로 붙였습니다.
- 계정 ACE는 그 계정의 모든 샌드박스 실행(모든 작업 폴더)에 같은 권한을 줍니다.

### 그 밖의 관찰

- **메모장 창.** 기준 구성에서 PowerShell로 띄운 메모장 창이 사용자 데스크톱에 보였습니다(5/5). 축소 구성들에서는 PowerShell이 시작하지 못해 재지 못했습니다.
- **PowerShell `> NUL`.** 샌드박스와 상관없이 호스트 대조군에서도 `NotSupportedException`이었습니다(.NET `FileStream`이 장치를 열지 않음). `> $null`과 `Out-Null`은 기준과 대조군에서 동작했습니다.
- **실행 시간.** 「축소+셋 다」의 본 단계는 약 100초였습니다. 응답하지 않는 Node 사례 4개가 각각 25초 제한까지 기다렸기 때문입니다. 기준은 약 9초였습니다.

## 4. 한계

- PC 한 대, 측정용 계정 두 개로 쟀습니다.
- 셸은 PowerShell 5.1·cmd, 도구는 이 PC의 Node v24.15.0·Git for Windows 2.54.0입니다. PowerShell 7, `npm`, 실제 테스트 실행기는 재지 않았습니다.
- 축소 목록에서 PowerShell이 CLR 시작에 실패하는 원인은 확인하지 못했습니다. 데스크톱·기본 DACL·장치·`Local\`·전역 이름 공간·MSYS2 디렉터리 ACE로는 풀리지 않았습니다. 명명된 파이프 생성이나 다른 「Everyone에만 쓰기를 주는 객체」일 가능성이 있다고 추정합니다.
- 명명된 파이프 생성은 파이프 루트의 보안 설명자를 조회할 수 없어 대상 ACE를 시험하지 않았습니다.
- 장치와 전역 이름 공간에 붙인 계정 ACE는 컴퓨터 전체 객체의 DACL 변경입니다. 실제 제품에서는 설치 단계(관리자)가 계정마다 붙이고 유지해야 하며, 재부팅하면 사라지므로 다시 붙이는 과정도 필요합니다. 이번 측정에서는 메모리에서만 바꾸고 정리 때 복원했습니다.
- 다른 프로세스는 열기만 했습니다. 메모리 읽기·쓰기, 주입, 토큰 사용은 시험하지 않았습니다.
- 측정용 계정의 프로필은 만들지 않았습니다(Codex와 같은 로그온 플래그 0).
