### 무효로 한 회차

다음 두 번의 실행은 측정 도구 문제로 무효로 하고, 원본만 `run1/`·`run2-invalid/`에 보관했습니다.

1. **첫 실행(00:56–01:09).** bash를 `--noprofile`로 실행해 호출한 쪽의 PATH를 그대로 썼습니다.
   - 일반 세션 측정은 Git Bash에서 시작해 PATH에 `/usr/bin`이 있었습니다. UAC 배치는 cmd에서 시작해 PATH에 `/usr/bin`이 없었습니다.
   - 그래서 QwenPaw 관리자에서만 `cat`을 찾지 못했고(127), 백그라운드 `sleep`도 실행되지 않았습니다.
2. **두 번째 실행(01:12–01:13).** bash 명령 앞에 `PATH=/usr/bin:$PATH`를 붙였는데, 측정 프로그램이 인자에 Python `expandvars`를 적용해 `$PATH`를 Windows PATH로 바꿨습니다. 호스트 대조군을 포함해 bash 명령이 구문 오류(2)로 끝났습니다.

인자를 그대로 넘기도록 고친 뒤 네 구성과 대조군을 다시 측정했습니다(01:14–01:23). 아래 결과는 이 측정입니다. 첫 실행의 결과도 무효 항목을 빼면 같았습니다.

## 2. 해석

**Node(비관리자 두 구성).**
- 자식 프로세스의 표준 입출력을 파이프로 연결하는 모든 방식(`spawnSync`, `spawn`, `execSync`, `fork`)이 `EPERM`으로 실패했습니다. 표준 입출력을 물려주는 `inherit`와, 파이프를 쓰지 않는 `worker_threads`는 성공했습니다.
- Node가 만든 명명된 파이프 서버에는 같은 프로세스도 연결하지 못했습니다.
- 두 결과 모두 [2026-11-26-01 Q1](2026-11-26-01.md#q1-병렬-빌드-실패-단계)과 같은 형태입니다. 보안 설명자 없이 만든 명명된 파이프는 소유자(사용자 SID)에게만 쓰기를 주고, 두 구성의 제한 SID 목록에는 사용자 SID가 없습니다.
- Node(libuv)가 자식 표준 입출력에 명명된 파이프를 쓴다는 점과 이 결과를 맞춰 본 추정입니다. libuv 소스는 확인하지 않았습니다.
- 영향: `npm run`, 테스트 실행기의 작업자 프로세스, 빌드 도구처럼 Node가 자식 프로세스를 파이프로 띄우는 작업은 이 두 구성에서 실패할 것으로 봅니다. 실제 `npm`·테스트 실행기는 측정하지 않았습니다.

**Git Bash(비관리자 두 구성).**
- Git Bash의 런타임(MSYS2)이 시작할 때 만드는 사용자별 공유 메모리(이름이 사용자 SID로 시작하는 section)에서 거부되어, 어떤 명령도 실행되지 않았습니다. 2026-11-24에 QwenPaw 비관리자에서 본 것([2026-11-24-07](2026-11-24-07.md#git-bash가-셸로-잡힌-경우-각-5회))과 같은 오류이며, Codex `unelevated`도 같았습니다.
- 별도 계정 두 구성에서는 성공했습니다. 그래서 파이프와 같은 원인으로 추정합니다. 이 공유 메모리가 사용자 SID에만 쓰기를 주는 보안 설명자로 만들어지고, 제한 SID 목록에 사용자 SID가 없어 쓰기 검사에서 거부됐다는 것입니다. MSYS2 소스는 확인하지 않았습니다.

**QwenPaw 관리자의 Git Bash.**
- [2026-11-26-01](2026-11-26-01.md#qwenpaw-관리자의-이름-있는-객체-호출)에서 이 구성은 Windows API(kernel32)의 이름 있는 객체 함수가 모두 실패했습니다. 그런데 Git Bash는 공유 메모리를 만들고 파이프라인까지 실행했습니다.
- 따라서 이 구성에서 실패하는 것은 kernel32 함수로 이름 있는 객체를 만드는 프로그램이고, 이름 있는 객체를 쓰는 프로그램 전부는 아닙니다. MSYS2가 다른 경로로 객체를 만드는 것으로 보입니다(추정).

**Git의 저장소 소유자 검사(별도 계정 두 구성).**
- QwenPaw 관리자는 사용자 소유 저장소에서 `git status`가 거부됐습니다(5/5). Git은 현재 계정이 저장소 소유자가 아니면 `safe.directory`에 등록된 경우에만 동작하기 때문입니다.
- Codex `elevated`는 같은 조건에서 성공했습니다. Codex가 elevated 실행 때 작업 폴더의 Git 루트와 그 아래를 `GIT_CONFIG_COUNT`·`GIT_CONFIG_KEY_n`·`GIT_CONFIG_VALUE_n` 환경 변수로 `safe.directory`에 넣기 때문입니다. [`inject_git_safe_directory`](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/windows-sandbox-rs/src/sandbox_utils.rs#L36-L54) · [elevated 실행 경로의 호출](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/windows-sandbox-rs/src/elevated_impl.rs#L136)
- 이번 측정에서는 작업 폴더(`ws-A`)에 측정용 `.git` 폴더가 있어서, Codex가 `ws-A`를 Git 루트로 보고 그 아래의 `repo`까지 등록했습니다.

## 4. 측정하지 않은 것과 한계

- 실제 `npm` 명령, 테스트 실행기, 빌드 도구는 실행하지 않았습니다. Node 내장 함수 호출로만 측정했습니다.
- Git Bash는 `--noprofile --norc`로 실행했습니다. 로그인 셸 초기화(`/etc/profile`)는 측정하지 않았습니다.
- 실패 원인 가운데 Node(libuv)와 MSYS2 내부 동작은 소스로 확인하지 않은 추정입니다.
- Codex `elevated`의 `safe.directory` 처리는 작업 폴더에서 찾은 Git 루트 기준입니다. 작업 폴더 밖의 저장소는 측정하지 않았습니다.
