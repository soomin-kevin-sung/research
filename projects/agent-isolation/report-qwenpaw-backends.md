# QwenPaw Windows 샌드박스 실측 보고서: Restricted Token과 AppContainer

QwenPaw `2.3.0.post1`은 Windows의 두 격리 방식인 Restricted Token과 AppContainer를 샌드박스 백엔드로 제공합니다. 이 보고서는 두 방식이 실제로 무엇을 막고 무엇을 막지 못하는지 측정한 결과입니다.

- 측정은 2026-11-23~24에 Windows 11 Pro 25H2(빌드 26200)의 관리자 권한 없는 계정에서 했습니다.
- [실측 프로토콜](protocol.md)의 ISO-01~18을 실행했고, 대부분의 조건은 5회 반복했습니다.

## 핵심 결론

**QwenPaw가 구성한 그대로라면 두 방식 모두 신뢰하지 않는 코드의 접근을 제한하는 보안 경계로 쓰기 어렵습니다.**
- Restricted Token은 작업 폴더 밖에 실수로 쓰는 일을 줄이는 정도입니다.
- AppContainer는 실제로 접근을 거부하지만, 개발 도구 실행이 많이 실패하고 실제 에이전트 경로에서는 선택되지 않습니다.

| 질문 | 답 |
| --- | --- |
| Restricted Token은 무엇을 막나? | 작업 폴더 밖 쓰기와 사용자 레지스트리 쓰기만 막습니다. 작업 폴더 밖 읽기, 네트워크, 클립보드, 환경 변수는 막지 못합니다. Everyone에게 쓰기를 열어 둔 폴더에는 쓰기도 됩니다. |
| AppContainer는 무엇을 막나? | 작업 폴더 밖 읽기·쓰기, 외부 네트워크, 호스트의 명명된 파이프, 사용자 레지스트리 쓰기를 Windows가 직접 거부합니다. 클립보드는 열립니다. |
| 작업 폴더 안의 일부 폴더만 잠글 수 있나? | 둘 다 안 됩니다. Restricted Token에는 기능이 없고, AppContainer는 설정해도 모든 권한이 열렸습니다. |
| 개발 작업은 되나? | Restricted Token은 대부분 됩니다. AppContainer에서는 사용자가 설치한 도구, cmd의 `dir`·`del`, 호스트와 주고받는 로컬 서버 연결이 실패합니다. Python 병렬 빌드는 둘 다 실패합니다. |
| 시간·자원 제한이 지켜지나? | 프로세스 수·메모리 한도는 둘 다 집행되지 않습니다. 셸이 끝난 뒤 남은 백그라운드 프로세스에는 시간 제한이 걸리지 않습니다. |
| 실제 에이전트는 어느 방식을 쓰나? | 기본 설정은 격리를 쓰지 않습니다. 켜면 관리자 권한이 없는 계정에서는 항상 Restricted Token을 씁니다. 차단된 명령도 사용자가 한 번 승인하면 격리 없이 실행되고, 그 승인은 세션 동안 유지됩니다. |

결과의 상당수는 Windows 기술 자체의 한계가 아니라 QwenPaw가 두 방식을 구성한 방법에서 나왔습니다. 그래서 다른 제품의 Restricted Token이나 AppContainer에는 그대로 적용되지 않습니다. [8장](#8-windows가-만든-결과와-qwenpaw가-만든-결과)에서 둘을 나눴습니다.

## 1. 측정 목적과 방법

### 목적

코딩 에이전트가 명령을 실행할 때 Windows의 두 격리 방식이 권한을 어디까지 제한하는지, 그 대가로 어떤 작업이 실패하는지 확인합니다.

- QwenPaw는 두 방식을 모두 일반 사용자 PC에서 켤 수 있어 측정 수단으로 썼습니다.
- [문헌·소스 조사 보고서](report.md)는 실제 차단 동작을 "측정 전"으로 남겼습니다. 이 보고서는 그중 QwenPaw 부분을 실측으로 확인합니다.

### 환경

| 항목 | 값 |
| --- | --- |
| 제품 | QwenPaw `2.3.0.post1`, 전용 Python 3.12.10 가상환경 |
| 운영체제 | Windows 11 Pro 25H2, 빌드 26200 |
| 계정 | 관리자 권한 없는 일반 사용자 |
| 셸 | `C:\Windows\System32\cmd.exe`. Git Bash는 별도로 관찰 |
| 기간 | 2026-11-23 ~ 2026-11-24 |

### 방법

- **두 경로.** ISO-01~14는 두 백엔드를 직접 호출해 측정했습니다. ISO-15~18은 에이전트가 실제로 거치는 도구 래퍼와 승인 서비스를 통해 측정했고, 승인 요청에는 사람 대신 측정 스크립트가 답했습니다.
- **합성 데이터.** 시험용 파일, 시험용 환경 변수, 직접 띄운 로컬 서버를 썼습니다. 차단을 판정하기 전에는 같은 대상이 허용 상태에서 정상 동작하는지 먼저 확인했습니다.
- **반복.** 대부분의 조건은 5회 반복했고 매회 새 샌드박스를 만들었습니다. 1회만 측정한 항목은 표에 따로 적었습니다.
- **실제 계정 보존.** 실제 계정 설정과 프로젝트 파일 권한은 바꾸지 않았습니다. 레지스트리와 클립보드는 해당 권한으로 열어 보기만 했고, 값과 내용은 읽지도 쓰지도 않았습니다. 측정 뒤에는 실제 QwenPaw 상태 폴더가 기준선과 같은지, AppContainer 프로필·등록과 시험 프로세스가 남지 않았는지 확인했습니다.
- **판정 용어.** 통과(기대와 일치), 실패(기대와 다름), 미지원(제품이 기능을 제공하지 않음), 미실측.

## 2. 두 방식의 원리와 QwenPaw 구성

Windows의 각 프로세스에는 액세스 토큰(이하 토큰)이 붙습니다. 토큰에는 사용자 SID, 그룹 SID, 특권, 무결성 수준이 들어 있습니다. SID(Security Identifier)는 사용자·그룹·로그온 세션 등을 식별하는 값입니다. 파일과 레지스트리 키에는 DACL(접근 허용·거부 목록)이 붙고, DACL의 각 항목인 ACE는 "이 SID에게 이 권한을 허용 또는 거부"를 뜻합니다. Windows는 접근할 때마다 토큰의 SID와 DACL을 비교합니다. 두 방식은 토큰을 제한하는 방법이 다릅니다.

| 구분 | Restricted Token | AppContainer |
| --- | --- | --- |
| 원리 | 현재 사용자의 토큰에 `CreateRestrictedToken`과 `WRITE_RESTRICTED`를 적용합니다. 읽기는 원래 토큰과 똑같이 검사하고, 쓰기만 제한 SID 목록으로 DACL을 한 번 더 검사합니다. | 토큰에 AppContainer SID(`S-1-15-2-…`)와 capability SID(`S-1-15-3-…`)를 넣고 무결성 수준을 Low로 낮춥니다. 읽기·쓰기 모두, 사용자 SID 검사와 별도로 DACL이 AppContainer SID, capability SID, `ALL APPLICATION PACKAGES` 중 하나에 접근을 허용해야 합니다. 네트워크는 `internetClient` 같은 네트워크 capability SID가 토큰에 있을 때만 쓸 수 있습니다. |
| 기본 원칙 | 기본 허용, 쓰기만 제한 | 기본 거부, 허용 ACE가 있는 곳만 접근 |
| QwenPaw 구성 | 제한 SID 목록은 무작위로 만든 capability SID(`S-1-5-21-…` 형식), 로그온 SID, Everyone입니다. 작업 폴더 DACL에 이 capability SID의 쓰기 허용 ACE를 추가합니다. 명령을 Job 객체(여러 프로세스를 묶어 관리하는 Windows 객체)에 넣지만 자원 한도는 설정하지 않습니다. | 작업 폴더 DACL에 AppContainer SID의 수정 허용 ACE를, QwenPaw를 실행한 Python 폴더에 읽기·실행 허용 ACE를 추가합니다. 네트워크를 허용하면 capability SID `internetClient`·`internetClientServer`·`privateNetworkClientServer`를 넣고, 차단하면 capability SID를 넣지 않습니다. Job 객체는 쓰지 않습니다. |
| QwenPaw가 고르는 조건 | `allow_read_all=True`(기본값), 관리자 아님 | `allow_read_all=False`, 관리자 아님 |

관리자 계정에서는 별도 저권한 계정과 Windows 방화벽 규칙을 쓰는 세 번째 백엔드가 선택됩니다. 이 보고서에서는 측정하지 않았습니다.

## 3. 파일 접근

| 시험 | Restricted Token | AppContainer |
| --- | --- | --- |
| ISO-01 작업 폴더 안 읽기·쓰기 | 통과 5/5 | 통과 5/5 |
| ISO-02 작업 폴더 밖 읽기 | 실패: 읽힘 5/5 | 통과: 거부 5/5 |
| ISO-03 작업 폴더 밖 쓰기 | 경로 권한에 따름. 사용자 임시 폴더는 거부 5/5, Everyone 모든 권한이 걸린 공용 폴더는 덮어써짐 5/5 | 통과: 거부, 원본 유지 5/5 |
| ISO-06 정리 후 작업 폴더 파일 유지 | 통과(1회) | 통과(1회) |
| ISO-07 읽기 전용 하위 폴더 | 실패: 덮어쓰기·이름 변경·삭제 됨(1회) | 실패: 쓰기·삭제 권한까지 모두 열림 5/5 |
| ISO-08·09 접근 거부 하위 폴더, 시작 후 생긴 파일 | 미지원: 읽기·덮어쓰기·삭제 됨(1회) | 실패: 거부 설정이 걸려 있어도 모든 권한 열림 5/5 |

- **Restricted Token의 쓰기 허용 범위는 폴더 DACL에 따라 정해집니다.** 제한 SID 목록에 Everyone이 있어서, DACL에 Everyone 쓰기 허용 ACE가 있는 폴더에는 쓰기가 허용됩니다.
  - 시험 폴더에 Everyone 수정 허용 ACE만 추가하자 덮어쓰기가 5/5 성공했습니다.
  - INTERACTIVE 수정 허용 ACE를 추가한 폴더는 5/5 거부됐습니다.
  - 다른 프로그램이 만든 공용 폴더처럼 Everyone에게 쓰기를 허용한 폴더에는 샌드박스 프로세스가 쓸 수 있습니다.
- **AppContainer 읽기 전용 하위 폴더에 쓰기가 허용된 원인은 QwenPaw 구성입니다.** 하위 폴더에 읽기·실행 허용 ACE를 추가하기만 하고, 작업 폴더에서 상속된 수정 허용 ACE를 제거하지 않습니다.
- **AppContainer 거부 하위 폴더**에는 AppContainer SID 대상 모든 접근 거부 ACE가 폴더와 기존·신규 파일에 실제로 설정돼 있었습니다.
  - 자식 프로세스의 토큰은 AppContainer 토큰, 무결성 수준 Low, capability SID 없음이었고, 토큰의 AppContainer SID가 거부 ACE의 SID와 같았습니다.
  - 그런데도 목록·읽기·쓰기·삭제 권한이 모두 허용됐습니다. Windows가 이 거부 ACE를 적용하지 않은 이유는 문서로 확인하지 못했습니다.
- **처음 기록한 "AppContainer는 목록·삭제를 막았다"는 보호 효과가 아니었습니다.** AppContainer 안에서는 cmd의 `dir`·`del`이 보호 설정이 없는 작업 폴더에서도 실패합니다. 같은 일을 Python으로 하면 성공합니다.

## 4. 파일 밖 자원

| 시험 | Restricted Token | AppContainer |
| --- | --- | --- |
| ISO-04 환경 변수 허용 목록 | 실패: 호스트 값 노출(허용·차단 구성 각 1회) | 실패: 같음 |
| ISO-05 네트워크 전체 차단 | 실패: 프록시 환경 변수를 사용하는 프로그램만 연결 실패. `curl --noproxy "*"`는 외부 연결 성공 5/5 | 통과: DNS 조회 단계에서 실패 5/5, `--noproxy`도 실패 |
| ISO-05 도메인 허용 목록 | 실패: 목록에 없는 도메인 접속 성공 5/5 | 실패: 같음 5/5 |
| ISO-10 호스트의 로컬 서버 접속 | 네트워크 허용 시 성공 5/5. 차단 시에는 프록시 환경 변수를 사용하는 프로그램만 실패 | 실패: 시간 초과 5/5(네트워크 허용·차단 모두) |
| ISO-10 샌드박스 안 개발 서버 | 바인딩, 같은 프로세스 접속, 호스트에서 접속 모두 성공 5/5 | 바인딩과 같은 프로세스 접속은 성공, 호스트에서 접속은 실패 5/5 |
| ISO-11 호스트의 명명된 파이프 | 읽기 성공, 쓰기 거부 5/5 | 읽기·쓰기 거부 5/5 |
| ISO-12 사용자 레지스트리 읽기 | 시험한 키 모두 읽음 5/5 | 키 권한대로: `Environment` 등은 읽힘, `Console`과 자동 실행(`Run`) 키는 거부 5/5 |
| ISO-12 사용자 레지스트리 쓰기 | 통과: 값 쓰기·하위 키 생성 권한 거부 5/5 | 통과: 같음 5/5 |
| ISO-13 클립보드 | 실패: 열림 5/5 | 실패: 열림 5/5 |
| ISO-14 프로세스 수·메모리 한도 | 미지원: 1개·64 MB로 지정해도 자식 3개 동시 실행, 256 MB 할당 5/5 | 미지원: 같음 5/5 |

- **네트워크.**
  - Restricted Token에는 네트워크 접근을 제한하는 기능이 없습니다. 그래서 QwenPaw는 아무것도 수신하지 않는 주소 `127.0.0.1:9`를 프록시 환경 변수로 지정하고, 생성할 때 "프록시를 무시하는 연결은 막지 못한다"고 경고합니다.
  - 도메인 단위 허용은 두 백엔드 모두 구현돼 있지 않고, 제품도 "모든 네트워크가 허용된다"고 경고합니다. AppContainer는 목록이 비어 있지 않으면 네트워크 capability SID 세 개를 모두 넣습니다.
- **로컬 연결.** AppContainer는 Windows의 기본 루프백 격리 때문에 호스트와 컨테이너 사이 로컬 연결이 양방향으로 막힙니다. QwenPaw는 예외를 설정하지 않습니다.
- **레지스트리 쓰기.** Restricted Token은 제한 SID 목록에 사용자 SID가 없고, 사용자 레지스트리 키의 DACL은 제한 SID 목록의 SID에게 쓰기를 허용하지 않아 거부됩니다. 레지스트리 값은 쓰지 않았고, 쓰기 권한으로 열리는지만 확인했습니다.
- **클립보드.** 열 수 있는지만 확인하고 내용은 읽지 않았습니다. 두 방식 모두 사용자와 같은 창 스테이션·데스크톱(`WinSta0\Default`)을 쓰고, QwenPaw는 Job 객체의 UI 제한(클립보드 읽기·쓰기 제한 등)을 설정하지 않습니다.

## 5. 명령 수명과 정리

| 시험 | Restricted Token | AppContainer |
| --- | --- | --- |
| ISO-06 시간 초과 시 자식 프로세스 | 통과: 5초 안에 종료 5/5 | 실패: 자식이 살아 있고 호출도 반환되지 않음 5/5 |
| ISO-06 셸 종료 뒤 남은 백그라운드 자식 | 실패: 시간 제한을 넘겨 계속 실행, 호출 반환 안 됨 5/5 | 실패: 같음 5/5 |
| ISO-06 전용 임시 폴더 | 미지원: 호스트의 `TEMP` 값을 그대로 받았고 그 폴더에 쓰지도 못함 5/5 | 통과: AppContainer 프로필의 전용 임시 폴더. `stop()` 뒤에는 남고 `destroy()`에서 삭제 5/5 |
| ISO-06 호스트 프로세스 비정상 종료 | 자식 종료 5/5. 작업 폴더 ACE는 다음 실행의 정리까지 남음 5/5 | 미실측 |
| ISO-14 입력을 기다리는 명령 | 입력 종료 신호 없이 3초 제한까지 대기(1회) | 같음(1회) |

- QwenPaw의 시간 제한은 셸 프로세스에만 걸리고, 호출은 출력 파이프가 닫힐 때까지 기다립니다. 개발 서버나 파일 감시 도구를 백그라운드로 띄우면 도구 호출 하나가 끝나지 않습니다.
- Restricted Token만 명령을 Job 객체로 묶어, 시간 초과 시 자식까지 한꺼번에 종료합니다.

## 6. 작업 호환성

| 작업 | Restricted Token | AppContainer |
| --- | --- | --- |
| 공통 합성 워크로드(`run.cmd`) | 성공 5/5 | 성공 5/5 |
| 순차 빌드, 자식 프로세스 동시 실행 | 됨 | 됨 |
| Python 병렬 빌드(작업 프로세스 4개) | 안 됨 5/5 | 안 됨 5/5 |
| 사용자가 설치한 Python 실행 | 됨 | 안 됨: 설치 폴더 DACL에 AppContainer SID나 `ALL APPLICATION PACKAGES` 허용 ACE가 없음 |
| cmd `dir`·`del` | 됨 | 안 됨: 작업 폴더 안에서도 실패 |
| `ping` | 측정 안 함 | 안 됨 |
| 호스트의 로컬 서버·데이터베이스 접속 | 됨 | 안 됨 |
| 샌드박스 안 개발 서버를 호스트 브라우저에서 접속 | 됨 | 안 됨 |
| 호스트 `TEMP` 폴더에 쓰기 | 안 됨 | 해당 없음(전용 임시 폴더) |
| Git Bash를 셸로 사용 | 모든 명령 실패 5/5 | 측정 안 함 |

- **병렬 빌드.** 두 방식 모두 작업 프로세스를 만들기 전에, 명명된 파이프를 만드는 단계에서 권한 거부(`WinError 5`)가 났습니다. 명명된 파이프로 작업 프로세스와 통신하는 도구는 같은 문제를 겪을 수 있습니다. 다른 빌드 도구는 측정하지 않았습니다.
- **Git Bash.** QwenPaw는 `SHELL` 환경 변수를 따라 셸을 고릅니다. Git Bash에서 QwenPaw를 띄우면 Restricted Token 안에서 bash가 시작하자마자 끝나고, 제품은 이를 "샌드박스 위반"으로 분류해 격리 없이 실행할지 묻습니다.

## 7. 정리와 운영 부담

- **Restricted Token.** 실행 중 작업 폴더 DACL에 capability SID의 ACE를 추가합니다. `stop()`으로는 지워지지 않고, 프로세스 종료 시 등록되는 정리 함수나 다음 실행이 지웁니다. 비정상 종료하면 다음 실행까지 남습니다.
- **AppContainer.**
  - 실제 사용자 프로필 아래에 AppContainer 프로필 폴더(`%LOCALAPPDATA%\Packages\qwenpaw_<id>`)가 생기고, 사용자 레지스트리(HKCU)에 AppContainer SID 매핑이 등록됩니다. 둘 다 `destroy()`에서 삭제됐습니다(5/5).
  - 작업 폴더의 ACE(5/5)와 QwenPaw Python 폴더의 ACE(20/20)도 `destroy()`에서 삭제됐습니다.
  - 그런데 시험용 Python 가상환경 폴더에는 이전 실행이 남긴 것으로 보이는 AppContainer SID의 ACE 4개가 있었습니다. 출처는 확정하지 못했고 변경하지 않았습니다. 비정상 종료하면 정리되지 않는 경로가 있을 수 있습니다.
- 샌드박스 초기 설정 시간은 측정하지 않았습니다.

## 8. Windows가 만든 결과와 QwenPaw가 만든 결과

| 결과 | 원인 |
| --- | --- |
| Restricted Token에서 작업 폴더 밖 읽기, 레지스트리 읽기, 파이프 읽기 허용 | Windows: `WRITE_RESTRICTED` 토큰은 쓰기만 제한 SID 목록으로 추가 검사 |
| Restricted Token에서 사용자 레지스트리·파이프 쓰기 거부 | Windows |
| Everyone에게 쓰기가 허용된 위치에 Restricted Token이 씀 | QwenPaw: 제한 SID 목록에 Everyone을 넣음 |
| Restricted Token 네트워크 차단 실패 | Restricted Token에 네트워크 제한 기능이 없고, QwenPaw는 프록시 환경 변수만 설정 |
| AppContainer의 작업 폴더 밖 읽기·쓰기, 네트워크, 파이프 차단 | Windows |
| AppContainer의 로컬 연결 양방향 차단 | Windows 루프백 격리. QwenPaw는 예외를 설정하지 않음 |
| AppContainer에서 사용자 설치 도구, cmd `dir`·`del`, `ping` 실패 | Windows 구조(호환성) |
| AppContainer 읽기 전용 하위 폴더 실패 | QwenPaw: 상속된 수정 허용 ACE를 제거하지 않음 |
| AppContainer 거부 하위 폴더 실패 | 거부 ACE는 설정됐지만 Windows가 적용하지 않음(이유 미확인) |
| 두 방식 모두 명명된 파이프 병렬 빌드 실패 | Windows 구조로 판단: 두 방식 모두 작업 프로세스용 명명된 파이프 생성이 거부됨 |
| 환경 변수·도메인 허용 목록, 자원 한도 미집행 | QwenPaw |
| AppContainer 시간 초과 시 자식 생존, 두 방식의 백그라운드 자식 | QwenPaw: AppContainer는 Job 객체를 쓰지 않고, 호출은 출력 파이프가 닫힐 때까지 기다림 |
| 두 방식 모두 클립보드 열림 | 사용자와 같은 창 스테이션 사용. QwenPaw가 Job 객체의 UI 제한을 설정하지 않음 |

다른 제품을 측정할 때 이 표가 기준이 됩니다. Windows 쪽 결과는 같은 방식을 쓰면 반복될 가능성이 높습니다. QwenPaw 쪽 결과는 구성에 따라 달라질 수 있습니다.

## 9. 실제 에이전트 경로 (ISO-15~18)

백엔드가 실제 에이전트에서 어떻게 쓰이는지 측정했습니다. 조건은 `security.sandbox_enabled=true`, 기본 정책 수준 `smart`, 관리자 권한 없는 계정입니다. 이 경로는 Restricted Token과 "네트워크 전체 허용"으로 샌드박스를 만들었습니다.

| 상황 | 결과(각 5회) |
| --- | --- |
| 기본 설정 | `security.sandbox_enabled` 기본값이 꺼짐이라 셸에 격리가 적용되지 않음(소스 확인) |
| 샌드박스가 막은 명령을 승인 | 같은 명령이 격리 없이 내 계정 권한으로 다시 실행됨. 승인 화면에는 "격리 없이 재실행" 경고가 있음 |
| 거부하거나 응답하지 않음 | 실행되지 않음. 감사 기록은 둘 다 `User Deny`로 남아 구분되지 않음 |
| 승인 뒤 같은 세션의 같은 명령 | 묻지 않고 격리 없이 실행됨. 규칙이 디스크에 저장돼, 거버넌스 객체를 다시 만들어도 같은 세션이면 유지됨 |
| 승인 뒤 다른 명령, 또는 다른 세션의 같은 명령 | 다시 물음 |
| 승인을 기다리는 동안 거부 규칙 추가 | 기다리던 명령은 승인되면 그대로 실행됨. 새 규칙은 그 뒤의 호출에만 적용됨 |
| 가장 엄격한 `strict` 수준에서 승인 | 실행 전에 묻지만, 승인된 명령은 격리 없이 실행됨 |
| 파일 쓰기 도구로 작업 폴더 밖에 쓰기 | 승인 없이 써짐. 샌드박스를 거치지 않음 |
| 파일 읽기 도구로 작업 폴더 밖 읽기 | 허용됨 |

실제 에이전트의 보안 수준은 백엔드보다 이 경로가 결정합니다. AppContainer의 강한 격리는 이 경로에서 쓰이지 않습니다. Restricted Token의 쓰기 차단도 승인 한 번이나 파일 도구로 우회됩니다.

## 10. 판단과 권고

- **Restricted Token(QwenPaw 구성)** 은 신뢰하는 에이전트가 실수로 작업 폴더 밖 파일을 고치는 일을 줄이는 장치입니다. 비밀 파일 읽기와 외부 전송을 막지 못하므로, 신뢰하지 않는 코드나 프롬프트 주입을 막는 경계는 아닙니다.
- **AppContainer(QwenPaw 구성)** 은 파일·네트워크·명명된 파이프 접근 제한이 실제로 작동합니다. 그러나 다음 한계가 있습니다.
  - 작업 폴더 안 세부 보호를 할 수 없고, 클립보드가 열립니다.
  - 개발 도구 호환성이 낮고, 자식 프로세스와 자원 관리가 부족합니다.
  - 에이전트 경로에서 선택되지 않습니다.

권고는 다음과 같습니다.

1. 신뢰하지 않는 작업에는 전용 계정이나 가상 머신 같은 별도 경계를 함께 씁니다.
2. QwenPaw를 쓴다면 `security.sandbox_enabled`를 켜고, "격리 없이 재실행" 승인은 기본적으로 거부합니다. 파일 도구는 샌드박스 밖에서 실행된다는 점을 전제로 정책을 정합니다.
3. Restricted Token을 쓰는 PC에서는 DACL에 Everyone 쓰기 허용 ACE가 있는 폴더를 점검합니다. 이런 폴더에는 샌드박스 프로세스가 쓸 수 있습니다.
4. 비밀을 작업 계정이 읽을 수 있는 파일, 사용자 환경 변수, 클립보드에 두지 않습니다. Restricted Token은 모두 읽고, AppContainer도 사용자 환경 변수 레지스트리 키는 읽습니다.
5. QwenPaw를 Git Bash에서 실행하지 않습니다.

## 11. 한계와 미실측 항목

- **일반화의 한계.** QwenPaw의 구성을 측정한 결과입니다. 다른 제품의 Restricted Token(예: Codex)은 제한 SID 목록, 읽기 제한, 별도 데스크톱 사용이 다를 수 있습니다.
- **측정하지 않은 백엔드.** 관리자 백엔드(별도 계정과 방화벽 규칙)는 측정하지 않았습니다.
- **성능 비용.** 공통 워크로드 한 번의 호출 시간 중앙값은 Restricted Token 41.6 ms, AppContainer 51.6 ms였습니다. 호스트 기준은 시작 호출 2.0 ms와 종료 대기 34.4 ms였습니다. 측정 방법이 달라 추가 비용으로 바로 비교할 수는 없습니다. 샌드박스 초기 설정 시간도 측정하지 않았습니다.
- **측정 조건.** PC 한 대에서 측정했고, 언어 모델 없이 측정 스크립트로 같은 코드 경로를 호출했습니다.
- **미실측 항목**
  - 다른 사용자 세션의 레지스트리 접근(두 번째 계정이나 가상 머신 필요)
  - 자격 증명 관리자의 시험용 자격 증명(동의 필요)
  - 클립보드 내용 읽기·쓰기, 창·화면·입력(동의 필요)
  - AppContainer 호스트 비정상 종료
  - 브라우저와 MCP(Model Context Protocol) 도구가 실행되는 위치
- **1회만 측정한 항목.** Restricted Token 하위 폴더 조작, 환경 변수, 지속 파일, 입력을 기다리는 명령.
- **원인을 확정하지 못한 항목.** AppContainer SID 대상 거부 ACE가 적용되지 않은 이유, 초기 측정에서 AppContainer `curl`이 거부된 이유(당시 PATH 기록 없음).

- **Codex `elevated`.** 관리자 승인으로 만든 별도 저권한 계정과 방화벽 규칙으로 실행합니다. QwenPaw의 관리자용 백엔드와 같은 계열이며, 이 보고서에서는 측정하지 않은 방식입니다. 계정·시스템 설정에 미치는 영향을 실행 조건으로 기록합니다.

  - 명령이 끝날 때 남은 자식의 종료
  - 권한 확대를 승인한 뒤에도 읽기 거부가 유지되는지
