- **제한 SID가 하나라도 있으면 schannel과 Negotiate 모두 자격 증명을 얻지 못했습니다.**
  - 실패 코드는 모두 `SEC_E_NO_CREDENTIALS`(`0x8009030e`)였습니다. 4종의 결과는 회차마다 같았습니다.

## 4. 해석

- **「online 계정만 프로필 로드」로는 schannel HTTPS 실패가 풀리지 않습니다.** 원인은 셸 토큰이 제한 토큰이라는 점입니다. 제한 SID 목록의 구성이나 `WRITE_RESTRICTED` 여부와 무관했습니다.
- **같은 구조를 유지하면 셸 안에서 다음이 되지 않습니다.**
  - schannel을 쓰는 HTTPS: `curl.exe`, PowerShell 5.1 `Invoke-WebRequest`, Git의 schannel 백엔드
  - Negotiate 자격 증명 획득
  - OpenSSL을 쓰는 Python urllib는 모든 칸에서 됐습니다.
- **프로필을 로드하면 생기는 차이.**
  - 셸의 HKCU가 계정 자신의 하이브가 되어, 제한 토큰으로도 쓰고 다음 실행에서 다시 읽습니다. 이 계정을 쓰는 모든 작업 폴더가 이 값을 공유합니다.
  - 프로필 폴더가 생기고, 지운 뒤에도 HKLM 키 2개가 남습니다.

## 6. 확인하지 못한 것

- LSA와 schannel이 제한 토큰을 어떻게 판정해 `SEC_E_NO_CREDENTIALS`를 내는지는 확인하지 못했습니다. ETW나 Process Monitor 추적은 하지 않았습니다.
- 실제 Codex online 계정과 `codex sandbox`로는 다시 재지 않았습니다. 같은 호출 형태의 시험 실행기로 쟀습니다.
  - Codex와 다른 점은 2026-11-26-03과 같습니다. 개인 바탕 화면 대신 `WinSta0\Default`를 썼고, 표준 입출력은 파일과 빈 파이프입니다.
