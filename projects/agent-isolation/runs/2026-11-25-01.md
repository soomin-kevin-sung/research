## 2. 측정 준비 중 실제 Codex `elevated` 1회 실행

측정 준비 중 `codex sandbox windows --help`를 실행했습니다. `--` 없이 실행했기 때문에 Codex는 `--help`를 도움말 옵션이 아니라 샌드박스에서 실행할 명령으로 받았습니다. 그 결과 실제 `~/.codex`로 `elevated` 샌드박스가 한 번 실행됐습니다.

계정 재설치는 일어나지 않았습니다. 바뀐 것은 다음과 같고, 모두 읽기 전용으로 확인했습니다.

- `.sandbox-bin`에 `codex-command-runner-0.172.0.exe` 사본이 추가됐습니다.
- 프로필 바로 아래 폴더 2개에 `CodexSandboxUsers` 읽기 ACE가 추가됐습니다.
- `deny_read_acl_state.json` 내용이 `{"principals": {}}`로 다시 쓰였습니다.
- 로그와 모델 캐시가 생겼습니다.

이후 모든 Codex 실행은 `CODEX_HOME`과 백엔드를 명시하고 명령 앞에 `--`를 붙였습니다.

### Codex `elevated`가 만든 보호 폴더 때문에 작업 폴더를 쓸 수 없게 됨

B6 추가 측정에서 Codex `elevated` 샌드박스가 작업 폴더 B에 `.git`·`.agents`·`.codex`를 만들었습니다. 이후 작업 폴더 B의 모든 명령이 실패했습니다.

- **소유자.** 새로 만든 세 폴더의 소유자는 `CodexSandboxOffline`이었습니다. 상속된 ACE만 있었습니다.
- **실패 과정.** 다음 명령의 갱신 단계는 사용자 권한으로 실행되며, 이 폴더에 쓰기 거부 ACE를 추가하려고 `WRITE_DAC`로 열었습니다. 결과는 `os error 5`였습니다.
- **결과.** 갱신 단계가 `setup refresh had errors`로 끝났고, 명령이 시작되지 않았습니다. 로그에 같은 오류가 16번 기록됐습니다.
- **복구.** 세 폴더를 지운 뒤 B8b와 P6 그룹을 다시 측정했습니다.

정리하면, 샌드박스 명령이 보호 대상 폴더를 처음 만들 수 있고, 그렇게 만들어진 폴더 때문에 그 작업 폴더에서는 이후 명령을 실행할 수 없게 됩니다.

- **두 비관리자 구성.** 현재 사용자가 읽는 것을 모두 읽습니다. 사용자 범위 DPAPI 데이터도 복호화합니다.
- **Codex `elevated`.**
  - **읽기 범위.** 계정이 달라 사용자만 허용한 파일과 `.ssh`는 읽지 못했습니다.
  - **그래도 읽은 위치.** `~/.codex`의 인증·설정 파일, `AppData`, `.gitconfig`, 프로필 아래 새 폴더는 읽었습니다.
    - 이 항목들에는 측정 전부터 `CodexSandboxUsers` 읽기 ACE가 있었습니다. `.ssh`에는 없었습니다.
    - 프로필 루트에서 상속되는 `Users`·`Everyone` 읽기도 있었습니다.
    - 그래서 "다른 계정이라 사용자 파일을 못 읽는다"는 이 PC에서 `.ssh`처럼 DACL을 보호한 위치에만 해당합니다.
  - **DPAPI.** 사용자 범위 데이터는 사용자 마스터 키로 암호화되므로 다른 계정은 복호화하지 못합니다(`NTE_BAD_KEY_STATE`).
- **비밀번호 파일.** `~/.codex\.sandbox-secrets`는 두 비관리자 구성에서 읽혔고, 컴퓨터 범위 DPAPI 복호화도 허용됐습니다. Codex는 샌드박스 계정 비밀번호를 컴퓨터 범위 DPAPI로 저장합니다. 따라서 이 두 결과를 합치면 비관리자 샌드박스 안에서 Codex 샌드박스 계정의 비밀번호를 얻을 수 있다는 뜻이 됩니다. 실제 파일 복호화는 하지 않았습니다.

### C5·C6 읽기 거부 (각 5회)

QwenPaw는 `deny_paths`, Codex는 `isodeny` 프로필로 `targets\deny-read`의 읽기 거부를 요청했습니다.

측정 방법은 다음과 같습니다.

1. 매 회차 먼저 거부 설정 없이 같은 파일을 샌드박스에서 읽어 양성 대조를 확인했습니다.
2. 거부 설정으로 명령을 시작했습니다.
3. 명령이 신호를 보낸 뒤 호스트가 새 파일을 만들고, 다른 폴더의 파일을 거부 폴더로 옮겼습니다.

| 확인 항목 | QwenPaw 비관리자 | Codex `unelevated` | Codex `elevated` |
| --- | --- | --- | --- |
| 실행 | 경고 없이 실행 | `Restricted read-only access requires the elevated Windows sandbox backend`로 실행 거부(종료 코드 1) 5/5 | 실행 |
| 기존 파일 읽기 | 허용 5/5 | — | 거부 5/5 |
| 시작 뒤 만든 파일 | 허용 5/5 | — | 거부 5/5 |
| 시작 뒤 옮겨 온 파일 | 허용 5/5 | — | **허용** 5/5 |
| 다른 폴더의 하드 링크로 읽기 | 허용 5/5 | — | 거부 5/5 |
| 거부 폴더 안 원래 경로로 읽기 | 허용 5/5 | — | 거부 5/5 |

- **Codex `elevated`가 붙이는 거부 ACE.** 거부 폴더에 `CodexSandboxUsers` 대상 거부 ACE 두 개가 붙었습니다.
  - 폴더 자체: `0x120089`(읽기)
  - 상속용: `OI|CI|IO`, `GENERIC_READ` 포함
- **같은 폴더 안 파일은 막힘.** 새로 만든 파일은 상속으로 막혔습니다. 하드 링크는 같은 파일 객체이므로 다른 경로로 열어도 막혔습니다.
- **옮겨 온 파일은 막히지 않음.** 같은 볼륨 안에서 옮긴 파일은 원래 DACL을 그대로 가지고 와서 거부 ACE를 상속받지 않습니다.
- **QwenPaw.** 비관리자 구성은 읽기 거부를 적용하지 않습니다.
- **Codex `unelevated`.** 적용할 수 없는 정책이면 명령을 시작하지 않습니다.

### 거부 설정을 지워도 Codex `elevated`의 거부 ACE가 남음

- **관찰.** 2~5회차의 양성 대조(거부 설정 없는 `iso` 프로필)도 거부됐습니다. 1회차가 붙인 거부 ACE가 그대로 있었기 때문입니다.
- **영향.** 이 ACE는 `CodexSandboxUsers` 그룹 대상입니다. 따라서 설정에서 경로를 지운 뒤에도 모든 작업 폴더의 Codex `elevated` 실행이 그 경로를 읽지 못합니다.
- **소스상 설계.** [상태 동기화 함수](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/windows-sandbox-rs/src/deny_read_state.rs)의 의도는 다음과 같습니다.
  1. 적용한 경로를 `deny_read_acl_state.json`에 기록합니다.
  2. 다음 실행에서 원하는 목록에 없는 경로의 ACE를 `revoke_ace`로 지웁니다.
- **실측 동작.**
  - 갱신 로그에 `applied 1 deny-read ACLs`가 5번 기록됐습니다.
  - 거부 설정이 없는 다음 실행은 상태 파일에서 이 경로를 지웠습니다. 상태 파일은 측정 전과 같은 `{"principals": {}}`로 돌아갔습니다.
  - 그러나 거부 ACE는 남았습니다.
- **원인.** `revoke_ace`는 `SetEntriesInAclW`에 `REVOKE_ACCESS`를 넘깁니다([`acl.rs`](https://github.com/openai/codex/blob/rust-v0.171.0/codex-rs/windows-sandbox-rs/src/acl.rs)). [`ACCESS_MODE` 문서](https://learn.microsoft.com/windows/win32/api/accctrl/ne-accctrl-access_mode)에 따르면 `REVOKE_ACCESS`는 해당 SID의 허용 ACE와 감사 ACE만 지웁니다. 시험 폴더에서 같은 호출을 재현해 확인했습니다. 같은 SID의 허용 ACE는 지워지고 거부 ACE는 남았습니다.
- **결과.** 상태 파일에서는 지워졌으므로 Codex가 이 ACE를 다시 찾아 지울 방법도 없습니다.
- **정리.** 측정 뒤 이 ACE는 `icacls /remove:d`로 지웠습니다. 실제 환경에서 읽기 거부를 썼던 경로에도 같은 ACE가 남아 있을 수 있습니다.

## 6. QwenPaw 작업 폴더에 남은 capability SID ACE

측정 뒤 QwenPaw 작업 폴더 A에 capability SID 허용 ACE(`0x1301bf`) 15개가 남아 있었습니다. 메타데이터 파일은 남아 있지 않았습니다.

**원인: 재사용 확인이 이 PC에서 항상 실패**
- QwenPaw는 같은 설정의 샌드박스 메타데이터가 있으면 `_verify_acl_present_sync`로 ACE가 남아 있는지 확인하고 그 capability SID를 다시 씁니다.
- 이 함수는 `icacls` 출력 문자열에서 SID를 찾습니다. 이 PC에서는 도메인 트러스트 오류 때문에 `icacls`가 ACE의 SID 자리를 비워서 출력합니다.
- 그래서 API로는 ACE 15개가 보이는데도 이 함수는 `False`를 돌려줬습니다(직접 호출해 확인).

**ACE가 남는 과정**
1. 재사용에 실패하면 QwenPaw는 새 capability SID를 만들고, 같은 이름의 메타데이터 파일을 덮어씁니다.
2. 이전 QwenPaw 프로세스가 강제 종료되어 정리하지 못한 ACE는 기록이 사라진 채로 남습니다.
3. 측정에서 작업 폴더 A의 QwenPaw 작업자를 강제 종료한 횟수는 G1·P6·r2x 각 5회, 합계 15회로 남은 ACE 수와 같습니다.

**판정과 영향**
- 회사 도메인 환경 때문에 생긴 실패로 기록합니다. SID 조회가 되는 PC에서는 재사용 확인이 성공할 것으로 예상합니다.
- 남은 ACE의 SID는 무작위 값이라 다시 쓰이지 않습니다. 따라서 다른 실행에 쓰기 권한을 주지는 않습니다. 대신 DACL에 계속 쌓입니다.
- 2026-11-24 실측의 "비정상 종료하면 다음 실행의 정리까지 남음"은 메타데이터가 남아 있을 때의 결과입니다.

### P4·P7 사용자 프로세스 전체 (P4는 1회, P7은 각 5회)

P4는 사용자 프로세스를 `QUERY_LIMITED`로만 열었습니다. P1 시험 프로세스는 DACL에 로그온 SID ACE가 없어 일반 데스크톱 프로세스와 달랐습니다. 그래서 사용자 프로세스 전체를 권한별로 여는 P7을 추가했습니다.

- **P7 방식.** 호스트는 각 프로세스의 DACL을 `READ_CONTROL`로 읽어 로그온 SID ACE가 있는지 분류만 했습니다. 프로세스 이름은 저장하지 않았습니다.
- **대상 수.** P7의 사용자 프로세스는 회차마다 213~234개였습니다(QwenPaw 비관리자 213~220, Codex `unelevated` 213~234, Codex `elevated` 215~233). 아래 분류 수에는 목록을 만든 뒤 여는 사이에 종료된 프로세스가 들어 있습니다. 결과 표의 개수는 종료된 프로세스를 뺀 값입니다.
  - 로그온 SID ACE가 있는 프로세스: 106개(explorer 포함). 여는 사이에 종료된 프로세스는 없었습니다.
  - 로그온 SID ACE가 없는 프로세스: 104~117개. 여는 사이에 종료된 0~10개를 빼면 104~108개입니다.
  - 호스트가 DACL을 읽지 못한 프로세스: 3~12개(측정 중 종료된 프로세스 포함)

| --- | --- | --- | --- |
| P4 `QUERY_LIMITED`로 열림(1회) | 212/212 | 212/212 | 119/213 |
| P7 로그온 SID ACE 있는 프로세스: `VM_READ`·`TERMINATE`·토큰 `DUPLICATE`·`IMPERSONATE`·`ASSIGN_PRIMARY` | 106/106 | 106/106 | **96/106** |

**두 비관리자 구성: 프로세스 권한이 갈리는 기준**
- 허용·거부가 나뉜 경계는 각 객체 형식의 `GENERIC_WRITE` 매핑과 정확히 일치합니다.
  - 프로세스: `VM_WRITE`·`VM_OPERATION`·`CREATE_THREAD`·`DUP_HANDLE`은 `GENERIC_WRITE`에 속합니다. `TERMINATE`·`QUERY_LIMITED`·`SYNCHRONIZE`는 `GENERIC_EXECUTE`에 속합니다.
  - 토큰: `ADJUST_DEFAULT`만 `GENERIC_WRITE`(`TOKEN_WRITE`)에 속합니다.
- `WRITE_RESTRICTED` 토큰은 제한 SID 검사를 쓰기 권한에만 적용합니다. 나머지 권한은 사용자 SID만으로 허용됩니다.
- 따라서 두 비관리자 구성의 샌드박스 명령은 사용자의 거의 모든 프로세스에 대해 다음을 할 수 있습니다.
  - 메모리 읽기 권한(`VM_READ`)과 종료 권한(`TERMINATE`)으로 열기
  - 그 프로세스의 제한 없는 토큰을 `DUPLICATE`·`IMPERSONATE`·`ASSIGN_PRIMARY`로 열기

**Codex `elevated`: 다른 계정이어도 사용자 프로세스가 열림**
- 계정이 달라도 사용자의 로그온 SID를 공유합니다.
- 로그온 세션 기본 DACL로 만들어진 사용자 프로세스는 로그온 SID에 권한을 줍니다. 예를 들어 explorer DACL은 로그온 SID에 `0x121411`(`VM_READ`, `QUERY_INFORMATION`, `TERMINATE` 포함)을 줍니다.
- 그래서 그런 프로세스는 `VM_READ`·`TERMINATE`로 열립니다.
- 다른 계정 사용으로 막히는 것은 DACL에 로그온 SID ACE가 없는 프로세스뿐이었습니다.

**P5 실행기와 P6 동시 실행 샌드박스**
- **P5 실행기.** Codex `elevated`의 실행기는 샌드박스 계정의 제한 없는 토큰으로 실행되고, 샌드박스 명령의 부모입니다. 샌드박스 명령은 이 실행기를 `VM_WRITE`·`CREATE_THREAD`로 열 수 있었습니다.
- **P6 동시 실행 샌드박스.**
  - QwenPaw 기본 DACL은 Everyone에 `GENERIC_ALL`을 줍니다.
  - Codex 기본 DACL은 로그온 SID에 `GENERIC_ALL`을 줍니다. 로그온 SID는 모든 실행과 사용자 프로세스가 공유하므로, 소스 주석이 설명한 "다른 실행의 접근 차단"은 이루어지지 않았습니다.
  - 결과적으로 작업 폴더 B에 직접 쓰기는 막혀도(B5), 동시에 실행 중인 작업 폴더 B의 샌드박스 프로세스는 쓰기·스레드 생성 권한으로 열립니다.
